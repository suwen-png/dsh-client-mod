## 一、开发流程规范

### 1.1 标准开发链路

```
需求确认 → 任务拆解 → 开发实现 → 本地验证 → 代码提交 → 自动构建 → 测试验证 → 部署上线
```

### 1.2 各阶段要求

| 阶段 | 输入 | 输出 | 验收标准 |
|:-----|:-----|:-----|:---------|
| 需求确认 | 用户需求/02-需求清单 | 需求确认记录 | 需求无歧义，验收标准明确 |
| 任务拆解 | 确认后的需求 | 03-待完成任务清单条目 | 任务可独立执行，有预估工时 |
| 开发实现 | 任务条目+设计方案 | 代码变更 | 符合编码规范，无语法错误 |
| 本地验证 | 代码变更 | 验证结果 | 构建通过，核心功能正常 |
| 代码提交 | 验证通过的代码 | Git commit | 提交信息规范，关联任务ID |
| 自动构建 | Git push | 构建产物 | CI 流水线通过，无报错 |
| 测试验证 | 构建产物 | 测试报告 | 测试用例通过率达标 |
| 部署上线 | 测试通过的产物 | 部署记录 | 线上功能正常，无回滚 |

### 1.3 代码提交规范

**提交信息格式**：
```
{类型}: {简短描述}

{详细说明（可选）}

关联任务: {任务ID}
```

**类型枚举**：
- `feat`: 新功能
- `fix`: Bug修复
- `refactor`: 代码重构
- `docs`: 文档更新
- `style`: 代码格式（不影响功能）
- `test`: 测试相关
- `chore`: 构建/工具/依赖调整
- `perf`: 性能优化

**示例**：
```
feat: 新增用户登录模块

实现邮箱+密码登录，支持JWT token鉴权
关联任务: T-015
```

## 二、编码规范

### 2.1 通用规范

1. **文件编码**：UTF-8（无 BOM）
2. **缩进**：Python 用 4 空格，TypeScript/JS 用 2 空格
3. **行尾**：LF（Unix 风格），Windows 开发环境配置 git autocrlf
4. **文件命名**：小写+短横线（kebab-case），Python 模块用 snake_case
5. **注释规范**：
   - 脚本头部必须有 SCRIPT-META 标准注释块
   - 函数必须有 docstring（入参、返回值、异常）
   - 复杂逻辑必须有行内注释

### 2.2 Python 规范

1. 遵循 PEP 8，行宽最大 120 字符
2. 类型注解强制：函数参数和返回值必须有类型注解
3. 异常处理：禁止裸 except，必须指定异常类型
4. 日志规范：使用 logging 模块，禁止 print 输出生产日志
5. 虚拟环境：使用 venv，依赖写入 requirements.txt

### 2.3 TypeScript/JS 规范

1. 遵循 ESLint + Prettier 配置
2. 优先使用 TypeScript，禁止 any 类型（除非明确注释原因）
3. 异步操作使用 async/await，禁止回调地狱
4. 模块导入使用绝对路径（配置 path alias）

## 三、CI/CD 流水线

### 3.1 流水线阶段

```
代码提交 → 静态检查 → 单元测试 → 构建打包 → 集成测试 → 部署预发 → 部署生产
```

### 3.2 各阶段命令

| 阶段 | 命令 | 失败处理 |
|:-----|:-----|:---------|
| 静态检查 | `npm run lint` / `flake8 .` | 阻断提交，修复后重试 |
| 单元测试 | `npm test` / `pytest` | 阻断部署，修复后重试 |
| 构建打包 | `npm run build` / `python setup.py build` | 阻断部署 |
| 集成测试 | `npm run test:e2e` | 阻断生产部署 |
| 部署预发 | `npm run deploy:staging` | 回滚预发 |
| 部署生产 | `npm run deploy:prod` | 自动回滚到上一版本 |

### 3.3 质量门禁

| 门禁项 | 阈值 | 不达标处理 |
|:-------|:-----|:-----------|
| 代码覆盖率 | ≥ 80% | 阻断合并 |
| 单元测试通过率 | 100% | 阻断合并 |
| ESLint/flake8 错误 | 0 | 阻断合并 |
| 安全漏洞扫描 | 0 高危 | 阻断部署 |
| 构建时长 | ≤ 10分钟 | 告警，优化构建 |

## 四、环境配置

### 4.1 环境分层

| 环境 | 用途 | 访问权限 |
|:-----|:-----|:---------|
| 本地开发 | 开发者本地调试 | 开发者个人 |
| 测试环境 | QA 测试验证 | 开发+测试团队 |
| 预发环境 | 上线前最终验证 | 开发+运维 |
| 生产环境 | 正式对外服务 | 运维（需审批） |

### 4.2 环境变量规范

1. 环境变量统一存放在 `.env.{环境}` 文件
2. `.env` 文件必须加入 `.gitignore`，禁止提交到代码仓库
3. 敏感信息（API Key、密码）必须通过环境变量注入，禁止硬编码
4. 环境变量命名：大写+下划线（如 `DATABASE_URL`、`API_KEY`）

### 4.3 跨环境路径规范

遵循 `CROSS-ENV-SYNC.md` 规范，使用占位符：
- `$ROOT`：项目根目录
- `$WORKSPACE`：工作区根目录
- 各环境自行替换为实际路径

## 五、构建与部署

### 5.1 构建产物规范

1. 构建产物统一输出到 `dist/` 或 `build/` 目录
2. 构建产物必须包含版本号和构建时间
3. 构建产物命名：`{项目名}-{版本号}-{环境}.{扩展名}`

### 5.2 部署流程

1. **预发部署**：合并到 main 分支后自动触发
2. **生产部署**：预发验证通过后，手动触发（需审批）
3. **回滚机制**：保留最近 5 个版本，支持一键回滚
4. **部署验证**：部署后自动运行健康检查，失败自动回滚

### 5.3 数据库迁移

1. 数据库迁移脚本必须纳入版本控制
2. 迁移脚本命名：`{时间戳}_{描述}.sql`
3. 迁移必须可回滚，同时编写 up 和 down 脚本
4. 生产环境迁移需 DBA 审批
