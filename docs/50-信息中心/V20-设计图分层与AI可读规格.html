一句话结论：「层层堆叠」不是视觉问题，是数据模型缺一层 —— 三幅本来应该分开编辑的画面（总监页底图 / 右侧对话弹窗 / 导图态）被压进同一个 elements[] 平铺数组，它们的从属与先后关系只编码在一个裸整数 z 里；而上层一旦存在，下层在物理上就点不到， 于是「不知道该从哪些部分、按什么顺序改」是必然结果，不是操作不熟练。

// design-schema.js:320-329（命中测试） export function hitTest(elements, x, y) { let best = null; for (const el of list) { if (x >= el.x && x <= el.x + el.w && ...) { if (!best || el.z >= best.z) best = el; // ↑ 同 z 时「后遍历者胜」 } } return best; }
判据是 >= 而不是 > ⇒ 同 z 谁在上取决于数组顺序，而不是任何显式约定。 今天能工作，只是因为 FRAME_SEEDS 的书写顺序恰好对。
A3

七条成因（逐条给证据）

按危害排序
前三条是同一个病的三个阶段：没有画面概念 → 层级只能塞进 z → 上层存在即下层不可达。
#成因证据（可自行复跑核验）
1 「画面」不是一个概念 20 条 seed 里 13 条属总监页底图、2 条属对话弹窗、5 条属导图态， 但数据模型里没有任何字段表达「这是哪幅画面」 （design-schema.js:290-302 的字段清单只有 id/kind/x/y/w/h/z/label/props/logic）。 区分它们的唯一凭据是 z 的区间约定：0-3 底图 / 6、8 浮层 / 10-11 模态。
2 层级只编码在裸整数 z 里 z: Math.round(num(p.z, 1))（:294）—— 一个无分组、无命名、无校验的整数。代码里没有一处声明「z≥10 表示模态」， 这个约定只活在作者的脑子里和设计稿的正文里。
3 没有第二条选择通道 左栏只有 LogicPanel（显示选中后的七元组， DesignStudio.js:1003-1016），没有元素列表。 唯一的选中途径是点画布 ⇒ 点不中的元素 = 完全不可编辑，不只是"难点"。
4 同 z 顺序不确定 el-32-can 与 el-40-edg 同 z=10 且 100% 交叠 （见 A2）；hitTest 用 >= ⇒ 层内顺序由数组下标决定，重排数组就会静默改变观感。
5 调序能力只有一个「置顶」 reorderElement（design.js:507-512）实现只有 where === "bottom" ? 0 : top + 1； UI 只渲染「置顶」一枚按钮（DesignStudio.js:330）。 「把 R5 挪到弹窗上面」「R1 下移一层」没有任何入口。
6 导出物是几何清单，不含结构 「导出 JSON」原样吐出 elements[]：只有 x/y/w/h/z + label + 七元组。AI 拿到的是一张20 行坐标表， 必须自己推断"这图里有三幅画面、哪几个属同一幅"⇒ 每次生成的图结构都可能不一样。这正是「三次改版改出来三版完全不一样的」的机制。
7 设计稿文档横向堆积 docs/50-信息中心/ 下已有 13 份设计稿 （V10 / V10.2 / V11 / V12 / V13 / V14 / V14.1 / V15 / V15.1 / V16 / V17 / V18 / V19）， 彼此无共享契约文件，迭代靠整文件复制。同一份 CSS 变量在三份稿里各抄一遍。
为什么这七条能解释"不知道该按什么顺序改"： 成因 1、2 让层级不可见（要读 z 数字才知道谁盖谁）； 成因 3 让下层不可达（43% 的元素点不到）； 成因 5 让顺序不可调（想换次序没入口）； 成因 6 让结构不可传递（AI 读不到，下次生成又变了）。 四条合起来 = 用户拿着鼠标，面对一堆互相覆盖的方块，任何动作都没有确定的下一步。
B

解法一：把「画面」变成一等公民

数据模型
B1

三层语义：画面 → 层 → 元素

规格
核心洞察：堆叠的三种情形在语义上完全不同，不该用同一套 z 数字表达 —— 属于不同画面（导图盖住总监页）、属于同画面的不同层（弹窗盖住内容）、 属于同层的相邻元素（R4 和 R5 并排，本来就不该相交）。 分开表达之后，「重叠」就不再是一个需要靠经验判断的东西，而是可以被校验的。
画面 screen
一幅可独立查看、独立编辑的完整屏。取值 director / chat / mindmap。
画面之间是重叠顺序关系（后一个盖前一个），不是平面摆位。
层 layer
画面内的分层。取值 base / content / deco。
同画面同层内的元素不应相交 —— 这是一条可校验的不变量。
元素 element
既有概念，不动：几何 + 标签 + 七元组逻辑。
18 类图元、20 个标准框架元素、版本快照机制全部保持现状。
新增字段（全部可缺省 ⇒ 旧数据零迁移）
字段取值缺省作用
screendirector | chat | mindmap由 z 推断归属哪幅画面。camera/坐标都不动 —— 只标身份。
layerbase | content | decobase画面内的层，决定修改次序。
hiddentrue | falsefalse隐而不删：不渲染，但仍在结构大纲里（可一键回来）。
lockedtrue | falsefalse锁而不动：不参与拖拽 / 缩放 / 删除，防误拖。
note字符串""一句话说明「这块干什么用」 —— 专给 AI 读，人可省略。
与冻结契约的关系（必须守住）： dsh.director.design 是本插件自有键，不在 R5 冻结清单内 ⇒ 可以自由加字段。 但 docId / title / elements / thread / revision 五个既有字段一律不动名、不动义； 元素数 20、图元数 18、reorderElement 的 top 语义 一个都不许变（否则基线闸门红）。新字段一律给缺省值 ⇒ 已落死基线读得懂新数据，反之亦然。
B2

分层后的不变量（可校验，不再是经验）

闸门口径
#不变量违反时意味着什么
N1每个元素的 screen 必须是已知画面数据损坏，或 AI 生成了未注册的画面名 ⇒ 拒收并报出是哪一条。
N2同画面 + 同层内，任意两元素不相交真的摆错了（本该并排却叠住）。跨画面相交是允许的，那是重叠语义。
N3locked 元素不参与拖拽 / 缩放 / 删除误拖。锁不是权限，是防手滑。
N4hidden 元素不渲染，但保留在大纲与导出里隐藏 ≠ 删除。删了就找不回来，藏起来随时能放。
N5z 只在画面内有意义，跨画面比较 z 无效画面之间的先后由 SCREEN_ORDER 决定，不由 z 决定。
N6聚焦某画面后，跨画面遮挡数必须为 0聚焦没生效 ⇒ 用户仍在「点不中」的状态里。
N2 与 N6 是这套设计真正兑现货的地方。 N6 直接消灭 A1 表里那 9 条不可选中；N2 把「摆歪了」从"看起来怪"变成"闸门报红"。

解法四：让 AI 直接读写的结构语言

行式 DSL
E1

为什么不用 JSON，改用「行式 DSL」

设计动机
用户的工作流是「我提想法 → AI 生成设计图 → 我改」。 那么这份图必须有两种读法：人读（在画布上看）与 AI 读（在文本里看）。 现在 AI 只能拿到 elements[] 的 JSON —— 它是一堆没有从属关系的坐标， AI 每次都要重新推断结构，于是每次生成的图都不一样。
维度JSON（现状）行式 DSL（本稿规格）
结构可见性要靠 x/y 反推谁盖谁缩进即从属，行序即层次
嵌套深度任意深，方言多固定两层（画面 → 元素），无嵌套括符
逐行 diff改一个字段 diff 出十几行一行一条 ⇒ diff 精确到"改了哪行的哪列"
LLM 出错率逗号 / 括号 / 引号易错列式定长，缺列即报错、可精确指出行号
版本对照要写专门的比较器两个版本逐行比即可，人能直接读
这不是自创路子。Thesys 的 OpenUI Lang 出于同样的动机做了同样的事： 官方给出的理由是「JSON 冗长、不可流式、模型约 3% 概率产出非法 JSON」， 改成形如 标识符 = 表达式 的一行一条语言后， 非法产出降到 0.3% 以下、token 省 45–67%（见 §F 对照表）。 差别只在于：OpenUI 用它描述 UI 组件树，我们用它描述设计图。
E2

语法规格（六条，够用且够严）

DSL v1
规则内容为什么这么定
R1一行一条语句，禁止 { } [ ] 等嵌套结构消除方言；解析器可逐行、可流式
R2首个非空行必须是 图 <docId> 「标题」唯一入口。参照 OpenUI Lang「首行必须赋给 root」，省掉"从哪儿开始读"的歧义
R3元素行 = 固定 5 列：层 类型 「标签」 x,y wxh，列间单空格定长列 ⇒ 可像 CSV 那样校验；缺列 / 多列都能精确报第几列
R4缩进 = 归属。画面下缩 2 空格，元素再缩 2 空格缩进即层级，人也能一眼看出从属
R5可选标记写在行尾：| hidden / | locked / | note=…追加不改列序 ⇒ 旧解析器遇到新标记不会错位
R6幂等：导出 → 导入 → 再导出，三次结果逐字节一致AI 改完再交回来不会产生"看着没改但 diff 满天飞"的噪声

工作流
你说想法 → AI 产出 DSL 全文 → 解析 + 校验（N1–N5 六条不变量） → 载入画布 → 你在结构大纲里逐层改 → 导出 DSL → AI 只读被改的那些行
为什么这个闭环能成立： 因为 DSL 是定长列 + 逐行独立的 —— AI 收到回稿后不需要重读全图， 只要看 diff 的那几行就知道你在哪一幅画面的哪一层动了什么。 这正是现在最缺的能力：现状下 AI 拿到的是整份 JSON，必须每次重新理解全局。
边界（不许越）： DSL 是交换格式，不是存储格式。 落库仍然走 dsh.director.design 的既有 JSON 结构 —— 加一层交换格式是为了让 AI 好读，不是为了动持久化契约。 导入失败时必须逐行报错并且一个字都不改图（不做"部分应用"）。

四份现成方案，各借一点

2026-09-14 核实
下面每条的机制描述均来自官方规范页或官方文档（URL 见 F2）， 不是转述二手的"据说"。借的是机制，不是代码 —— 本项目不引入任何外部依赖，只沿用其数据建模思路。
方案它解决的核心问题可借的点本项目落法
JSON Canvas
Obsidian · MIT		 无限画布的开放交换格式：顶层只有 nodes 与 edges 两个数组， 节点 4 类（text / file / link / group）； z 序 = 数组顺序（第一个在最下、最后在最上）。 ① group 作为显式容器节点（而不是靠坐标包含关系反推父子）； ② 用「顺序即层次」取代"显式 z 数字"； ③ 只有两个顶层数组这种极简骨架。 「画面」= 一种更粗的 group，但不是可选的装饰节点，而是必填归属字段 （因为我们不只画图，还要编辑，必须能寻址）。
Excalidraw
开源白板 · 官方 scene schema		 元素级 schema：groupIds（最深→最浅的组路径）、 frameId（frame 成员身份，只标身份、不改子元素坐标）、 index（分数索引排 z 序）、 locked、isDeleted 软删。 ① 「成员身份」与「坐标」正交 —— 认领归属不该顺手挪位置； ② 分数索引替代裸整数：在两元素之间插入不用全表重排； ③ locked / 软删的语义。 screen 字段照 ① 设计 —— 只标身份，x/y 一个不动； 层内顺序改用时序数组下标（比分数索引更简单，且我们的元素数上限仅 20 量级）。
tldraw
开源 SDK · 官方文档		 每个 shape 有 parentId（指向 page 或父 shape）⇒ 显式父子树； Pages：一个文档内有多个独立子文档，每页各自持有相机与选中态， 切页保留离开时的状态；默认上限 40 页。 ① Pages 模型：多幅画面 = 多页，而不是同一张画布上挪 z； ② getSortedChildIdsForParent 这类"按父取子、已排序"的取数方式； ③ isLocked / isHidden 成对出现。 这是与本稿最贴近的一份。我们把 Pages 改名为「画面」， 但不引入相机分页（本项目画布只有一幅固定尺寸 1180×644，无缩放平移需求）。
OpenUI Lang
Thesys · MIT		 面向 LLM 输出的行式 DSL：一行一条 标识符 = 表达式，首行必须是 root， 参数按 schema 键序位置化；为流式渲染允许前向引用。 官方动机：JSON 冗长、不可流式、模型约 3% 概率产出非法 JSON； 改成类代码语法后非法率降至 0.3% 以下、token 省 45–67%。 ① 面向模型输出设计的语法（不是为人手写设计的）； ② 固定入口标识符，消除"从哪儿开始读"的歧义； ③ 由组件库自动生成系统提示 —— 组件定义即提示词来源。 DSL 规格（§E2）照 ① ② 设计； 第 ③ 条我们天然具备条件：ELEMENT_KINDS 已经是 18 类带 logic 骨架的组件库，可直接生成"允许用哪些类型"的说明， 从而约束 AI 不臆造不存在的图元。

不采用的方案，以及为什么

反面对照
候选思路不采用的理由
只加"层级调序"按钮，不动模型 治标。加「上移一层 / 下移一层」后，用户仍然看不到有几个画面 —— 层级不可见这个根因一个都没碰，只是让 z 数字操作更方便。而且 9 个不可选中依旧不可选中。
靠"点击时遍历穿透"选中下层（连点几次循环到下面一层） 把不可见性换成不可预测性。点下去命中谁取决于之前的点击历史， 同一位置点两次结果不同 —— 比点不中更难排查，且无法写确定性断言。
把默认 z 间距拉开（0/10/20/…） 只解决"同 z 碰撞"，不解决"画面没有名字"。 而且间距一旦写死，下次加画面又要重排数字 —— 是把约定从脑子搬进常量，没有消除约定。
引入完整开源画布内核（如直接嵌 tldraw / Excalidraw） 与本项目纪律冲突：插件产物是单文件 bundle、不装 node_modules、 react 是平台冻结模块（ADR-001）。 引入画布内核会改变构建形态与全部既有闸门基线。借机制、不借依赖。
把设计图整体换成纯文本编辑 丢掉了这个功能存在的理由 —— design-schema.js 的原文注释写得很清楚：痛点是沟通， 要「指着同一个 id 说话」。纯文本没有空间感，改不了"这块往右挪一点"。
共同原则：凡是"让用户更容易容忍不可见"的方案都不采用， 只采用"让结构本身可见"的方案。
