C3

消息投递时序 —— 两个方向，两套独立 store

核心不变量：总监域数据不寄生在对话会话里
为什么必须双向分开画：总监域（dsh.director.store.* / DB dsh-director-db）与宿主会话流是两套物理独立的存储。 「总监 → 对话」是显式投递（要选目标、要确认）；「对话 → 总监」是自动回结（轮次一结束就发生，不用人点）。 两者不是同一条通道的正反方向 —— 若按同一通道实现，删对话会连着删总监记录。

方向一 · 总监 → 对话（显式投递 · 要选目标）

① 总监页 R4/R5选中分支节点 → 点「投递给该对话」人在操作
② 总监 store写 outbox 一条：{目标分支, 指令原文, 时间戳}落库先于发送
③ 对话弹窗读 outbox → 渲染为带「目标徽章」的气泡（来源可辨）只读消费
④ 你确认非破坏性且目标唯一 ⇒ 免确认；破坏性或目标多义 ⇒ 出确认卡闸门在此
⑤ 宿主会话调宿主发送接口 → 该分支进入 S2 执行中唯一写入口
⑥ 回结轮次结束 → 触发方向二第 1 步闭环起点

方向二 · 对话 → 总监（自动回结 · 不用人点）

① 宿主事件轮次结束 / 中止 / 报错 —— 三类都算"结束"事件源
② 摘取生成 resultDigest：改了哪些文件 + 校验结果 + 未解问题 + 下一步只摘不搬
③ 总监 store写 inbox 一条 → 总监页「回结卡」置「待审」并亮未读点落库
④ 六维审核质量 / 一致 / 风险 / 交付 / 范围 / 留痕 → directorDecisions[]人机共审
⑤ 三选一继续推进 / 再开分支 / 收口归档决策
⑥ 转派若选"继续"或"再开分支" ⇒ 回到方向一第 1 步闭环成形
对比项方向一（总监 → 对话）方向二（对话 → 总监）为什么不能合一
触发者人点（显式）宿主事件（自动）自动流不该带确认卡，否则每轮都弹一次
数据载体outboxinbox合卡则「已发未读」和「已收未审」分不开
是否需确认条件性（见 C4）否审核本身就是事后闸门，前置闸门会双重打断
写目标会话是（唯一写入口）否总监只读对话流 ⇒ 删对话不伤总监记录
失败退路投递失败 → 留在 outbox 并标红，可重发摘取失败 → 仍写一条"空回结"占位，不静默丢两头都不许出现"我不知道它结束了"

免确认 / 必确认 的判据（唯一裁决处）

情形是否出确认卡理由
目标唯一 + 只读动作免确认高频操作，每次弹卡会把人磨死
目标唯一 + 写动作（投递指令）免确认目标已在标题栏可见 ⇒ 已构成显式意图
目标多义（路由命中多个）必确认猜错 = 指令打到错分支，代价高且难察觉
破坏性动作（删分支 / 归档 / 中止）必确认不可逆；且删除是"从活跃树摘除"，需二次确认
跨域动作（合并回父）必确认 + 标"建议项"属非你提出的能力，必须显式点两次

C5

总监治理闭环 —— 五步一转，加上一条纠偏回路

总监不是聊天窗，是调度器
1 意图理解读输入 + 读全局状态 → 2 匹配分支对血缘树做匹配 → 3 拆分任务跨分支则拆子任务 → 4 决策直调 / 转派 / 新建 → 5 执行+回结落库并等待 ↻
第 5 步的回结触发第 1 步重新读取状态 ⇒ 闭环。这就是"总监对对话的控制非常频繁"在机制上的落点：每次结束都自动回到总监，不需要人去催。

五步的输入 / 规则 / 输出 / 退路

步输入判定规则失败退路
1 意图理解输入原文 + 分支树快照 + 各分支末次回结提取目标名词，判"是问事还是派活"判不出 ⇒ 直说"没听懂，请补充"，不瞎猜
2 匹配分支目标名词 vs 分支标题 / 派单原文命中 1 / 多 / 0 三档（对应 C4 三支）多命中必确认；零命中建议新建
3 拆分任务任务是否跨多个分支跨则拆子任务并各带 lock zone拆不开就整单给一个分支，并标"未拆分"
4 决策匹配结果 + 任务形态直调本域 / 转派既有分支 / 新建分支破坏性动作必过确认卡
5 执行+回结决策 + 目标分支投递（方向一）⇒ 等回结（方向二）投递失败留 outbox 标红可重发

纠偏回路（六维审核判不定时走这条）

S4 六维判不定证据不足 / 结论矛盾 → 打回重做附纠偏指令，回 S2 或 升级给人总监停止自决，等你裁
关键的克制：总监在证据不足时不许自决（不许"看起来差不多就放行"）。 这条直接来自前几轮的实际教训 —— 画面自相矛盾却一路放行到交付。判不定时必须显式打回或升级，两条路都要留痕。
