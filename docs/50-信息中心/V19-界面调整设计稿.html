A2

「刚点开就一闪而逝」根因

bug 根治
根因（已定位到行）：installHostPanelTrim() 给 MutationObserver 的回调套了 setTimeout(…, 300) 做"代价控制"。 ⇒ 首次安装时是立即裁剪的（不闪）；但宿主切页签 / 重挂载时节点被重建， 新节点先以可见状态渲染，300ms 后才被我们隐藏 ⇒ 你看到的闪一下就是这 300ms。
点「对话」页签→ 宿主重挂载该行（可见）→ 等 300ms→ 裁剪生效（消失） ＝视觉"一闪而逝"
修法：MutationObserver 回调里同步处理新增节点（微任务阶段，早于浏览器绘制帧）， 去掉 setTimeout。为守住"代价控制"，只扫 mutation.addedNodes 而不做全文扫描，并保留 markersAlive() 快速返回。 验收判据：连续切页签 3 次，被裁元素的"可见帧数"必须为 0（用 rAF 采样计数，而不是目测）。

按消息判定归属哪个对话

需求 6 ＝ V18 板块 F + 补投递
E1

根因：判定结果只写了记录，没接投递

bug 根治
判定能力本身是好的：logic/routing.js 的 scoreNodes() 会给每个节点打分（名称命中 ×3 / 会话记录命中 ×1.2 / 近 3 日活跃 +0.8 / 会话级 +0.3），suggestDestination() 据此给出三条去向 （转给该对话的总监 / 直接调用对应对话 / 新建对话）。
断在这两处：
DirectorPage.js:586 —— flowStore.move(flowId, DIM.CHAT, …, { status:"routed", target: flowSession }) ⇒ 目标写死当前会话；
DirectorDialog.js:572 —— sendToChat(subtasks.join("\n"), { autoSend }) ⇒ 没传任何目标会话（sendToChat 本身也只操作当前会话）。
⇒ 判定的 candidates[0].nodeId 只被 saveDecision 存进了决策记录，投递路径完全不知道它。
用户消息→ route() 判定 → 候选 nodeId→ saveDecision 只存记录 ⤳ 投递用 flowSession（当前会话）
修法（三处贯通）：
① 传下去：confirmRoute(dest) 取出 routeResult.candidates[0].nodeId 作为 targetNodeId；
② 走对通道：bridge/chat-bridge.js 已有 sendToHost(sessionId, text)（带会话参数）—— 目标非当前会话时改走它， 而不是继续用只认当前会话的 sendToChat；
③ 留痕：flowStore.move 的 target 写真实目标 id， 无候选时才回落到当前会话（且 UI 上明示"未命中，发当前会话"，不静默）。
验收判据（必须能反证）：造两条消息 —— 一条含目标对话名（应路由到它）、 一条含无关词（应回落当前会话）。两条的落点必须不同； 若两条都进当前会话 ⇒ 判据转红（证明接线没生效）。
