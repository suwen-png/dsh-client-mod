## 〇、核心理念：思维导图是第一公民

本方案的核心设计哲学是 \*\*"思维导图是第一公民"（MindMap First）\*\*：



* 思维导图不是对话的附属可视化，而是**对话的组织结构本身**

* 每一次对话都发生在思维导图的某个节点上

* 创建分支 = 在思维导图中添加节点

* 切换对话 = 在思维导图中导航节点

* 上下文管理 = 节点携带的摘要和压缩记录

* 用户的心智模型从 "线性对话列表" 转变为 "树状思维地图"

**对比现有模式**：



| 维度   | 现有模式（线性）        | 新模式（思维导图驱动）           |
| ---- | --------------- | --------------------- |
| 对话组织 | 线性列表，一个对话 = 一条线 | 树状结构，一个对话 = 一棵树       |
| 分支管理 | 分支列表（线性），切换靠列表  | 思维导图节点，切换靠点击节点        |
| 上下文  | 整个对话共享一个上下文     | 每个节点独立上下文，切换时自动加载     |
| 模型切换 | 在同一对话中切换，上下文累积  | 切换模型 = 创建新节点 + 压缩旧上下文 |
| 全局视图 | 只能看到当前对话        | 一眼看到所有分支和进度           |
| 导航   | 列表滚动查找          | 思维导图中直接点击             |

## 一、用户核心目标（第一性原理提炼）

用户要的不是 "一个思维导图组件"，而是：

> **以思维导图为核心的多分支对话管理系统**
> —— 让对话从线性变成树状，每个节点是一个对话分支，每个分支可以绑定不同模型，切换模型时自动压缩上下文，思维导图既是可视化也是导航入口和操作中心。

### 用户提出的 5 个具体问题



| # | 问题                   | 本质需求                            |
| - | -------------------- | ------------------------------- |
| 1 | 切换不同模型时自动压缩上下文       | 上下文管理：模型切换 = 新分支起点，旧对话压缩为摘要     |
| 2 | 调用新的分支，组成到思维导图中      | 数据打通：创建分支→自动添加思维导图节点            |
| 3 | 思维导图点击哪里进入对应的分支对话    | 导航交互：点击节点→切换到对应分支对话视图           |
| 4 | 将现有对话 + 分支的结构整理成思维导图 | 自动生成：从线性对话历史中识别分支点，生成树          |
| 5 | 如何更好地体现思维导图的作用       | 价值定位：思维导图不只是可视化，还是操作中心 + 上下文管理器 |

## 三、统一方案设计（汇总 + 补全）

### 3.1 核心概念定义



| 概念                               | 定义                                               | 数据结构                         |
| -------------------------------- | ------------------------------------------------ | ---------------------------- |
| **主线（Root）**                     | 对话的起点，用户与总监的主对话，承载**共享项目了解**                     | MindNode (parentId=null)     |
| **分支（Branch）**                   | 从主线或其他分支分叉出的**专业化工作单元**，有明确职责分工                  | MindNode (parentId = 父节点 id) |
| **节点（Node）**                     | 思维导图中的一个节点，对应一个分支                                | MindNode                     |
| **处理类型（Branch Type）**            | 分支的职责分工：文档 / 开发 / 测试 / 调研 / 通用等，决定分支 "做什么"       | branchType 字段                |
| **智能体绑定（Agent Binding）**         | 分支绑定的智能体角色，决定分支 "谁来做"（不只是模型，还有系统提示词 / 技能 / 执行逻辑） | agentId 字段                   |
| **模型绑定（Model Binding）**          | 分支使用的模型，决定分支 "用什么能力做"                            | model 字段                     |
| **分支依赖（Dependency）**             | 分支之间的输入输出依赖：A 分支的产出是 B 分支的输入                     | dependsOn \[] 字段             |
| **共享文件夹（Shared Folder）**         | 分支间数据流转的介质：文档分支写入文件夹，开发分支读取文件夹                   | inputFolder / outputFolder   |
| **产出物（Deliverables）**            | 分支完成后产出的文件 / 文档 / 代码列表                           | deliverables \[] 字段          |
| **上下文摘要（Context Summary）**       | 切换分支 / 创建分支时，对之前对话的压缩摘要，由总监传递给新分支                | summary 字段                   |
| **分支对话（Branch Conversation）**    | 一个分支对应的完整对话历史                                    | Message \[]，按 branchId 隔离    |
| **总监调度（Director Orchestration）** | 总监全局监控所有分支，负责工作安排、分支切换、上下文传递                     | 总监对话 + 调度事件                  |

### 3.1.1 分支的三维定义（核心）

每个分支由三个维度定义，三者共同决定分支的能力和职责：



| 维度        | 说明                                    | 示例                              | 对应字段       |
| --------- | ------------------------------------- | ------------------------------- | ---------- |
| **处理类型**  | 分支 "做什么"—— 职责分工                       | 文档编写 / 代码开发 / 测试验证 / 技术调研       | branchType |
| **智能体角色** | 分支 "谁来做"—— 绑定的智能体（含系统提示词 + 技能 + 执行逻辑） | 文档专家 / 代码工程师 / 测试工程师            | agentId    |
| **模型**    | 分支 "用什么做"—— 使用的 AI 模型                 | DeepSeek-V4 / Qwen2:7b / Llama3 | model      |

> **关键理解**
>
> ：用户说的 "不同分支不只是不同模型，还有不同的处理"，就是指这三个维度的组合。
> 文档分支 = 处理类型 (doc) + 智能体 (文档专家) + 模型 (通用模型)
> 开发分支 = 处理类型 (code) + 智能体 (代码工程师) + 模型 (代码强模型)
> 两个分支可以用同一个模型，但处理类型和智能体不同，职责完全不同。

```
\### 3.3 五大核心流程设计

\#### 流程 1：切换模型时自动压缩上下文（用户问题 1）

\*\*触发条件\*\*：用户在对话中切换模型（从模型 A 切换到模型 B）

\*\*核心策略：切换模型 = 创建新分支 + 压缩旧上下文\*\*

\> 设计决策：不在同一分支内切换模型。每次切换模型都创建一个新的思维导图节点（分支），旧分支的对话自动压缩为摘要，作为新分支的上下文起点。

\> 理由：

\> 不同模型有不同的 "思维风格"，混在同一对话中会导致上下文污染

\> 压缩旧对话为摘要，可以让新模型从干净的上下文开始，充分利用上下文窗口

\> 在思维导图中，每个模型对应一个节点颜色，用户可以一眼看到 "哪个部分用了哪个模型"

\> 可以随时回溯到旧分支，查看原始对话（上下文溯源）
```

```
\*\*设计要点\*\*：

\* \*\*压缩阈值\*\*：消息数≤5 条且总字数≤2000 字时，不压缩，直接创建新分支（短对话不需要压缩）

\* \*\*压缩引擎降级链\*\*：AI 压缩 → 规则压缩 → 手动输入（都失败时让用户手动写摘要）

\* \*\*摘要可编辑\*\*：新分支第一条系统消息中的摘要卡片，用户可点击编辑，修改后更新节点 summary

\* \*\*上下文溯源\*\*：新节点的 compressedFrom 字段记录源节点；点击 "查看原始对话" 弹出源分支的完整对话（只读滚动）

\* \*\*模型颜色编码\*\*：每个模型对应一个节点颜色（如 DeepSeek = 蓝、Qwen = 绿、Llama = 橙），思维导图中一眼看出模型分布

\* \*\*分支命名\*\*：默认 "{模型名} 分支"，用户可重命名（如 "方案探索"、"代码实现"）
```

```
\#### 流程 4：将现有对话 + 分支结构整理成思维导图（用户问题 4）

\*\*触发条件\*\*：

\* 用户第一次打开思维导图视图（自动生成）

\* 用户点击 "刷新思维导图" 按钮

\* 从旧版本升级（没有思维导图数据时）

\* 导入外部对话历史后

\*\*分支点识别规则（核心算法）\*\*：

从线性对话历史中识别分支创建事件，按优先级匹配：

\| 优先级 | 识别规则                        | 说明                       |

\| --- | --------------------------- | ------------------------ |

\| 1   | 系统消息匹配 \`已创建【{name}】分支\`      | V10 智能体调用流程的标准系统消息       |

\| 2   | 系统消息匹配 \`已切换到模型【{model}】\`    | 模型切换创建的分支（流程 1）          |

\| 3   | 消息元数据中包含 \`branchCreated\` 事件 | 程序化创建的分支（有事件标记）          |

\| 4   | branches.json 中的分支记录        | 从分支配置中反向查找创建时间点          |

\| 5   | 对话历史中明显的话题转换（AI 辅助）         | 低优先级，仅在以上都没有时用 AI 识别话题边界 |

\*\*完整流程\*\*：
```

用户打开思维导图视图 / 点击 "刷新"

&#x20;   │

&#x20;   ▼

① 收集数据

&#x20;  ├─ 加载所有分支（branches.json）

&#x20;  ├─ 加载所有对话历史（按 branchId 隔离的消息）

&#x20;  └─ 加载主线对话（branchId=null 或 root）

&#x20;   │

&#x20;   ▼

② 识别主线中的分支点

&#x20;  ├─ 遍历主线对话历史，按时间顺序

&#x20;  ├─ 对每条系统消息，按分支点识别规则匹配（上表 5 级优先级）

&#x20;  ├─ 匹配成功 → 记录分支点 {timestamp, branchName, branchId, parentBranchId}

&#x20;  │   ├─ parentBranchId：分支创建时所在的分支（默认 root 主线）

&#x20;  │   ├─ 如果分支创建事件发生在某个分支对话中 → parentBranchId = 该分支 id

&#x20;  │   └─ branchId：从系统消息或 branches.json 中匹配

&#x20;  └─ 构建分支点时间线

&#x20;   │

&#x20;   ▼

③ 构建树结构

&#x20;  ├─ 创建根节点：{id: "root", parentId: null, label: "主线", icon: "🎯", status: 'idle', model: 默认模型，msgCount: 主线消息数}

&#x20;  ├─ 按时间顺序处理每个分支点：

&#x20;  │   ├─ 创建节点：{id: branchId, parentId: parentBranchId, label: branchName, ...}

&#x20;  │   ├─ 从 branches.json 中补充：model、icon、branchType、contextFiles

&#x20;  │   ├─ 从对话历史中统计：msgCount、lastActivityAt

&#x20;  │   ├─ 从 compressions.json 中补充：summary、compressedFrom

&#x20;  │   └─ 如果分支已合并 → merged=true

&#x20;  ├─ 处理多级分叉：

&#x20;  │   ├─ 如果分支 A 的对话中又创建了分支 B → B.parentId = A.id

&#x20;  │   └─ 递归处理，支持无限级

&#x20;  └─ 处理孤立分支（找不到父节点）：

&#x20;      └─ 挂到 root 下，标记为 "孤儿分支"，UI 显示警告图标

&#x20;   │

&#x20;   ▼

④ 生成摘要（可选，增量）

&#x20;  ├─ 对每个 msgCount>5 且 summary 为空的节点

&#x20;  │   ├─ 调用压缩引擎生成摘要（同流程 1 的压缩逻辑）

&#x20;  │   ├─ Ollama 不可用时跳过（summary 留空，UI 显示 "点击生成摘要"）

&#x20;  │   └─ 生成后更新节点 summary

&#x20;  └─ 已有 summary 的节点不重复生成

&#x20;   │

&#x20;   ▼

⑤ 渲染思维导图

&#x20;  ├─ 将节点列表传给 BranchMindMap 组件

&#x20;  ├─ 自动布局（后序遍历算法）

&#x20;  ├─ 选中当前分支节点

&#x20;  └─ 适应屏幕

&#x20;   │

&#x20;   ▼

⑥ 完成

&#x20;  └─ 思维导图展示完整的对话 + 分支树结构



```
\*\*设计要点\*\*：

\* \*\*识别准确率优先\*\*：优先用明确的系统消息和事件标记识别，AI 话题识别仅作为最后兜底（避免误判）

\* \*\*增量更新\*\*：首次生成后保存到 mindmap.json，后续创建分支时只添加新节点，不需要全量重新生成

\* \*\*多级支持\*\*：通过 parentBranchId 递归构建，支持无限级分叉

\* \*\*合并标记\*\*：已合并的分支在思维导图中变灰 + 虚线连线，视觉上区分 "活跃分支" 和 "已合并分支"

\* \*\*孤儿分支处理\*\*：找不到父节点的分支挂到 root 下，标记警告，用户可手动调整父节点（拖拽）

\* \*\*大数量优化\*\*：节点数 > 20 时，默认收起二级以下子树，用户可展开；提供搜索功能

\#### 流程6：总监全局调度与分支工作安排（核心新增）

\*\*触发条件\*\*：

\- 用户在主线（总监对话）中提出一个需要多分支协作的需求

\- 总监判断需要创建专业化分支来分工完成

\- 分支执行完成后，总监审核并安排下一步

\*\*总监的角色定位\*\*：

\- \*\*全局监控者\*\*：监控所有分支的状态、进度、产出

\- \*\*工作安排者\*\*：根据需求拆解任务，分配给合适的分支（处理类型+智能体+模型）

\- \*\*上下文传递者\*\*：切换分支时，给新分支传递必要的上下文（项目了解+前置分支产出摘要）

\- \*\*质量审核者\*\*：分支完成后，审核产出质量，决定通过/退回/安排下一步

\- \*\*分支切换者\*\*：在分支之间切换，协调工作顺序和依赖关系

\*\*完整流程\*\*：
```

用户在主线提出需求："帮我做一个 XX 功能，先写设计文档，再根据文档开发"

│

▼

① 总监需求理解与拆解

├─ 总监理解用户需求

├─ 拆解为子任务：

│   ├─ 任务 A：写设计文档 → 处理类型 (doc) + 智能体 (文档专家) + 模型 (通用)

│   └─ 任务 B：根据文档开发 → 处理类型 (code) + 智能体 (代码工程师) + 模型 (代码强)

├─ 确定依赖关系：B 依赖 A（B 需要 A 的文档作为输入）

├─ 确定共享介质：A 的输出文件夹 = B 的输入文件夹（如 docs/design/）

└─ 生成执行方案，展示给用户确认

│

▼

② 用户确认方案

├─ 用户可修改：分支名称 / 智能体 / 模型 / 依赖关系 / 文件夹路径

└─ 确认后开始执行

│

▼

③ 总监创建第一个分支（文档分支 A）

├─ 创建 MindNode：

│   { id: branch-a, parentId: root, label: "设计文档", icon: "📄",

│     branchType: "doc", agentId: "doc-expert", model: "deepseek-v4",

│     outputFolder: "docs/design/", dependsOn: \[],

│     taskDescription: "编写 XX 功能的设计文档，包含需求分析 / 架构设计 / 接口定义",

│     summary: "项目了解：{主线对话压缩摘要}" }

├─ 写入 mindmap.json → 思维导图自动添加节点

├─ 向分支 A 发送总监调度消息（role=director, action=assign\_task）：

│   "📋 总监安排任务：编写 XX 功能的设计文档

│

│    项目背景：{主线对话摘要}

│   ├─ 通过 → 继续下一步（创建分支 B）

```
\*\*设计要点\*\*：

\- \*\*总监是调度者，不是执行者\*\*：总监不直接写文档/写代码，而是理解需求、拆解任务、分配给专业分支、审核产出

\- \*\*上下文由总监传递\*\*：每个分支创建时，总监给它传递必要的上下文（项目了解+前置产出摘要），分支不需要知道全局

\- \*\*分支间通过文件夹流转数据\*\*：A的outputFolder = B的inputFolder，不需要总监手动传递文件

\- \*\*依赖关系明确\*\*：dependsOn字段记录分支依赖，总监在依赖未完成时不会创建下游分支

\- \*\*审核是必经环节\*\*：每个分支完成后必须经过总监审核，通过才能进入下一步

\#### 流程7：分支间数据流转与上下文传递（核心新增）

\*\*触发条件\*\*：

\- 总监创建新分支时，需要给新分支传递上下文

\- 分支执行完成后，产出物需要供其他分支使用

\- 用户在分支之间切换时，需要加载对应分支的上下文

\*\*数据流转的三种介质\*\*：

\| 介质 | 说明 | 适用场景 |

\|------|------|---------|

\| \*\*共享文件夹\*\* | A分支写入outputFolder，B分支从inputFolder读取 | 文档→开发、设计→实现等文件级流转 |

\| \*\*上下文摘要\*\* | 总监压缩前置分支的对话和产出，作为摘要传递给新分支 | 项目了解、任务背景、前置结论 |

\| \*\*产出物清单\*\* | deliverables字段记录分支产出的文件列表和状态 | 总监审核、下游分支了解输入 |

\*\*完整流程\*\*：
```

分支 A 完成 → 总监创建分支 B（依赖 A）

│

▼

① 收集分支 A 的产出

├─ 读取分支 A 的 deliverables 列表

├─ 读取分支 A 的 outputFolder 中的文件

├─ 统计分支 A 的对话消息（msgCount）

└─ 生成分支 A 的产出摘要

▼

├─ 压缩内容：

│   ├─ 主线对话摘要（项目了解，所有分支共享）

│   ├─ 分支 A 的任务描述（A 做了什么）

│   ├─ 分支 A 的产出摘要（A 产出了什么，关键结论）

│   └─ 分支 A 的产出物清单（文件列表 + 路径）

├─ 调用压缩引擎（同流程 1 的压缩逻辑）

│   ├─ AI 压缩：Ollama 可用时，让模型总结前置产出

│   └─ 规则压缩：取任务描述 + 产出物列表 + 最后几条关键消息

└─ 生成 contextSummary

│

▼

③ 传递上下文给分支 B

├─ 将 contextSummary 写入分支 B 的 summary 字段

├─ 设置分支 B 的 inputFolder = 分支 A 的 outputFolder

├─ 设置分支 B 的 dependsOn = \[branch-a]

├─ 向分支 B 发送总监调度消息（role=director, action=pass\_context）：

│   "📦 总监传递上下文：

│

│    【项目背景】

│    {主线对话摘要}

│

│    【前置产出：设计文档分支】

│    任务：{分支 A 任务描述}

│    产出摘要：{分支 A 产出摘要}

│    产出文件：

│      - docs/design/01 - 需求分析.md

│      - docs/design/02 - 架构设计.md

│      - docs/design/03 - 接口定义.md

│

│    【你的任务】

│    {分支 B 任务描述}

│

│    💡 你可以从 docs/design/ 读取设计文档作为开发依据 "

└─ 分支 B 的对话历史中，第一条消息就是这条总监调度消息

│

▼

④ 分支 B 加载上下文

├─ 分支 B 启动时，读取 summary 字段作为初始上下文

├─ 从 inputFolder 读取文件（如果需要）

├─ 智能体的系统提示词 + 总监传递的上下文 = 完整工作上下文

└─ 分支 B 开始执行任务

│

▼

⑤ 用户切换分支时的上下文加载

├─ 用户在思维导图中点击分支 B → 切换到分支 B 对话

├─ 加载分支 B 的对话历史（按 branchId 隔离）

├─ 显示分支 B 的状态栏：处理类型 + 智能体 + 模型 + 依赖关系 + 输入 / 输出文件夹

├─ 如果分支 B 有 summary，显示摘要卡片（可展开）

├─ 如果分支 B 依赖其他分支，显示 "依赖：分支 A（已完成）"，点击可跳转

└─ 用户可在分支 B 中继续对话，或查看产出物



```
\*\*设计要点\*\*：

\- \*\*上下文最小化\*\*：每个分支只接收它需要的上下文（项目背景+前置产出摘要），不需要知道全局所有对话

\- \*\*总监是上下文桥梁\*\*：分支之间不直接通信，所有上下文都通过总监传递和压缩

\- \*\*文件夹是数据载体\*\*：大文件（文档/代码）通过文件夹流转，摘要只传递关键信息

\- \*\*上下文可追溯\*\*：每个分支的summary记录了上下文来源，用户可以点击查看原始对话和产出

\- \*\*切换分支即切换上下文\*\*：用户在思维导图中点击节点，自动加载该分支的完整上下文（对话+产出+依赖）

\### 3.4 多分支流水线协作示例（完整场景）

\*\*场景\*\*：用户要开发一个"用户登录功能"，需要经过需求分析→设计文档→前端开发→后端开发→测试验证

\*\*思维导图结构\*\*：
```

┌─ 需求分析分支 (doc) ─┐

│   产出: docs/requirements/

│                       ▼

主线 (root) ─────────┤                 设计文档分支 (doc)

项目了解            │                 产出: docs/design/

│                       │

│              ┌────────┴────────┐

│              ▼                 ▼

│         前端分支 (code)     后端分支 (code)

│         产出: src/frontend/ 产出: src/backend/

│              │                 │

│              └────────┬────────┘

│                       ▼

│                 测试分支 (test)

│                 产出: tests/

└───────────────────────┘



```
\*\*各分支的三维定义\*\*：

\| 分支 | 处理类型 | 智能体 | 模型 | 输入文件夹 | 输出文件夹 | 依赖 |

\|------|---------|--------|------|-----------|-----------|------|

\| 需求分析 | doc | 产品经理 | DeepSeek-V4 | - | docs/requirements/ | - |

\| 设计文档 | doc | 架构师 | DeepSeek-V4 | docs/requirements/ | docs/design/ | 需求分析 |

\| 前端开发 | code | 前端工程师 | DeepSeek-Coder | docs/design/ | src/frontend/ | 设计文档 |

\| 后端开发 | code | 后端工程师 | DeepSeek-Coder | docs/design/ | src/backend/ | 设计文档 |

\| 测试验证 | test | 测试工程师 | DeepSeek-V4 | src/frontend/+src/backend/ | tests/ | 前端+后端 |

\*\*总监调度时序\*\*：

1\. 用户提出需求 → 总监拆解为5个子任务，生成执行方案

2\. 用户确认 → 总监创建"需求分析"分支，传递项目背景

3\. 需求分析完成 → 总监审核 → 通过 → 创建"设计文档"分支，传递需求摘要+文档

4\. 设计文档完成 → 总监审核 → 通过 → 并行创建"前端"和"后端"分支（都依赖设计文档）

5\. 前端+后端都完成 → 总监审核 → 通过 → 创建"测试"分支（依赖前端+后端）

6\. 测试完成 → 总监审核 → 通过 → 汇总汇报，全部标记done

\*\*用户体验\*\*：

\- 用户在思维导图中一眼看到整个开发流水线的进度

\- 点击任意节点，进入该分支的对话，查看该分支的工作内容和产出

\- 总监在主线中汇报全局进度，用户不需要逐个切换分支

\- 分支之间的依赖关系用连线表示，未完成的依赖会阻塞下游分支
```

```
\## 六、风险与应对

\| 风险              | 影响                                     | 概率 | 应对策略                                         |

\| --------------- | -------------------------------------- | -- | -------------------------------------------- |

\| 上下文压缩质量不稳定      | 摘要丢失关键信息，影响后续对话                        | 中  | 摘要可编辑 + 上下文溯源（可查看原始对话）+ 压缩阈值控制（短对话不压缩）       |

\| Ollama 不可用时压缩失败 | 切换模型时无法生成摘要                            | 高  | 规则压缩降级（取最后 3 条用户消息 + 最后 1 条助手结论）+ 标记为 "规则压缩" |

\| 思维导图节点过多时布局混乱   | 大项目（>20 分支）时节点重叠                       | 中  | 虚拟滚动 + 按需展开子树 + 水平 / 垂直布局切换 + 拖拽调整           |

\| 分支对话数据量大时性能问题   | 切换分支时加载慢                               | 中  | 消息分页加载 + 虚拟滚动 + 按 branchId 隔离存储（只加载当前分支）     |

\| 与现有分支管理逻辑冲突     | 现有 branches.json 和新 mindmap.json 数据不一致 | 中  | 数据合并（mindmap.nodes 包含分支所有信息）+ 迁移脚本 + 原子操作    |

\## 七、待审核 / 待确认的问题

\> 注：问题 2（分屏模式）和问题 3（模型切换策略）已在本文档中明确设计决策，标记为 "已决策"，用户可推翻。

1\. \*\*压缩阈值\*\*：消息数 > 5 条或 > 2000 字时触发压缩，这个阈值是否合理？（可在设置中调整）

2\. \~\~分屏模式\~\~\~\~：是否需要 "分屏模式"？\~\~ \*\*已决策\*\*：默认分屏模式（左思维导图 35%+ 右对话 65%），替代现有二段切换。用户可推翻。

3\. \~\~模型切换策略\~\~\~\~：切换模型时创建新分支 + 压缩旧对话？\~\~ \*\*已决策\*\*：切换模型 = 创建新分支 + 压缩旧上下文。理由见流程 1。用户可推翻。

\## 九、数据迁移方案

\### 9.1 现有数据结构

\| 数据   | 存储位置                                    | 格式                            |

\| ---- | --------------------------------------- | ----------------------------- |

\| 分支配置 | branches.json                           | 线性分支列表（无树结构）                  |

\| 对话历史 | localStorage dsh.director.conversations | 按对话 ID 存储，未按 branchId 隔离      |

\| 总监状态 | localStorage dsh.director.store         | 包含 currentBranch、branchList 等 |

\### 9.2 迁移步骤
```

用户升级到新版本（首次启动）

&#x20;   │

&#x20;   ▼

① 检测是否需要迁移

&#x20;  ├─ 检查 mindmap.json 是否存在

&#x20;  ├─ 检查 branches.json 是否存在

&#x20;  └─ 如果 branches.json 存在且 mindmap.json 不存在 → 执行迁移

&#x20;   │

&#x20;   ▼

② 备份现有数据

&#x20;  ├─ 将 branches.json 备份为 branches.backup.{timestamp}.json

&#x20;  ├─ 将 localStorage 对话历史备份导出为 JSON 文件

&#x20;  └─ 备份完成后才开始迁移（失败可回滚）

&#x20;   │

&#x20;   ▼

③ 执行迁移

&#x20;  ├─ 读取 branches.json，将线性分支列表转换为思维导图节点

&#x20;  │   ├─ 创建根节点 root（主线）

&#x20;  │   ├─ 所有现有分支作为 root 的一级子节点（parentId=root）

&#x20;  │   ├─ 从分支配置中复制：name→label、icon、model、status

&#x20;  │   ├─ 从对话历史中统计：msgCount、lastActivityAt

&#x20;  │   └─ 标记 migratedFrom: "branches.json"

&#x20;  ├─ 对话历史按 branchId 隔离存储

&#x20;  │   ├─ 遍历现有对话历史

&#x20;  │   ├─ 按 branchId（或 conversationId）分组

&#x20;  │   └─ 写入 conversations/{branchId}.json

&#x20;  ├─ 生成 mindmap.json

&#x20;  └─ 保留 branches.json（不再使用，但保留作为备份和溯源）

&#x20;   │

&#x20;   ▼

④ 验证迁移结果

&#x20;  ├─ 检查 mindmap.json 节点数 = branches.json 分支数 + 1（根节点）

&#x20;  ├─ 检查每个节点的 msgCount 与原对话历史一致

&#x20;  ├─ 检查对话历史文件数 = 分支数

&#x20;  └─ 验证失败 → 回滚到备份，显示错误提示

&#x20;   │

&#x20;   ▼

⑤ 完成

&#x20;  ├─ 显示迁移成功提示："已从旧版本迁移 {n} 个分支到思维导图"

&#x20;  ├─ 用户打开思维导图视图时，自动展示迁移后的树结构

&#x20;  └─ 记录迁移日志到 logs/



```
\### 9.3 回滚方案

\* 迁移前自动备份所有数据

\* 迁移失败时：删除 mindmap.json + 新 conversations/ 目录，恢复 branches.json + 原 localStorage

\* 用户可手动回滚：在设置→数据→"回滚到旧版本数据结构"

\* 旧版本数据（branches.json）永久保留，不删除
```
