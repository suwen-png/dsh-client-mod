## 一、文档概述

### 1.1 目的

本文档定义**操作分级防护、应急预案、回滚机制、灾难恢复和事后复盘**的完整规范，确保：
1. 操作风险被准确分级，高风险操作有足够防护
2. 故障发生时有明确的应急处理流程，不慌乱
3. 操作失败时能快速回滚到操作前状态，减少损失
4. 灾难发生时有恢复计划，能尽快恢复服务
5. 事故发生后有复盘机制，持续改进

### 1.2 适用范围

| 场景 | 是否适用 | 说明 |
|------|:-------:|------|
| 文件修改/删除/创建 | ✅ 适用 | 按操作分级执行防护 |
| 系统配置修改 | ✅ 强制适用 | 至少R3级别，必须有回滚方案 |
| 批量操作 | ✅ 强制适用 | 至少R3级别，必须分步验证 |
| 代码修改/部署 | ✅ 适用 | 按变更管理流程执行 |
| 只读操作/查询 | ❌ 不适用 | R1级别，无特殊防护 |
| 普通办公/闲聊 | ❌ 不适用 | 不走应急与回滚流程 |

## 二、操作分级机制

### 2.1 四级操作风险

| 级别 | 名称 | 定义 | 典型操作 | 防护要求 |
|:----:|------|------|---------|---------|
| **R1** | 低风险 | 只读操作/临时文件创建/格式调整，无不可逆影响 | 查看文件、查询信息、创建tmp_临时文件、格式美化 | 无特殊防护，正常执行 |
| **R2** | 中风险 | 修改现有文件/创建新文档/安装工具，影响有限但可回滚 | 修改配置文件、创建项目文档、安装开发工具、修改非核心代码 | 执行前确认，执行后验证 |
| **R3** | 高风险 | 删除文件/修改系统配置/批量操作/核心代码修改，影响较大 | 删除文件、批量重命名、修改系统配置、部署代码、修改数据库 | 执行前快照/备份，方案需审核，执行中分步验证 |
| **R4** | 极高风险 | 不可逆操作/数据清除/系统级变更/安全相关，可能造成严重损失 | 格式化磁盘、清除数据库、修改系统核心配置、删除生产数据、安全策略变更 | 必须人类在场，双重确认，完整回滚方案，操作日志记录 |

### 2.2 操作分级判断流程

```
操作是否只读？
├─ 是 → R1 低风险
└─ 否 → 操作是否可逆？
    ├─ 否 → R4 极高风险（不可逆操作）
    └─ 是 → 操作影响范围？
        ├─ 单个非核心文件 → R2 中风险
        ├─ 多个文件/核心文件/系统配置 → R3 高风险
        └─ 数据清除/系统级变更/安全相关 → R4 极高风险
```

### 2.3 各级别防护措施详解

#### R1 低风险防护
- 无特殊防护要求
- 执行后简单验证结果
- 临时文件加 `tmp_` 前缀，便于后续清理

#### R2 中风险防护
- **执行前**：确认操作范围和目标，复述用户需求
- **执行中**：按计划执行，不擅自扩大范围
- **执行后**：验证操作结果，确认无副作用
- **回滚准备**：记录修改内容，必要时创建备份

#### R3 高风险防护（强制）
- **执行前**：
  - ✅ 必须创建快照或备份（文件/配置/数据）
  - ✅ 必须输出操作方案，包含步骤、风险、回滚方案
  - ✅ 方案需用户确认（CP2前置审核）
  - ✅ 检查环境和依赖是否正常
- **执行中**：
  - ✅ 分步执行，每步验证后再继续
  - ✅ 发现异常立即暂停，不强行继续
  - ✅ 实时反馈进度和结果
- **执行后**：
  - ✅ 全面验证操作结果
  - ✅ 确认无副作用和回归问题
  - ✅ 记录操作日志（时间、操作人、内容、结果）
  - ✅ 更新风险登记册状态

#### R4 极高风险防护（强制）
- **R3全部防护** + 以下额外要求：
- **执行前**：
  - ✅ 必须人类在场（远程或现场）
  - ✅ 双重确认（AI确认+人类明确确认）
  - ✅ 完整的回滚方案，且回滚方案已验证可行
  - ✅ 通知所有相关方
  - ✅ 选择低峰期执行
- **执行中**：
  - ✅ 人类全程监控，AI每步等待确认
  - ✅ 详细记录每一步的输入输出
  - ✅ 任何异常立即停止，等待人类指示
- **执行后**：
  - ✅ 人类验证操作结果
  - ✅ 完整的操作日志归档
  - ✅ 事后复盘（无论成功失败）
  - ✅ 更新应急预案（如有新发现）

### 2.4 操作分级标记

AI 执行操作时必须输出操作分级标记：

| 级别 | 标记格式 | 说明 |
|:----:|---------|------|
| R1 | 无需标记 | 低风险操作不输出标记 |
| R2 | `【R2中风险操作】` | 执行前输出，说明操作内容 |
| R3 | `【R3高风险操作】` | 执行前输出，包含操作方案+回滚方案 |
| R4 | `【R4极高风险操作确认】` | 执行前输出，等待人类明确确认 |

## 三、应急预案

### 3.1 应急响应流程

```
发现异常
  ↓
立即暂停当前操作（CP3阻塞反馈）
  ↓
评估异常严重程度
  ├─ 轻微 → 自行处理，记录日志
  ├─ 中等 → 通知用户，按应急预案处理
  └─ 严重 → 立即通知用户，启动灾难恢复计划
  ↓
执行应急处理
  ↓
验证处理结果
  ↓
恢复正常操作或回滚
  ↓
事后复盘
```

### 3.2 常见故障场景应急预案

#### 场景一：文件修改错误
**触发条件**：修改文件后发现内容错误或不符合需求
**应急步骤**：
1. 立即暂停后续操作
2. 评估错误影响范围
3. 如有备份/快照 → 恢复到修改前状态
4. 如无备份 → 手动撤销修改，对照原始内容恢复
5. 验证恢复结果
6. 重新分析需求，正确执行修改
**预防措施**：R2及以上操作前创建备份

#### 场景二：文件误删除
**触发条件**：删除了不应该删除的文件
**应急步骤**：
1. 立即暂停操作
2. 检查回收站/临时目录是否有备份
3. 如有快照/备份 → 从备份恢复
4. 如无备份 → 检查版本控制系统（如git）是否可恢复
5. 如都无法恢复 → 通知用户，评估损失，重建文件
6. 记录事故，事后复盘
**预防措施**：删除操作前必须确认，R3及以上删除前必须备份

#### 场景三：操作导致系统异常
**触发条件**：修改配置/代码后系统无法正常运行
**应急步骤**：
1. 立即暂停操作
2. 评估系统异常程度
3. 如有备份/快照 → 回滚到修改前状态
4. 如无备份 → 手动撤销修改，恢复原始配置
5. 重启相关服务/应用，验证恢复结果
6. 如无法恢复 → 启动灾难恢复计划
7. 记录事故，事后复盘
**预防措施**：系统配置修改前必须备份，修改后必须验证

#### 场景四：网络连接中断
**触发条件**：需要外网但网络不可用（VPN未开/网络故障）
**应急步骤**：
1. 检查网络连接状态
2. 检查VPN是否开启（用户未开VPN是常见原因）
3. 如VPN未开 → 通知用户开启VPN
4. 如VPN已开但仍无法连接 → 检查网络配置，尝试重启网络
5. 如短时间无法恢复 → 评估是否可离线执行部分任务
6. 如必须联网 → 等待网络恢复，记录阻塞原因（CP3）
**预防措施**：需要外网前检查VPN和网络状态

#### 场景五：工具/命令执行失败
**触发条件**：工具报错或命令执行无结果
**应急步骤**：
1. 读取错误信息，理解失败原因
2. 检查工具是否安装、环境是否正常
3. 检查命令参数是否正确
4. 如为环境问题 → 修复环境后重试
5. 如为参数问题 → 修正参数后重试
6. 如工具本身有问题 → 寻找替代工具或方案
7. 三次失败后换方案（准则5）
**预防措施**：执行前检查工具和环境，复杂命令先小范围测试

#### 场景六：数据丢失/损坏
**触发条件**：发现数据丢失或文件损坏
**应急步骤**：
1. 立即暂停所有可能影响数据的操作
2. 评估数据丢失范围和严重程度
3. 检查备份/快照/版本控制系统
4. 从最新可用备份恢复数据
5. 验证恢复数据的完整性
6. 如无备份 → 通知用户，评估损失，尝试数据恢复工具
7. 启动灾难恢复计划（如严重）
8. 记录事故，事后复盘
**预防措施**：重要数据定期备份，R3及以上操作前必须备份

### 3.3 应急联系与升级

| 异常等级 | 处理方式 | 响应时间 |
|:--------:|---------|:--------:|
| 轻微 | AI自行处理，记录日志 | 立即 |
| 中等 | AI通知用户，按应急预案处理 | 10分钟内 |
| 严重 | AI立即通知用户，启动灾难恢复计划 | 立即 |
| 灾难 | AI立即通知用户，人类主导恢复，AI辅助 | 立即 |

## 四、回滚机制

### 4.1 回滚触发条件

| 触发条件 | 说明 |
|---------|------|
| 操作结果不符合预期 | 执行后发现结果错误或不满足需求 |
| 操作产生副作用 | 操作影响了不应该影响的内容 |
| 系统异常 | 操作后系统无法正常运行 |
| 用户要求回滚 | 用户明确要求撤销操作 |
| 验证失败 | 后置审核不通过，需要回到操作前状态 |

### 4.2 回滚方式

| 方式 | 适用场景 | 操作步骤 | 恢复时间 |
|------|---------|---------|:--------:|
| 备份恢复 | 有完整备份的文件/配置 | 从备份复制覆盖当前文件 | 几分钟 |
| 快照恢复 | 有系统/目录快照 | 恢复快照到目标位置 | 几分钟到几十分钟 |
| 版本控制 | 使用git等版本控制系统 | git checkout/git revert | 几分钟 |
| 手动撤销 | 无备份但修改内容已知 | 手动恢复原始内容 | 视修改量而定 |
| 重新创建 | 文件丢失且无备份 | 从记忆/文档/历史记录重建 | 视复杂度而定 |

### 4.3 回滚操作步骤

```
1. 确认回滚需求
   ├─ 回滚原因是什么？
   ├─ 回滚到哪个时间点/版本？
   └─ 回滚影响范围是什么？
   ↓
2. 选择回滚方式
   ├─ 有备份/快照 → 备份恢复
   ├─ 有版本控制 → 版本回退
   ├─ 无备份但修改已知 → 手动撤销
   └─ 无备份且修改未知 → 评估损失，重建或接受
   ↓
3. 执行回滚
   ├─ R3/R4回滚操作本身也是高风险，需按操作分级防护
   ├─ 回滚前再次确认目标状态
   └─ 分步执行，每步验证
   ↓
4. 验证回滚结果
   ├─ 文件内容是否恢复到目标状态？
   ├─ 系统是否正常运行？
   ├─ 有无副作用？
   └─ 用户需求是否满足？
   ↓
5. 记录回滚日志
   ├─ 回滚原因、时间、操作人
   ├─ 回滚方式和步骤
   ├─ 回滚结果验证
   └─ 后续改进措施
```

### 4.4 备份策略

| 操作级别 | 备份要求 | 备份内容 | 保留时间 |
|:--------:|---------|---------|:--------:|
| R1 | 无需备份 | — | — |
| R2 | 建议备份 | 修改的文件 | 1周 |
| R3 | 强制备份 | 修改的文件+相关配置 | 1个月 |
| R4 | 强制完整备份 | 整个目录/系统快照 | 3个月 |

**备份命名规范**：`backup_[文件名]_[YYYYMMDD_HHMMSS].[扩展名]`
**备份位置**：项目目录下的 `_backups/` 目录或系统临时目录

## 五、灾难恢复计划

### 5.1 灾难分级

| 级别 | 名称 | 定义 | 示例 |
|:----:|------|------|------|
| D1 | 轻微灾难 | 单个文件丢失，可快速恢复 | 误删单个文档 |
| D2 | 中等灾难 | 多个文件丢失或目录损坏，需一定时间恢复 | 误删整个目录、磁盘分区损坏 |
| D3 | 严重灾难 | 系统无法启动或数据大面积丢失，需长时间恢复 | 系统崩溃、病毒攻击、磁盘故障 |
| D4 | 极端灾难 | 物理设备损坏或数据完全丢失，无法本地恢复 | 电脑被盗、火灾、硬盘物理损坏 |

### 5.2 灾难恢复流程

```
确认灾难发生
  ↓
评估灾难等级（D1-D4）
  ↓
通知用户，说明情况和预计恢复时间
  ↓
启动对应级别的恢复计划
  ├─ D1 → 从备份恢复单个文件
  ├─ D2 → 从备份/快照恢复目录，检查完整性
  ├─ D3 → 系统恢复+数据恢复+验证
  └─ D4 → 外部数据恢复服务/重建
  ↓
恢复数据和系统
  ↓
全面验证恢复结果
  ↓
恢复正常服务
  ↓
事后复盘，更新灾难恢复计划
```

### 5.3 各级别恢复计划

#### D1 轻微灾难恢复
1. 确认丢失文件
2. 检查 `_backups/` 目录是否有备份
3. 检查版本控制系统（git）是否有历史版本
4. 从最新备份恢复
5. 验证文件完整性
6. 记录事故

#### D2 中等灾难恢复
1. 评估丢失范围
2. 检查最近的目录快照/备份
3. 从快照恢复整个目录
4. 逐个验证文件完整性
5. 如部分文件无备份 → 从版本控制或记忆重建
6. 全面验证系统功能
7. 记录事故，事后复盘

#### D3 严重灾难恢复
1. 立即通知用户，说明严重程度
2. 评估系统状态，判断是否可修复
3. 如可修复 → 修复系统+恢复数据
4. 如不可修复 → 重装系统+从备份恢复数据
5. 恢复所有配置和依赖
6. 全面验证系统功能和数据完整性
7. 记录详细事故报告
8. 事后复盘，更新防护措施

#### D4 极端灾难恢复
1. 立即通知用户，说明极端情况
2. 评估物理设备状态
3. 如设备可修复 → 专业数据恢复服务
4. 如设备不可修复 → 从云端备份/外部存储恢复
5. 如无任何备份 → 评估损失，从零重建
6. 记录详细事故报告
7. 全面复盘，更新备份策略和灾难预防措施

### 5.4 预防灾难的措施

| 措施 | 说明 | 频率 |
|------|------|:----:|
| 定期备份 | 重要数据定期备份到外部存储或云端 | 每周 |
| 版本控制 | 所有代码和文档使用git等版本控制 | 持续 |
| 操作前备份 | R3/R4操作前必须创建备份/快照 | 每次操作 |
| 系统还原点 | 定期创建系统还原点 | 每月 |
| 防病毒/防恶意软件 | 安装安全软件，定期扫描 | 每周 |
| 物理安全 | 设备防盗、防火、防水 | 持续 |

## 六、事后复盘

### 6.1 复盘触发条件

| 触发条件 | 说明 |
|---------|------|
| R3/R4操作完成后 | 无论成功失败，高风险操作必须复盘 |
| 应急事件发生后 | 任何需要应急处理的事件 |
| 灾难发生后 | 任何级别的灾难 |
| 定期复盘 | 每月/每季度定期回顾 |
| 用户要求复盘 | 用户明确要求时 |

### 6.2 复盘流程

```
1. 事件回顾
   ├─ 发生了什么？
   ├─ 时间线是什么？
   └─ 影响范围是什么？
   ↓
2. 根因分析（5Why法）
   ├─ 为什么会发生？
   ├─ 为什么没有预防？
   ├─ 为什么没有及时发现？
   ├─ 为什么处理不及时？
   └─ 根本原因是什么？
   ↓
3. 经验教训
   ├─ 哪些做得好？
   ├─ 哪些做得不好？
   └─ 下次怎么改进？
   ↓
4. 改进措施
   ├─ 预防措施（避免再次发生）
   ├─ 检测措施（更早发现）
   └─ 响应措施（更快处理）
   ↓
5. 跟踪验证
   ├─ 改进措施是否执行？
   ├─ 效果如何？
   └─ 是否需要进一步改进？
```

### 6.3 根因分析方法（5Why）

**示例**：文件误删事件
1. 为什么文件被删？→ 执行删除命令时选错了文件
2. 为什么会选错？→ 没有仔细确认文件名，操作太快
3. 为什么没有确认？→ 删除操作前没有强制确认机制
4. 为什么没有强制确认？→ 操作分级机制未落实，删除操作未按R3防护
5. 根本原因：操作分级机制执行不到位，缺少强制确认环节

**改进措施**：
- 预防：删除操作前必须输出文件列表，等待用户确认
- 检测：删除操作后立即验证目标文件状态
- 响应：删除前自动创建备份，误删后可快速恢复

### 6.4 复盘记录模板

```markdown
## 复盘记录：[事件标题]

**事件日期**：YYYY-MM-DD
**事件等级**：R3/R4/D1-D4
**事件描述**：发生了什么，影响范围
**时间线**：
- HH:MM 发现异常
- HH:MM 启动应急
- HH:MM 恢复正常

**根因分析**：
1. Why1：...
2. Why2：...
3. Why3：...
4. Why4：...
5. Why5（根本原因）：...

**经验教训**：
- 做得好的：...
- 做得不好的：...

**改进措施**：
| 措施 | 类型 | 负责人 | 计划完成 | 状态 |
|------|------|:------:|:--------:|:----:|
| ... | 预防/检测/响应 | ... | ... | ... |

**验证结果**：改进措施是否有效，是否需要进一步改进
```

## 七、AI在应急与回滚中的职责

### 7.1 AI 必须做的

| 职责 | 执行时机 | 输出 |
|------|---------|------|
| 操作分级 | 每次操作前 | 操作级别标记（R1-R4） |
| 备份创建 | R3/R4操作前 | 备份/快照 |
| 方案输出 | R3/R4操作前 | 操作方案+风险+回滚方案 |
| 分步验证 | R3/R4操作中 | 每步验证结果 |
| 异常暂停 | 发现异常时 | 立即暂停+CP3阻塞反馈 |
| 应急处理 | 故障发生时 | 按应急预案执行 |
| 回滚执行 | 需要回滚时 | 按回滚流程执行 |
| 事后复盘 | R3/R4操作/应急事件后 | 复盘记录+改进措施 |

### 7.2 AI 不能做的

| 禁止行为 | 原因 |
|---------|------|
| 跳过操作分级 | 所有操作必须准确分级，不能为了省事而降级 |
| R3/R4操作前不备份 | 备份是回滚的基础，无备份不执行高风险操作 |
| 异常时强行继续 | 发现异常必须暂停，不能"试试看"强行继续 |
| 隐瞒操作错误 | 操作出错必须立即报告，不能隐瞒或试图掩盖 |
| 未经确认执行R4操作 | R4操作必须人类明确确认，AI不能自行执行 |
| 删除备份 | 操作成功后不能立即删除备份，保留至少保留期限 |

### 7.3 AI 何时必须请求人类介入

| 场景 | 介入方式 |
|------|---------|
| R4极高风险操作 | 必须人类在场，双重确认，全程监控 |
| 操作结果不确定 | 向用户说明不确定性，请求确认 |
| 应急事件无法自行处理 | 立即通知用户，等待指示 |
| 灾难发生 | 立即通知用户，人类主导恢复 |
| 回滚方案不可行 | 向用户说明情况，请求替代方案 |
| 操作影响超出预期 | 立即暂停，通知用户，评估影响 |

### 8.1 操作前检查

- [ ] 操作已准确分级（R1-R4）

- [ ] R4操作有人类在场
- [ ] R4操作已双重确认
- [ ] R4回滚方案已验证可行
- [ ] 环境和依赖已检查正常

### 8.2 操作中检查

- [ ] 按计划分步执行，不擅自扩大范围

- [ ] 发现异常立即暂停（CP3）

- [ ] 风险登记册状态已更新
