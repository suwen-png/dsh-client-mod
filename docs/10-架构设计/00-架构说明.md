# 00 - 架构说明

> 文档编号：DSH-MOD-ARCH-00 ｜ 版本：V1.0 ｜ 日期：2026-08-24

## 一、设计决策

### 1.1 为什么直接改原客户端，而不是外部 bundle 注入

| 维度 | 外部 bundle 注入（旧方案） | 直接改原客户端（本方案） |
|------|---------------------------|------------------------|
| 原理 | 通过 profile 启用 + 符号链接注入独立 npm 包，在 `apply(ctx)` 中往 slot 注入组件 | 直接修改 Harness 原客户端的编译产物 `lib/client.js`，通过 Junction 替换原包 |
| 主区渲染 | 依赖 `main.page` keyed slot 的注册时序，存在「组件被调用但视觉不渲染」的卡点 | 直接在 layout 源码中改渲染逻辑，不存在时序问题 |
| 复杂度 | 需要理解 slot 注册机制、inject/register 时序、keyed 选择条件 | 直接读源码改源码，逻辑直观 |
| 风险 | 注入失败时静默不加载（连角标都没有） | 修改出错时 Harness 可能报错，但可一键复原 |
| 可维护性 | 独立包，与原客户端解耦 | 与原客户端版本强绑定，升级需重新适配 |

**决策**：当前阶段（功能验证 + 快速迭代）选择直接改原客户端，优先级是「能跑起来、能看到效果」。后续稳定后可考虑回退到 bundle 注入方案。

### 1.2 为什么用 Junction 符号链接，而不是直接覆盖

- **零拷贝**：Junction 是目录级符号链接，修改 workspace 文件即时生效，无需复制
- **可切换**：删除 Junction 即恢复原目录，无需重新复制文件
- **可追踪**：`status.ps1` 可清晰看到哪些包被替换、指向哪里
- **安全**：Junction 指向 workspace，原文件始终保留在 original/


## 三、脚本调用关系

```
backup.ps1          原安装目录 → original/        （首次/重新备份）
init-workspace.ps1  original/ → workspace/        （首次/重置工作区）
apply.ps1           workspace/ → Junction 替换     （应用修改，自动快照）
restore.ps1         original/ → 原安装目录         （一键复原）
status.ps1          只读检查                       （查看所有包状态）
diff.ps1            workspace vs original          （生成差异报告）
snapshot.ps1        workspace/ → snapshots/        （手动快照）
```

## 四、安全机制

| 机制 | 说明 |
|------|------|
| 应用前自动快照 | `apply.ps1` 执行前自动将当前 workspace 复制到 `snapshots/snapshot-<时间>-before-apply/` |
| original 只读约定 | 文档明确 original/ 是复原源，不直接修改 |
| Junction 保护 | `restore.ps1` 只删除 Junction，不删除非 Junction 的真实目录（防止误删） |
| 操作日志 | 所有脚本操作写入 `logs/dsh-mod-YYYYMMDD.log` |
| 状态可查 | `status.ps1` 随时查看每个包的原始/修改状态 |
