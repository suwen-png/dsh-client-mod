## 一、背景与定位

### 1.1 方案变更

| 维度 | 旧方案（外部bundle注入） | 本方案（原客户端直接改造） |
|------|--------------------------|--------------------------|
| 原理 | 独立npm包通过profile注入，在apply(ctx)中往slot注入组件 | 直接修改Harness原客户端编译产物lib/client.js，通过Junction替换原包 |
| 主区渲染 | 依赖main.page keyed slot注册时序，存在不渲染卡点 | 在conversation.view list slot中新增总监tab，与对话/轨迹同层 |
| 复杂度 | 需要理解slot注入时序、keyed选择条件 | 直接在原代码中新增注册，逻辑直观 |
| 风险 | 注入失败静默不加载 | 修改出错可一键复原（restore.ps1） |
| 决策 | 废弃 | **采用** |

### 1.2 总监的本质定义（从项目原始设计提炼）

**总监层 = 会话预处理中枢**，核心铁律：
- ❌ 不执行业务
- ❌ 不调用工具
- ❌ 不运行大模型推理（指业务推理，总监自身用本地小模型做整理/路由）
- ✅ 索引检索 → 按需加载 → 上下文筛选精简 → 模型路由 → 组装报文 → 写入提交列

**总监处理流程（5步标准执行逻辑）**：
1. **整理语言**：按对项目的理解，把用户意图整理成更适合大模型识别的语言（本地qwen2:7b）
2. **判断是否需要切新分支**：该消息与当前上下文是否连续
3. **判断是否需要切模型**：任务类型匹配最优模型（切模型自动调整分支）
4. **切换分支时判断传哪些上下文**：跨模型上下文片段筛选
5. **自动审核大模型产出**：文档/代码是否符合要求

### 1.3 三层总监体系（本阶段落地第一层）

```
全局总管（光球）    ← 本阶段不落地，后续迭代
    ↓
项目总监（文件夹级）  ← 本阶段不落地，后续迭代
    ↓
会话总监（当前会话）  ← ★ 本阶段落地：每个会话绑定一个总监实例
```

本阶段先实现**会话级总监**：在Harness的每个会话中，总监tab提供预处理能力。文件夹级/全局级总监后续迭代。

### 2.3 完整消息流（核心）

```
用户在总监tab输入消息
    │
    ▼
① 发送目标判定（当前tab=总监 → 发给总监）
    │
    ▼
② 总监预处理（本地qwen2:7b via Ollama :11434）
   ├─ 整理语言（把用户口语化意图整理为精确指令）
   ├─ 判断切分支/切模型
   ├─ 上下文筛选
   └─ 组装待提交报文
    │
    ▼
③ 总监处理过程展示在总监对话流（思考路径/整理结果）
    │
    ▼
④ 自动转发到原对话系统（调用原sendSession）
   → 原对话tab显示总监整理后的消息 + 大模型回复
   → 原轨迹tab显示完整调用链
    │
    ▼
⑤ 总监自动审核大模型产出（可选，执行逻辑开关控制）
```

**关键设计决策**：
- 总监**只发整理后的指令**到对话系统，不发总监自己的回复
- 总监对话流是独立的消息记录（用户↔总监），与原对话流（用户↔大模型）分离但共享会话
- 鼠标停在对话tab发送 → **完全跳过总监**，直接大模型直连
- 鼠标停在总监tab发送 → 走总监预处理流程

### 2.4 与原对话/轨迹的关系

| 维度 | 原对话tab | 原轨迹tab | 总监tab |
|------|----------|----------|---------|
| 消息存储 | 原chatStore | 原trajectory store | 新增directorStore（独立但同sessionId） |
| 输入栏 | 原InputBar | 无（只读） | 原InputBar（发送目标=总监） |
| 模型选择 | 原模型选择器 | 无 | 总监设置中配置（本地/云端路由） |
| 数据共享 | sessionId共享 | sessionId共享 | sessionId共享 |
| 切换影响 | 不丢数据 | 不丢数据 | 不丢数据 |
| 原功能保留 | ✅ 完全保留 | ✅ 完全保留 | 新增，不影响原tab |

### 3.1 执行逻辑项（可配置的prompt模板）

**本质**：每个执行逻辑 = 一段prompt模板 + 启停开关，控制总监要做什么。

| 执行逻辑项 | 默认状态 | prompt模板（示例） |
|-----------|---------|-------------------|
| 整理语言 | ✅ 启用 | "你是一个项目总监，请把用户的口语化需求整理为精确、无歧义的技术指令，保留核心意图，去除冗余表述。" |
| 调整模型 | ✅ 启用 | "根据任务类型判断最优模型：代码任务→coder模型，推理任务→reasoner模型，日常对话→chat模型。输出模型名称和理由。" |
| 切换分支 | ✅ 启用 | "判断当前消息与已有对话上下文是否连续。连续→沿用当前分支；不连续→建议开新分支。" |
| 上下文筛选 | ✅ 启用 | "当切换模型/分支时，筛选需要传递的上下文片段，去除无关历史，控制token量。" |
| 自动审核产出 | ✅ 启用 | "大模型返回结果后，自动审核文档/代码是否符合原始需求，不符合则标注问题并建议修正。" |

> 🔴 **2026-09-12 修订（原为「⬜ 禁用」，与本文 §1.2 规格自相矛盾）**：总监被定义为

> 第 4/5 步被 `enabled` 过滤掉 ⇒ 用户核心目标「审核由总监统筹」默认不生效。
> 两步都是 **G0**（零模型、零网络、永不抛错），开启不引入失败面 ⇒ 默认改为启用。
> 代码留痕：`src/logic/duties.js`；闸门：`scripts/verify-batch8.mjs`（断言"五步显式 enabled 且都为 true"）。

async function directorProcess(userInput, sessionContext, enabledLogics) {
    const systemPrompt = buildDirectorSystemPrompt(enabledLogics);
    const response = await fetch("http://localhost:11434/api/chat", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({
            model: "qwen2:7b",
            messages: [
                { role: "system", content: systemPrompt },
                { role: "user", content: userInput }
            ],
            stream: false,
            options: { temperature: 0.3 }  // 总监整理用低温度
        })
    });
    const data = await response.json();
    return parseDirectorOutput(data.message.content);
}

### 6.6 改动点5：总监处理核心逻辑

```javascript
async function directorProcess(sessionId, userText, chatActions) {
    const store = directorStoreFactory(sessionId);
    const config = store.getConfig();

    // 1. 添加用户消息到总监对话流
    store.addMessage({ role: "user", content: userText, ts: Date.now() });
    store.setStatus("processing");

    try {
        // 2. 调用本地模型预处理
        const systemPrompt = buildDirectorSystemPrompt(config.enabledLogics);
        const result = await callOllama(systemPrompt, userText, config.model);

        // 3. 解析总监输出
        const parsed = parseDirectorOutput(result);
        // parsed = {整理后指令, 模型建议, 分支建议, 上下文片段}

        // 4. 添加总监消息到总监对话流
        store.addMessage({
            role: "assistant",
            content: result,
            parsed: parsed,
            ts: Date.now()
        });

        // 5. 自动转发到原对话系统
        if (config.autoForward) {
            chatActions.sendToChat(parsed.instruction);
        }

        store.setStatus("done");
    } catch (err) {
        store.setStatus("error");
        store.addMessage({ role: "system", content: `总监处理失败: ${err.message}`, ts: Date.now() });
    }
}
```

function buildDirectorSystemPrompt(enabledLogics) {
    const base = `你是Starfield项目的会话总监。你的职责是对用户输入进行预处理，然后将整理后的指令转发给大模型执行。
你不直接回答用户问题，只做整理和路由。`;

    const logicPrompts = {
        "整理语言": `1. 语言整理：把用户的口语化需求整理为精确、无歧义的技术指令，保留核心意图，去除冗余。`,
        "调整模型": `2. 模型路由：根据任务类型推荐最优模型（代码→coder，推理→reasoner，日常→chat）。`,
        "切换分支": `3. 分支判断：判断当前消息与上下文是否连续，连续则沿用，不连续建议开新分支。`,
        "上下文筛选": `4. 上下文筛选：切换模型/分支时，筛选需要传递的上下文，控制token量。`,
        "自动审核产出": `5. 产出审核：大模型返回后，审核是否符合原始需求。`
    };

    const enabled = enabledLogics.filter(l => l.enabled).map(l => logicPrompts[l.name]).join("\n");
    const outputFormat = `\n输出格式（JSON）：{"instruction": "整理后指令", "model": "模型建议", "branch": "分支建议", "reasoning": "思考过程"}`;

    return base + "\n" + enabled + outputFormat;
}
