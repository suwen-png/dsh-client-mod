# 总监对话模式 — 开发规范与审核文档

## 0. 流程规范声明

**本项目所有开发必须严格遵循以下流程：**
1. **先写文档**：每个修改点必须先写入本文档，包含根因分析、涉及函数/变量、修改方案、概率评估
2. **文档审核**：审核文档是否满足需求、修改概率是否>80%
3. **审核通过后改代码**：仅修改文档中已审核通过的点
4. **改完全局审核**：检查所有函数变量引用、调用链、作用域、流程通顺性
5. **按测试标准验证**：每个修改点必须有对应的测试用例和通过标准

**当前状态**：已打探针（scrollProbe/directChatProbe）用于数据采集，探针不属于功能修改，测试完成后移除。

## 1. 当前问题清单（待用户提供探针数据后确认）

### P1：总监消息发送后停在顶部，不自动滚到底部
**现象**：发送消息后，新消息在底部，但视图停在顶部，需手动下拉。

**已实施修改（待验证）**：
- `DirectorView` 行7233：`useEffect + scrollIntoView` → `useLayoutEffect + requestAnimationFrame + scrollTop=scrollHeight`
- 原因：useEffect 在 DOM 更新前执行，scrollHeight 是旧值；scrollIntoView 滚到视口顶部而非容器内部底部

**涉及函数/变量**：
- `messagesEndRef`（ref，绑定消息滚动容器）
- `scrollProbe`（state，探针：scrollTop/scrollHeight/clientHeight）
- `state.messages.length`（触发重渲染的依赖）

**概率评估**：85%（useLayoutEffect+RAF 是标准解决方案，但需确认容器 overflow/flex 设置正确）

**测试标准**：
- 发送消息后，`scrollProbe` 的 scrollTop ≈ scrollHeight（差值<50px）
- 消息可见，无需手动滚动
- 连续发送多条消息，每次都自动滚到底部

### P2：总监tab中给对话发消息发不出去
**现象**：点击右侧对话小窗后，输入消息发送，消息未出现在对话中。

**已实施修改（待验证）**：
- `window.__directChatSubmit` 添加 `window.__directChatProbe` 全局探针（记录调用次数/sessionId/draft）

**涉及函数/变量**：
- `directorLayoutStore.setFocusTarget("chat")`（点击对话小窗时调用）
- `window.__directorFocusTarget`（全局变量，InputBar 读取）
- `window.__directorCurrentView`（全局变量，InputBar 读取）
- `InputBar` 键盘回车逻辑（行~3543）：判断 dirView+focusTarget
- `InputBar` 发送按钮逻辑（行~3717）：判断 dirView+focusTarget
- `window.__directChatSubmit(sessionId, draft)`（实际发送函数）
- `sessions.list.getSnapshot().byId[sessionId]`（获取会话对象）
- `conversation.sendSession(sess, draft, [], "chat")`（发送到对话）

**可能根因（待探针数据确认）**：
1. 点击对话小窗后 focusTarget 未更新为 "chat"
2. InputBar 中 dirView 不是 "director"
3. `__directChatSubmit` 被调用但 sess 为 undefined
4. `sendSession` 调用失败

**概率评估**：60%（需探针数据确认具体根因，当前无法确定）

**测试标准**：
- 点击对话小窗后，标题栏 `focus:` 标签变为 chat
- 发送消息后，`directCall:` 探针 +1
- 消息出现在对话历史中
- 若 directCall 不增加 → 焦点切换问题；若 directCall 增加但消息不出现 → 发送函数问题

### P3：每次打开总监数据都为空（持久化失效）
**现象**：发送总监消息后，关闭重启 Harness，总监对话历史丢失。

**已实施修改（待验证）**：
- `createDirectorStore` 创建时调用 `loadDirectorStore(sessionId)` 从 localStorage 加载
- `notify()` 中调用 `saveDirectorStore(sessionId, state)` 保存到 localStorage
- localStorage key：`dsh.director.store.${sessionId}`

**涉及函数/变量**：
- `loadDirectorStore(sessionId)`（行5412，读取 localStorage）
- `saveDirectorStore(sessionId, state)`（行5423，写入 localStorage）
- `createDirectorStore(sessionId)`（行5429，创建时加载）
- `notify()`（行5437，变化时保存）
- `directorStoreFactory(sessionId)`（行5469，缓存 store）
- `DIRECTOR_STORE_PREFIX = "dsh.director.store."`（key 前缀）

**可能根因（待验证）**：
1. localStorage 在 Harness 插件环境中不可用或域隔离
2. sessionId 每次打开会话不同
3. saveDirectorStore 未被调用（notify 未触发）
4. loadDirectorStore 读取失败（JSON 解析错误）

**概率评估**：50%（代码逻辑正确，但 Harness 环境特殊性未知，需 console.log 验证）

**测试标准**：
- 发送消息后，localStorage 中存在 `dsh.director.store.${sessionId}` 键
- 重启 Harness 后，总监消息数量与重启前一致
- 若 localStorage 无数据 → 保存失败；若有数据但加载后为空 → 加载失败或 sessionId 不匹配

### P7：消息排列方向错误（从顶部开始，应从底部开始）
**现象**：总监消息流中，消息从容器顶部开始排列，新消息添加在底部但视图停在顶部。用户期望"和标准对话一样在下面，一点点往上堆"——即消息从容器底部开始排列，新消息在最下方。

**根因分析**：
- 当前消息容器样式：`display: flex; flex-direction: column;` — 消息从顶部开始排列
- 标准对话（ChatView）使用 `flex-direction: column` 但配合自动滚动到底部，视觉上消息在底部
- 但总监容器缺少 `justify-content: flex-end` 或等效机制，导致消息少时贴在顶部而非底部

**涉及函数/变量**：
- `DirectorView` 消息容器 style（行~7308，`flex: 1, overflowY: auto, display: flex, flexDirection: column`）
- `DirectorFlow` 消息容器 style（行~5530，同样的 flex 布局）

**修改方案**（优先级从高到低）：
- **方案A（优先）**：不修改 CSS，仅依赖 P1 的自动滚动到底部。消息少时消息在顶部，但自动滚动把视图滚到底部，视觉上消息在底部。与标准对话（ChatView）行为一致。
- **方案B（备选）**：消息容器添加 `justifyContent: "flex-end"`。风险：`flex-end` + `overflow-auto` 在某些浏览器中内容超出时无法滚动到顶部（已知 CSS 问题），需测试验证。
- **方案C（不推荐）**：`flex-direction: column-reverse`，需反转消息数组顺序，复杂度高。

**概率评估**：方案A 90%（与标准对话一致，仅需 P1 自动滚动正常工作）；方案B 70%（有 CSS 兼容性风险）

**测试标准**：
- 消息数量少时，消息贴在容器底部（非顶部）
- 消息数量多时，新消息在底部，自动滚动到底部
- 向上滚动查看历史时，不被自动滚动打断（仅新消息时滚动）

### P8：总监设置选项扩充
**现象**：当前总监设置弹窗只有"自动转发"一个开关，缺少总监职责配置选项。

**用户需求**（之前对话明确提到）：
- 语言规范整理（对用户输入进行语言规范化）
- 上下文记忆（维护会话上下文摘要）
- 执行逻辑分析（分析用户意图，决定执行路径）
- 模型路由（根据任务类型选择模型）
- 分支路由（决定是否创建新分支）
- 本地模型配置（Ollama 端点 + 模型名，用于本地处理省 token）
- 允许增加/删除职责项

**涉及函数/变量**：
- `DirectorView` 设置弹窗（行~7340，当前只有 autoForward 复选框）
- `directorStore.config`（当前只有 `autoForward` 字段）
- `directorProcessMock`（根据 config 决定处理逻辑）
- `saveDirectorStore` / `loadDirectorStore`（持久化 config）

**修改方案**：
1. 扩展 `directorStore.config`，新增 `duties` 数组（职责项列表，每项含 id/name/enabled/description）
2. 设置弹窗改为可配置职责列表，支持启用/禁用、添加、删除
3. 本地模型配置项（endpoint + modelName）
4. `directorProcessMock` 根据启用的职责项执行对应处理
5. 持久化扩展后的 config

**概率评估**：70%（功能明确，但实现量较大，需分阶段）

**测试标准**：
- 设置弹窗显示职责列表，每项可启用/禁用
- 可添加新职责项，可删除职责项
- 本地模型配置可编辑端点和模型名
- 设置变更后持久化，重启后保留
- 启用的职责项在总监处理时生效

### P9：总监读取对话大模型返回信息进行审核
**现象**：当前总监只处理用户输入并转发，不读取对话大模型的返回信息，不对返回结果进行审核。

**用户需求**（之前对话明确提到）：
- 对话大模型返回消息后，总监自动读取返回内容
- 总监对返回内容进行审核（整理、总结、提取关键信息、判断是否需要追问）
- 审核结果添加到总监消息流中
- 用户可查看总监审核意见

**涉及函数/变量**：
- `useSession`（订阅对话消息变化，`s.chat.nodes`）
- `DirectorView`（需添加 useEffect 监听对话消息变化）
- `directorStore.addMessage`（添加审核结果到总监流）
- `directorProcessMock`（新增审核处理逻辑）

**修改方案**：
1. DirectorView 中添加 useEffect，订阅 `useSession((s) => s.chat.nodes)` 变化
2. 当检测到新的 assistant 消息时，调用总监审核处理函数
3. 审核处理函数：提取返回内容、生成审核摘要、添加到总监消息流
4. 审核结果可配置（在 P8 设置中启用/禁用"对话返回审核"职责）

**概率评估**：60%（需研究 useSession 在 DirectorView 中的订阅时机，以及如何区分新消息和历史消息）

**测试标准**：
- 对话大模型返回消息后，总监消息流中出现审核结果
- 审核结果包含返回内容摘要和关键信息
- 可在设置中启用/禁用此功能
- 不影响正常对话流程
