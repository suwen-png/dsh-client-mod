## 一、架构总览（用户愿景解析）

### 1.1 核心定位

整个软件是一个**大总监统治体系**，本质是联邦式多项目管理 + 智能路由 + 文档驱动 + 审核闭环。

```
┌─────────────────────────────────────────────────────────────┐
│                    主总监（全局统治层）                        │
│              主记忆 · 全局路由 · 审核标准 · 跨项目调度          │
├──────────────┬──────────────┬──────────────────────────────┤
│  项目A记忆    │  项目B记忆    │  项目C记忆（分记忆）           │
│  定位/目标    │  定位/目标    │  定位/目标                    │
│  文档/对话    │  文档/对话    │  文档/对话                    │
│  决策/待办    │  决策/待办    │  决策/待办                    │
├──────┬───────┤              │                              │
│子项目│子项目  │              │                              │
│ A-1  │ A-2   │              │  ← 允许无限嵌套拆分            │
├──┬───┤       │              │                              │
│A1│A1-1│      │              │                              │
└──┴───┴───────┴──────────────┴──────────────────────────────┘
```

### 1.2 四大核心机制

| 机制 | 核心 | 实现路径 |
|------|------|---------|
| **嵌套记忆体系** | 主记忆→项目记忆→子项目记忆，无限拆分 | IndexedDB分层存储，每个记忆层独立文档/对话/决策 |
| **智能路由** | 单一对话入口，自动理解意图，分发到对应项目/子项目 | 意图理解→项目匹配→任务拆分→下发执行 |
| **文档驱动** | 所有沟通/方案/执行/审核都落实文档 | 沟通→对话记录，方案→方案文档，执行→任务清单，审核→审核文档 |
| **审核闭环** | 方案→执行→审核，标准=满足客户核心需求 | 前置审核（方案是否满足需求）+ 后置审核（执行是否达标） |

### 1.3 最终效果（用户愿景）

> 只有一个对话，我和这个对话交流，自动判断我说的内容应该放入哪些项目，甚至一次输出包含多个对话，需要理解我要做什么，然后不断下发或者直接找到对应的对话框。

**交互流程：**
```
用户输入（可能包含多个任务/多个项目）
    ↓
意图理解（这是什么？属于哪个项目？包含几个任务？）
    ↓
项目匹配（找到对应项目/子项目记忆）
    ↓
任务拆分（一次输入拆分为多个子任务）
    ↓
下发执行（路由到对应项目对话，或创建新子项目）
    ↓
方案生成（每个任务生成方案文档）
    ↓
前置审核（方案是否满足客户核心需求？）
    ↓
执行落实（方案执行，记录到任务清单）
    ↓
后置审核（执行结果是否达标？）
    ↓
文档归档（所有沟通/方案/执行/审核落实文档）
```

## 一补、总监-执行者分离与分支分派架构（最终愿景）

### 1A.1 核心原则

| 原则 | 说明 |
|------|------|
| **每对话一总监** | 每个对话/项目都有自己的总监，不是全局一个总监 |
| **沟通执行分离** | 总监负责沟通（方案/审核），执行者负责执行，两者严格分离 |
| **总监不执行** | 总监只做方案制定、任务分派、多维度审核，不亲自执行具体任务 |
| **执行者按方案执行** | 执行者严格按总监制定的方案约束执行，确保满足总监方案 |
| **总监核心认知** | 总监对项目/对话整个核心有完整了解，才能保证不偏差 |

### 1A.2 总监-执行者协作流程

```
用户输入
    │
    ▼
┌─────────────────────────────────────────────┐
│  总监（沟通层）                               │
│  1. 理解需求：拆解用户核心诉求                 │
│  2. 制定方案：输出执行约束（目标/步骤/标准）   │
│  3. 方案审核：确保方案符合客户核心诉求          │
│  4. 任务分派：派出不同执行分支                 │
└──────────────┬──────────────────────────────┘
               │ 分派任务（带方案约束）
               ▼
┌──────────┬──────────┬──────────┬──────────┐
│ 执行分支1  │ 执行分支2  │ 执行分支3  │ 执行分支4  │
│ (执行者)   │ (执行者)   │ (执行者)   │ (执行者)   │
│ 按方案执行  │ 按方案执行  │ 按方案执行  │ 按方案执行  │
│ 只了解自己  │ 只了解自己  │ 只了解自己  │ 只了解自己  │

      └──────────┴────┬─────┴──────────┘
                      ▼
              执行结果汇总
                      │
                      ▼
┌─────────────────────────────────────────────┐
│  总监（审核层）— 多维度审核                   │
│  ✅ 需求满足度：是否满足客户核心需求            │
│  ✅ 方案符合度：是否符合总监制定的方案约束       │
```

### 1A.3 分支分派机制

总监可以分派出不同执行分支。**当前页面实现方式：用多个对话当做分支**（每个对话是一个执行分支，加载对应的标准智能体）。

**终极目标：流程图样式**（节点图展示分支分派关系、执行状态、结果流向），当前页面无法支撑，留待后续阶段（V10+）实现。

**分支类型（对应标准智能体）：**

| 分支类型 | 对应智能体 | 职责 | 上下文范围 | 推荐模型 |
|---------|-----------|------|-----------|---------|
| **代码执行分支** | 代码智能体 | 代码编写、调试、重构 | 项目核心认知 + 代码相关上下文（需求/技术栈/代码规范） | deepseek-coder / 本地代码模型 |
| **文档执行分支** | 文档智能体 | 文档撰写、整理、润色 | 项目核心认知 + 文档相关上下文（目标/格式/参考资料） | deepseek-chat / 本地通用模型 |
| **调研执行分支** | 调研智能体 | 信息检索、分析、总结 | 项目核心认知 + 调研相关上下文（问题/范围/数据源） | deepseek-reasoner / 联网搜索模型 |
| **测试执行分支** | 测试智能体 | 测试用例编写、执行、验证 | 项目核心认知 + 测试相关上下文（需求/测试标准/环境） | 测试专用模型 / 本地模型 |
| **审核执行分支** | 审核智能体 | 代码审查、文档审核、质量检查 | 项目核心认知 + 审核相关上下文（标准/检查清单/被审核内容） | deepseek-reasoner |

**上下文原则（不绝对隔离）：**
- 每个分支都加载**项目核心认知**（定位/目标/核心需求/决策历史），保证对项目有基本了解，不会跑偏
- 在核心认知基础上，加载分支专属上下文（代码/文档/调研/测试相关），最大程度利用上下文
- 不传递与分支任务无关的信息，避免上下文污染和浪费
- 分支之间不直接通信，所有结果汇总给总监
- 总监负责上下文的裁剪、分配和汇总

**智能体 = 执行规范保证：**
- 总监页最上面的"智能体"区域展示可用的标准智能体
- 每个智能体定义了对应分支的执行规范、标准、检查清单
- 创建分支（对话）时自动加载对应智能体的规范
- 智能体保证对应执行的规范和标准性

**当前页面实现（V9）：**
- 总监页顶部"智能体"区域：展示标准智能体列表
- 点击智能体 → 创建对应的对话（分支），加载该智能体规范
- 多个对话（分支）并行执行
- 总监对话区负责分派任务、审核结果

**后续阶段（V10+）：**
- 流程图样式的分支可视化
- 分支执行状态实时展示
- 分支结果流向图
- 分支依赖关系管理

### 1A.4 模型路由机制

**核心原则：不同模型做自己擅长的事情，相同模型走同一个分支，确保上下文不重复传递。**

**模型能力矩阵：**

| 模型 | 擅长领域 | 适用分支 | 上下文共享 |
|------|---------|---------|-----------|
| deepseek-reasoner | 复杂推理、方案设计、逻辑分析 | 调研分支、审核分支 | 同模型分支共享推理上下文 |
| deepseek-coder | 代码编写、调试、重构 | 代码执行分支 | 同模型分支共享代码上下文 |
| deepseek-chat | 通用对话、文档撰写、翻译 | 文档执行分支 | 同模型分支共享通用上下文 |
| 本地模型(qwen2:7b) | 简单任务、预处理、快速响应 | 测试分支、预处理 | 本地模型共享本地上下文 |

**路由策略：**
1. 总监根据任务类型选择最合适的模型
2. 相同模型的多个分支共享同一个模型会话，避免上下文重复传递
3. 不同模型的分支独立会话，上下文隔离
4. 支持动态切换模型（任务复杂度变化时）

**上下文优化：**
- 相同模型走同一个分支/会话，上下文增量传递（只传新增信息）
- 不同模型之间通过总监中转，总监负责信息压缩和转换
- 避免同一上下文在多个模型间重复传递

### 1A.5 总监核心认知体系

总监对项目/对话整个核心的了解，是保证不偏差的基础。

**核心认知维度：**

| 维度 | 内容 | 来源 |
|------|------|------|
| **项目定位** | 项目是什么、目标是什么、当前阶段 | 项目文档 + 对话历史 |
| **核心需求** | 客户最核心的诉求是什么（不是表面需求，是本质需求） | 需求拆解 + 总监理解 |
| **决策历史** | 之前做了什么决策、为什么做、影响是什么 | 决策记录文档 |
| **执行状态** | 各个分支的执行进度、结果、问题 | 分支执行报告 |
| **风险偏差** | 当前有什么风险、是否跑偏、偏差在哪里 | 风险检测 + 总监判断 |
| **约束条件** | 技术约束、时间约束、资源约束、质量标准 | 项目配置 + 方案文档 |

**认知更新机制：**
- 每次对话后更新核心认知
- 每次分支执行完成后更新执行状态
- 每次审核后更新风险偏差
- 核心认知持久化到记忆体系，跨会话保留

### 1A.6 总监其他职能（补充完善）

| 职能 | 说明 |
|------|------|
| **上下文压缩** | 总监负责压缩和管理上下文，确保执行者只看到相关信息，避免上下文过长 |
| **冲突解决** | 多个分支结果冲突时，总监负责裁决，确定最终方案 |
| **优先级调度** | 总监根据任务优先级和依赖关系，调度分支执行顺序 |
| **资源分配** | 总监根据任务复杂度分配模型和计算资源（简单任务用本地模型，复杂任务用云端模型） |
| **学习进化** | 总监从每次执行和审核中学习，优化未来的方案制定和分支分派 |
| **质量门禁** | 总监设定质量标准，执行结果必须通过总监审核才能进入下一环节 |
| **方向校准** | 总监定期检查项目方向，发现偏差及时校准，确保不跑偏 |
| **知识沉淀** | 总监将每次沟通、方案、执行、审核的结果沉淀为文档，形成项目知识库 |

### 1A.7 沟通与执行的严格分离

**沟通层（总监）：**
- 只在总监对话区进行
- 内容：需求讨论、方案制定、任务分派、审核反馈
- 不执行具体任务
- 所有沟通落实为文档（方案文档、审核文档、决策记录）

**执行层（执行者/分支）：**
- 在独立的执行分支中进行
- 内容：按总监方案执行具体任务
- 不参与方案讨论
- 执行过程记录为执行日志
- 执行结果提交给总监审核

**分离的好处：**
- 上下文不污染（沟通上下文 vs 执行上下文分离）
- 职责清晰（总监把控方向，执行者专注执行）
- 审核独立（总监审核自己不参与执行的结果，更客观）
- 可并行（多个执行分支同时执行，总监统一调度）

### 1A.8 标准智能体规范（5类）

每个分支加载对应的标准智能体，智能体定义执行规范、标准、检查清单，保证对应执行的规范和标准性。

| 智能体 | 职责 | 执行标准 | 检查清单 | 推荐模型 |
|--------|------|---------|---------|---------|
| **代码智能体** | 代码编写、调试、重构 | 1.遵循项目编码规范 2.函数有注释 3.异常处理完整 4.无硬编码密钥 | 1.命名是否规范 2.是否有语法错误 3.边界条件是否处理 4.是否有安全漏洞 | deepseek-coder |
| **文档智能体** | 文档撰写、整理、润色 | 1.结构清晰 2.术语统一 3.格式规范 4.内容准确 | 1.是否覆盖所有要点 2.格式是否符合规范 3.是否有错别字 4.引用是否准确 | deepseek-chat |
| **调研智能体** | 信息检索、分析、总结 | 1.来源可靠 2.数据准确 3.分析客观 4.结论有据 | 1.信息来源是否可信 2.数据是否最新 3.分析是否全面 4.结论是否有依据 | deepseek-reasoner |
| **测试智能体** | 测试用例编写、执行、验证 | 1.覆盖正常/异常/边界 2.用例可重复 3.结果可验证 4.缺陷可追踪 | 1.是否覆盖所有场景 2.用例是否可执行 3.预期结果是否明确 4.缺陷是否记录 | 测试专用模型/本地 |
| **审核智能体** | 代码审查、文档审核、质量检查 | 1.对照标准逐项检查 2.问题有具体位置 3.建议可操作 4.结论明确 | 1.是否对照检查清单 2.问题描述是否具体 3.整改建议是否可操作 4.结论是否明确 | deepseek-reasoner |

### 1A.9 多维度审核检查清单（6维度）

执行完成后总监进行多维度审核，标准=满足客户核心需求。

| 维度 | 检查项 | 通过标准 |
|------|--------|---------|
| **需求满足度** | 核心需求覆盖 | 用户必做项100%覆盖，无遗漏 |
| | 可选需求处理 | 可选项明确标注已实现/未实现/延后 |
| | 约束条件遵守 | 用户限制条件、边界、禁止项全部遵守 |
| **方案符合度** | 方案约束遵守 | 执行符合总监制定的方案约束（目标/步骤/标准） |
| | 范围一致 | 执行范围与方案一致，无遗漏/无超范围 |
| | 变更可追溯 | 执行中如有调整，已记录并说明原因 |
| **质量达标度** | 代码/文档质量 | 符合对应智能体的执行标准和检查清单 |
| | 功能可验证 | 核心功能可运行/可验证，非纸面实现 |
| | 性能可接受 | 无明显性能问题（响应时间/资源占用） |
| **风险控制** | 无新增Bug | 执行未引入新的逻辑错误、回归问题 |
| | 安全风险 | 无硬编码密钥、注入风险、权限越界 |
| | 已知问题记录 | 遗留问题明确记录，有后续计划 |
| **完整性** | 无遗漏 | 方案中所有任务都已执行，无遗漏 |
| | 文档完整 | 沟通/方案/执行/审核都已落实文档 |
| | 边界覆盖 | 边界值、极值、空值场景已处理 |
| **一致性** | 方向一致 | 与项目整体方向、核心需求一致，无偏差 |
| | 规范一致 | 符合项目架构/编码/文档/业务规范 |
| | 决策一致 | 与历史决策、项目记忆一致，无冲突 |

### 1A.10 分支分派与汇总机制

**分派机制（总监→分支）：**
1. 总监在总监对话区讨论需求，制定方案约束
2. 总监点击对应智能体（代码/文档/调研/测试/审核），创建分支对话
3. 分支对话自动加载：项目核心认知 + 对应智能体规范 + 任务描述 + 方案约束
4. 分支对话独立执行，不参与方案讨论

**汇总机制（分支→总监）：**
1. 分支执行完成后，在分支对话中标记"执行完成"，提交执行结果
2. 总监对话区收到分支完成通知（含分支名称/执行摘要/结果链接）
3. 总监点击分支结果，查看详细执行内容
4. 总监进行多维度审核（6维度检查清单）
5. 审核通过→归档文档；审核不通过→打回分支重执行（带审核意见）

**分支间通信：**
- 分支之间不直接通信
- 所有跨分支信息通过总监中转
- 总监负责信息压缩、转换、分发

### 1A.11 异常处理与降级方案

| 异常场景 | 处理方式 | 降级方案 |
|---------|---------|---------|
| 分支执行失败 | 总监收到失败通知，查看错误日志 | 降级到总监对话直接执行，或分派给其他分支 |
| 多分支结果冲突 | 总监裁决，确定最终方案 | 标记冲突，请求用户确认 |
| 智能体规范加载失败 | 使用默认通用规范 | 提示用户手动配置规范 |
| 项目文档读取失败 | 使用空项目认知，提示用户补充 | 降级到通用模式，不加载项目特定信息 |
| 模型调用失败 | 切换到备用模型 | 降级到本地模型，或提示用户检查网络 |
| 分支数量过多 | 总监合并相似分支，或暂停低优先级分支 | 限制最大并行分支数（默认5个） |

### 1A.12 分支状态机

```
待分派 → 执行中 → 待审核 → 已完成
  ↓         ↓         ↓
  取消    失败      打回重执行
                    ↓
                  执行中（循环）
```

| 状态 | 说明 | 触发条件 | 可执行操作 |
|------|------|---------|-----------|
| 待分派 | 分支已创建，等待任务分派 | 总监创建分支对话 | 分派任务/取消 |
| 执行中 | 分支正在执行任务 | 总监分派任务 | 查看进度/暂停/取消 |
| 待审核 | 分支执行完成，等待总监审核 | 分支标记执行完成 | 审核通过/打回重执行 |
| 已完成 | 审核通过，任务完成 | 总监审核通过 | 查看结果/归档 |
| 失败 | 分支执行失败 | 执行过程中出错 | 重试/取消/降级 |
| 取消 | 分支被取消 | 总监取消分支 | 无（终态） |

### 1A.13 项目核心认知自动提取机制

**提取流程：**
1. 项目初始化时，读取项目文档（`docs/00-统筹入口/`）
2. 从总统筹入口文档提取：项目定位、目标、当前阶段
3. 从项目总需求清单提取：核心需求、优先级
4. 从已完成任务清单提取：决策历史、执行状态
5. 从工作快照提取：当前进度、风险、下一步
6. 汇总为项目核心认知，存储到记忆体系

**核心认知内容：**
- 项目定位：项目是什么、解决什么问题
- 核心目标：项目的最终目标、关键里程碑
- 当前阶段：当前处于什么阶段、做到哪了
- 核心需求：客户最核心的诉求（不是表面需求，是本质需求）
- 决策历史：之前做了什么决策、为什么做
- 风险偏差：当前有什么风险、是否跑偏
- 约束条件：技术约束、时间约束、资源约束

**更新机制：**
- 每次总监对话后更新核心认知
- 每次分支审核完成后更新执行状态
- 每次项目文档变更后重新提取
- 核心认知持久化到记忆体系，跨会话保留

## 二、记忆体系设计（嵌套逻辑）

### 2.1 三层记忆结构

```typescript
interface MemoryNode {
  id: string;                    // 记忆节点ID
  name: string;                  // 项目/子项目名称
  level: "global" | "project" | "subproject";  // 层级
  parentId: string | null;       // 父记忆节点ID（null=全局）
  children: string[];            // 子记忆节点ID列表
  
  // 项目元数据
  meta: {
    positioning: string;         // 定位
    goal: string;                // 目标
    currentPhase: string;        // 当前阶段
    createdAt: number;
    updatedAt: number;
  };
  
  // 文档索引（该记忆层下的所有文档）
  docs: {
    docId: string;
    docName: string;
    docType: "overview" | "plan" | "execution" | "review" | "decision" | "memory";
    path: string;
    updatedAt: number;
  }[];
  
  // 对话历史（该记忆层下的所有对话）
  conversations: {
    conversationId: string;
    title: string;
    lastMessage: string;
    lastTime: number;
    messageCount: number;
  }[];
  
  // 决策记录
  decisions: {
    decisionId: string;
    title: string;
    reason: string;
    madeAt: number;
    status: "active" | "superseded" | "rejected";
  }[];
  
  // 待办/路线图
  todos: {
    todoId: string;
    title: string;
    priority: "high" | "medium" | "low";
    status: "pending" | "in-progress" | "done" | "blocked";
    dueDate?: number;
  }[];
  
  // 风险/偏差
  risks: {
    riskId: string;
    title: string;
    level: "high" | "medium" | "low";
    status: "open" | "mitigated" | "closed";
    description: string;
  }[];
}
```

### 2.2 记忆存储方案

- **存储引擎**：IndexedDB（`dsh-memory-db`）
- **Store设计**：
  - `memoryNodes`：所有记忆节点（keyPath: id）
  - `memoryDocs`：所有文档内容（keyPath: docId）
  - `memoryConversations`：所有对话消息（keyPath: messageId，index: conversationId）
  - `memoryDecisions`：所有决策记录（keyPath: decisionId）
  - `memoryTodos`：所有待办（keyPath: todoId）
  - `memoryRisks`：所有风险（keyPath: riskId）
- **嵌套查询**：通过parentId递归查询子节点，构建记忆树

### 2.3 记忆隔离与共享

- **隔离**：每个项目/子项目的文档、对话、决策、待办、风险相互隔离
- **共享**：全局总监记忆可访问所有项目记忆，用于跨项目调度和全局路由
- **继承**：子项目继承父项目的定位/目标/审核标准，但可以覆盖

## 四、文档驱动与审核闭环

### 4.1 文档类型体系

| 文档类型 | 触发时机 | 内容 | 存储位置 |
|---------|---------|------|---------|
| **沟通记录** | 每次对话 | 对话消息、意图、决策 | memoryConversations |
| **方案文档** | 任务执行前 | 目标、步骤、风险、回滚 | memoryDocs (type=plan) |
| **执行记录** | 任务执行中 | 执行步骤、结果、问题 | memoryDocs (type=execution) |
| **审核文档** | 方案执行前后 | 审核标准、检查项、结论 | memoryDocs (type=review) |
| **决策记录** | 关键决策时 | 决策内容、原因、影响 | memoryDecisions |
| **核心记忆** | 项目理解更新 | 定位、目标、阶段、关键认知 | memoryDocs (type=memory) |

### 4.2 审核闭环

```
用户需求
    ↓
┌──────────────┐
│ 方案生成      │ ← 沟通讨论，生成方案文档
└──────┬───────┘
       ↓
┌──────────────┐
│ 前置审核      │ ← 对照客户核心需求审核
│              │   - 是否满足核心需求？
│              │   - 是否有遗漏？
│              │   - 风险是否可控？
└──────┬───────┘
       ↓ （通过）
┌──────────────┐
│ 执行落实      │ ← 按方案执行，记录执行过程
└──────┬───────┘
       ↓
┌──────────────┐
│ 后置审核      │ ← 对照预期效果审核
│              │   - 是否达到预期？
│              │   - 是否引入新问题？
│              │   - 是否需要调整？
└──────┬───────┘
       ↓
┌──────────────┐
│ 文档归档      │ ← 所有沟通/方案/执行/审核落实文档
└──────────────┘
```

### 4.3 审核标准（统一）

所有审核的唯一标准：**是否满足客户的核心需求**。

审核检查项：
1. 客户核心需求是什么？（从项目记忆中提取）
2. 方案/执行是否覆盖了所有核心需求？
3. 是否有偏离核心需求的部分？
4. 是否有未考虑的风险？
5. 客户体验是否达标？

## 四补、多方案对比与选择

### 方案A：单项目驾驶舱（选定方案）

**描述**：先实现单项目驾驶舱，总监页展示项目总览+导航+记忆+对话，为后续宏大架构打基础。

**优点**：
- 范围可控，一次执行可完成
- 风险低，不破坏现有功能
- 为后续V10-V13预留扩展点
- 用户可快速验证核心体验

**缺点**：
- 不支持多项目切换
- 不支持嵌套子项目
- 分支分派用多对话模拟，不是真正的流程图

**适用场景**：V9阶段，先验证单项目驾驶舱体验

### 方案B：全架构一次性实现

**描述**：一次性实现完整的总监统治架构（多项目+嵌套子项目+智能路由+流程图分支+全自动审核）。

**优点**：
- 一步到位，用户体验完整
- 不需要分阶段迭代

**缺点**：
- 范围过大，一次执行无法完成
- 风险高，可能破坏现有功能
- 编译产物修改复杂度高，调试困难
- 用户无法中途验证，容易跑偏

**适用场景**：不推荐，风险过高

### 方案C：先做分支分派+智能体，再做驾驶舱

**描述**：先实现多对话分支+智能体规范，再做项目驾驶舱。

**优点**：
- 优先解决用户最关心的"分支分派"问题
- 智能体规范可独立验证

**缺点**：
- 没有项目驾驶舱，分支缺少项目上下文
- 用户体验不完整
- 需要两次大改，总工作量更大

**适用场景**：如果用户最优先需要分支分派功能

### 方案选择理由

**选定方案A（单项目驾驶舱）**，理由：
1. **风险可控**：单项目范围，不破坏现有功能
2. **可验证**：用户可快速验证核心体验，及时反馈
3. **扩展性**：为后续V10-V13预留扩展点，不阻塞宏大架构
4. **符合分阶段路线图**：V9→V10→V11→V12→V13，逐步实现
5. **编译产物修改限制**：直接修改lib/client.js，范围过大容易出问题

**风险评估与应对**：
| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|---------|
| V9范围过大，一次执行不完 | 中 | 中 | 按优先级执行，P0必须完成，P1/P2可延后 |
| 编译产物修改引入Bug | 中 | 高 | 每次修改后语法检查，apply前快照，出问题可回滚 |
| 项目文档自动提取不准确 | 高 | 低 | 提供手动编辑入口，自动提取结果可修改 |
| 多对话分支体验不流畅 | 中 | 中 | V9先做基础机制，V10+优化为流程图 |

### 9.2 任务详细说明

**T1：记忆体系IndexedDB**
- 输入：记忆体系数据结构设计（§二）
- 输出：IndexedDB数据库`dsh-memory-db`，含6个store（memoryNodes/memoryDocs/memoryConversations/memoryDecisions/memoryTodos/memoryRisks），CRUD接口
- 验收标准：①数据库可创建 ②数据可读写 ③数据持久化（退出重开不丢失） ④与现有`dsh-director-db`不冲突
- 依赖：无

**T2：项目文档读取与解析**
- 输入：项目文档路径（`docs/00-统筹入口/`）、核心认知提取规则（§1A.13）
- 输出：项目核心认知对象（定位/目标/阶段/核心需求/决策历史/风险/约束）
- 验收标准：①能读取总统筹入口文档 ②能提取定位/目标/阶段 ③提取结果可手动编辑 ④提取失败有降级提示
- 依赖：T1

**T3a：总监页布局骨架**
- 输入：V8现有总监页布局、V9布局设计（§五）
- 输出：总监页三栏结构（顶部固定栏+上面框+对话区+下面框+a-2），flex布局，可伸缩
- 验收标准：①顶部固定不随滚动移动 ②上面框/下面框可伸缩折叠 ③对话区正常滚动 ④不破坏现有a-1/a-2对话功能
- 依赖：无

**T3b：项目总览卡片**
- 输入：T2项目核心认知、总览卡片设计（§5.3）
- 输出：顶部下方项目总览卡片（定位/目标/阶段/进度/风险数/待办数）
- 验收标准：①展示6项信息 ②数据来自T2核心认知 ③点击可展开详情 ④无数据时有占位提示
- 依赖：T3a, T2

**T4：上面框项目导航**
- 输入：T2项目文档列表、导航设计（§5.4）
- 输出：上面框三个Tab（文档树/路线图待办/关键文件），可点击跳转
- 验收标准：①文档树展示项目文档结构 ②路线图展示待办清单 ③关键文件展示常用文件 ④点击文件在a-2打开
- 依赖：T3a, T2

**T5：下面框总监记忆**
- 输入：T1记忆体系数据、记忆面板设计（§5.5）
- 输出：下面框三个Tab（核心记忆/决策记录/偏差风险），可查看/编辑
- 验收标准：①核心记忆展示项目核心认知 ②决策记录展示历史决策 ③偏差风险展示风险提醒 ④数据持久化
- 依赖：T3a, T1

**T6：智能体区域**

- 验收标准：①展示5个智能体 ②每个智能体有名称/职责/模型 ③点击有反馈 ④hover显示详细规范
- 依赖：T3a

**T7：多对话分支机制**
- 输入：T6智能体列表、分支机制设计（§1A.10）、分支状态机（§1A.12）
- 输出：点击智能体→创建对应对话分支（新对话窗口/tab），自动加载项目核心认知+智能体规范+任务模板，分支状态管理
- 验收标准：①点击智能体创建分支对话 ②分支加载核心认知+规范 ③分支状态可追踪（待分派/执行中/待审核/已完成） ④多分支可并行 ⑤分支结果可汇总到总监

- 验收标准：①三种模式可切换 ②对话模式正常聊天 ③文档编辑模式可查看/编辑/保存 ④项目详情模式展示项目核心认知 ⑤切换不丢失数据
