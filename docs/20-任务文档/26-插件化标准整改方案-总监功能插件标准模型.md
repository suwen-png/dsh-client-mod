## 一、需求理解（解表达 + 提炼诉求）

### 1.1 用户原话拆解

| 层 | 内容 |
|---|---|
| 核心诉求 | 总监功能的开发形态应回归「插件」初衷：独立、可安装、可移植、不与客户端补丁纠缠 |
| 现状认知 | 用户已察觉当前实现是「直接改客户端」（事实正确，见 §二差分） |
| 整改方向 | 按插件开发的**标准模型**重构——即 Harness 官方插件机制（__ModuleLoader__ / slots / 独立包），而非自创形态 |
| 约束 | 已有功能与数据（46/46 回归基线、IDB 记忆库）不得损坏；每阶段可回滚 |

### 1.2 一句话诉求

**把内联在 client.js 里的总监功能抽成独立插件包，把 client.js 补丁减薄到只剩宿主锚点，使总监功能可以像插件一样整体安装、移植、升级。**

## 二、现状差分（实证）

### 2.1 现状清单（代码事实，2026-09-07）

| 维度 | 现状 | 证据 |
|---|---|---|
| 唯一改动文件 | `workspace/@deepseek-ai/dsh-client-ui-conversation/lib/client.js`（1,423,779 B） | status.ps1 / diff.ps1 实测 2026-09-07 |
| 总监 tab 注册 | ✅ 已用 Harness 插槽 API：`slots.register({name:"conversation.view", id:"director"...}, DirectorView)` | client.js:13481–13520（25号文 §3.1） |
| MOD-B 组件实体 | ❌ DirectorView 全部内联在 client.js（:8898+，含 A区/R2/D区/dModal/设置弹层/对话小窗） | 25号文 §三 |
| MOD-A 布局侵入 | ❌ 直接修改 ChatView 内部渲染结构（:7087+，左栏总监小窗+拖拽条） | 25号文 §二 |
| 状态与数据 | ❌ directorStores / directorLayoutStore / IDB CRUD（memoryCore 等store）全在 client.js | 25号文 §3.6 / ADR-006 |
| 样式 | ❌ 令牌与内联样式随组件内联 | V9.5 令牌化记录（22号文） |
| 部署形态 | 「类插件」：整目录复制 + apply.ps1 文件级替换（24号文 §七），但**功能本身不可独立安装** | 24号文 |

### 2.2 Harness 标准插件模型（目标基准，细节以 P0 勘察为准）

| 机制 | 说明 | 来源 |
|---|---|---|
| `window.__ModuleLoader__.load({ id, factory })` | 插件注册入口 | 24号文 §三.6；dsh-client-runtime 包职责（config.json） |
| `slots.register / slots.inject` | 视图与 UI 扩展点 | 同上；dsh-client-ui-slots 包职责 |
| 独立 npm 包 + 静态资源通道 | 插件为独立包，经后端 HTTP 或本地物化加载 | 24号文 §三.6 |
| 「插件物化」 | **config.json 明确 dsh-client-web 职责含「插件物化」→ 原生存在插件落盘/加载通道，P0 必须勘察清楚** | config.json target_packages |

### 2.3 差分结论

**注册层已经是插件式（slots.register），组件层完全不是。** 整改本质 = 把「组件实体 + 状态 + 样式 + 数据」从 client.js 迁入独立插件包，client.js 只留：①插件加载引导（若官方通道需宿主引导）②MOD-A 布局锚点（若插槽不可达）。

## 三、目标架构

```
dsh-client-mod\
├─ dsh-director-plugin\              ← 新增：总监功能独立插件包（可整体复制安装）
│  ├─ package.json                   ← 包清单（id/name/version/harness 兼容区间）
│  ├─ src\
│  │  ├─ index.js                    ← 入口：__ModuleLoader__.load({id:'dsh-director-plugin', factory})
│  │  ├─ director-view.js            ← MOD-B 整页（迁自 client.js :8898+）
│  │  ├─ chat-panel.js               ← MOD-A 小窗组件（可迁移部分）
│  │  ├─ stores.js                   ← directorStores / directorLayoutStore（迁自 :6440+）
│  │  ├─ idb.js                      ← 记忆库 CRUD（store 名不变，数据无损）
│  │  ├─ styles.js                   ← 令牌 + 样式（V9.5 令牌体系随迁）
│  │  └─ utils.js                    ← __dshDebug / toast / 分支创建等工具
│  ├─ build\build.mjs                ← esbuild 打包：单文件 bundle，external=['react','react-dom','react-jsx-runtime',宿主chunk]
│  ├─ dist\bundle.js                 ← 产物（部署单元）
│  └─ README.md                      ← 安装/卸载/移植说明（插件标准模型交付件）
├─ workspace\...\lib\client.js       ← 补丁层，目标仅剩：
│   ① 插件加载引导（若官方通道需要宿主侧触发）
│   ② MOD-A 最小布局锚点（若 conversation 面板插槽不可达）
│   ③ 现有 slots.register director tab 若必须宿主侧注册则保留一行指向插件
└─ scripts\apply.ps1 / restore.ps1 / deploy.ps1 ← 扩展：插件 dist 部署与回收
```

**关键约束**：bundle 严禁打入第二份 React——必须通过 external + 宿主 require 复用同一实例（双实例是编译产物改造的头号崩溃源，ADR-001 风险的插件版）。

## 五、风险与回滚

| 风险 | 等级 | 缓解 |
|---|:---:|---|
| 官方插件通道不存在或不可用（物化机制仅服务内置包） | 中 | P0 第一时间勘察；降级方案 =「thin-loader patch」模式：client.js 只留一个 require+load 引导（约10行），插件实体仍独立——仍达成可移植目标 |
| React 双实例导致崩溃 | 高 | esbuild external 全量宿主模块；spike 先验证 |
| 迁移期间功能回归 | 中 | 每阶段独立快照 + git 分支 `refactor/plugin-model`；46/46 基线不劣化才进下阶段 |
| client.js 升级（rc.12）覆盖补丁 | 低 | 锚点契约文档化；插件实体不受宿主升级影响（本次整改的核心收益） |
| IDB 数据丢失 | 高 | store 名与版本号不变；T-PLUG-009 专项验证；apply 前自动快照照旧 |

**回滚**：每阶段 apply 前自动快照；git revert；restore.ps1 一键复原；spike 失败即退回现状（现状本身可正常运行）。

## 六、验收标准（做到什么程度算完成）

1. `dsh-director-plugin/` 作为整体单元，按 README 可在另一台电脑安装生效（复制→部署→重启）。

3. Playwright CDP 回归 46/46 通过；原对话/轨迹/侧边栏功能无损。
4. IDB 记忆数据迁移无损（条数抽查一致）。
5. 交付三件套：插件包 + 锚点契约文档 + 安装 README。
