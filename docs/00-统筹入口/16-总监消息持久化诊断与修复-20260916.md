# 16 · 总监消息「一个消息都没有」——诊断与修复

> **轮次**：第二十二轮 ｜ **日期**：2026-09-16 ｜ **触发**：用户原话
> 「总监消息没有持久化么 为什么一个消息都没有」
> **一句话结论**：**不是没持久化**（通道实测完好），是**验收闸门自己把库清空了**，
> 叠加**OPFS 单文件串桶**与**写消息触点过窄**三件事。

---

## 一 · 结论先行

| # | 真因 | 关键证据 | 性质 |
|:-:|:-----|:---------|:-----|
| **D4** | **验收闸门 D 段把 `directorConversations` 全表清空，跑完不还原** | 连跑 10 轮验收后全表 **0 条**，而 `directorNodes` 有 **458 条** ⇒ 不是"库打不开"，是**消息被清干净** | 🔴 **闸门缺陷**（违反纪律 15：会写盘的闸门段必须快照→还原） |
| **D5** | **OPFS 是单文件 `director-store.json`，不分桶** ⇒ `loadDirectorStore(sessionId)` 命中缓存**不校验归属** | 多会话互相覆盖 / **串桶**（A1 的消息可能出现在 A2） | 🔴 产品缺陷 |
| **D6** | **写消息的触点只有 4 个动作**（统筹 / 派发 / 回收 / 运行总监链） | 在原生框写内容后点「登记为流转」**只写 flow、不写消息** ⇒ 用户手动做的事不留痕 | 🟡 触点窄（与用户预期不符） |

**通道完好性实测**（决定性）：点一次「统筹」⇒ `总监消息 0 → 1`、库计数 `0 → 1`（2.5 s 内完成）。
⇒ **写入、计数、界面刷新三段全通** —— 坏的不是持久化，是**"谁把数据清掉了"**。

## 三 · 修复

### F1 · 闸门不许破坏用户数据（**D4**，纪律 15）

`scripts/verify-novel-split.mjs` D 段新增：
1. **快照**（清除前）：读全表，记下条数 + 取一条**真实**消息的 `messageId` 作正对照样本；
2. 清除 → 原有断言**一条不改**；
3. **还原**：调产品侧 `restoreDirectorMessages()`；
4. **哨兵收尾**：把闸门自己写的 `gate-sentinel-*` 定向删掉（不留在用户表里）。

| 编号 | 判据 | 反例上会不会也通过 |
|:-----|:-----|:-------------------|
| `NS-6l` | 插件命名空间下的**用户数据键**组数前后不变（🔴 第 22 批起**排除备份槽** —— 它由「清除」自己产生，算进去会让判据在**正确行为**上报红，实测 `9 → 10`） | 会（什么都没做时也相等）⇒ 由 NS-6l2/6p 兜住 |
| `NS-6l2` | **清除必须留下退路**：备份槽存在、条数 == 本次被清条数、且界面 `data-backup-count` 与之一致 | 不会 —— 没写备份就 `exists:0` |
| `NS-6p` | **恢复可从界面点**：真实鼠标命中 `dp-maint-restore`，界面回报 `restored == 被清条数` | 不会 —— 没接界面就只有 API 返回，DOM 为空 |
| `NS-6p2` | 界面读数完整：`restored + skipped === total` **且** `total == 备份条数` | 会（都 0 时相等）⇒ 前提 `restored>0` 由 NS-6p 保证 |
| `NS-6q` | **正对照**：快照里的真实消息，恢复后按 `messageId` **读得回来** | 不会 —— 没恢复就 `MISS` |
| `NS-6r` | **幂等（走界面）**：再点一次「↩ 恢复」⇒ `restored=0 / skipped=total`（有界等待，防读到第一次的旧读数） | 不会 —— 产生副本时 `restored>0` |
| `NS-6s` | 闸门哨兵**不留在用户表里**（还原后定向清掉） | 不会 —— 残留时 `left=1` |

### F2 · 「清除」自带安全网（清得掉，也拿得回）

`src/store/plugin-db.js` 新增（**只增不改**）：

| 符号 | 作用 |
|:-----|:-----|
| `backupDirectorMessages(rows, note)` | 清前把**即将被删的行**写进 `dsh.director.msgs.backup`；写后读回校验；**超限/失败一律 `ok:false` + reason**（不许假装有安全网） |
| `readMessageBackup()` | 读备份；无备份 / 非法 JSON / 结构错 ⇒ **返回 `null` 且不抛**（抛穿会把「恢复」按钮打崩） |
| `pickRestorableRows(existing, rows)` | **纯函数**：丢掉无主键行 + 跳过已在库的 ⇒ 恢复**幂等** |
| `restoreDirectorMessages()` | 按 `messageId` 写回，返回 `{ok,total,restored,skipped,at,reason}` |
| `clearMessageBackup()` | 显式丢弃备份槽 |

`clearDirectorMessages()`：**先备份、再删除**（顺序不可颠倒），返回值新增 `backup` 字段。
`installPluginDbApi` 同步暴露上述符号（调试 / 闸门用）。

### F3 · OPFS 归属校验（**D5**）

`src/store/persist.js`：
- **写**：payload 增 `sid: safeDirectorKey(sessionId)`；
- **读**：OPFS 缓存命中时校验 `parsed.sid === safeDirectorKey(sessionId)`，
  **不符即视为未命中**（打印一行 SKIP 原因），继续走 cookie / localStorage（那两层按 key 分桶，天然隔离）；
- **旧格式（无 `sid`）一律视为未命中** —— 宁可降级到按桶的层，也不把"不知道属于谁"的数据塞给当前会话。

### F4 · 界面：让退路看得见

`src/components/DirectorPage.js`：
- 清除结果 toast **必须带退路**：`· 已备份 N 条，可点「↩ 恢复」还原`；
  备份失败 ⇒ `⚠ 备份未成功（原因），本条不可恢复`；
- 维护区新增按钮 `dp-maint-restore`（`data-has-backup` / `data-backup-count` 供闸门断言），
  文本 `↩ 恢复 N`；
- 新增读数 `dp-restore-result`（`data-restored` / `data-total` / `data-skipped` / `data-ok`）；
- `dp-maint-result` **只增属性**（`data-backup-count` / `data-backup-ok`），原有属性名不动（纪律 7）。

## 四 · 判据

### 4.1 离线（`scripts/test-message-backup.mjs` · **13/13 全绿**）

`MB-1..5` 挑选规则（含 **MB-5 负对照**：`Set` 与数组入参结果一致）·
`MB-6..8` 备份写入（**MB-8 超限 ⇒ `ok:false` 且旧备份原样保留**）·
`MB-9..11` 读/清（**MB-10 非法 JSON 不抛**、**MB-10b 结构错不抛**）·
**`MB-12` 反例校准**（去掉"跳过已存在"后结果必然不同 ⇒ 判据不是空真）。

### 4.2 真机（闸门 D 段 · **106/106 TRUE**）

```
清除前快照（供还原）：{"n":8,"realN":7,"sample":"dm_…"}
清除读数：{"before":8,"removed":8,"ok":"1"}          ← 闸门哨兵 + 用户真实消息一并被清
备份槽：{"exists":1,"count":8,"note":"全表清除（无 nodeId 参数）"} ｜ 界面 data-backup-count=8
真实点击「↩ 恢复」：{"ok":true,"x":453,"y":154} ⇒ 界面读数 {"restored":8,"total":8,"skipped":0,"ok":"1","text":"已恢复 8/8"}
第二次点击后界面读数：{"restored":0,"total":8,"skipped":8,"ok":"1","text":"已恢复 0/8"}
哨兵收尾：{"del":true,"left":0} ｜ 还原后消息数（观测）：8 → 8
```

判据：`NS-6l` `NS-6l2` `NS-6p` `NS-6p2` `NS-6q` `NS-6r` `NS-6s` **全绿**，
**恢复过程全程走真实鼠标**（不是调 API）—— 目标是「**跑完闸门后，用户的消息还在**」，已达成。
