## 一、需求（用户原话 → 我的理解）

### 1.1 用户原话（逐字，本轮唯一指令）

> 现在会话有问题, 重复创建了一百多个会话,
> 我需要的是总监确认完需求之后先考虑目前存在的会话,然后没有才是新建会话
> 不会话都有自己的总监,存在自己的会话总结文档
> 清理无效的多余的文件 和所有会话
> 然后继续反复测试
> 遇到问题就思考怎么处理
> 然后把整个流程记下来,思考如何优化,如何更符合我的想法

### 1.2 拆成五件事（每件都要有产品落点）

| # | 需求 | 落点 | 验收方式 |
|:--|:--|:--|:--|
| R1 | **派发前先复用已有会话**，匹配不到才新建 | `logic/director-reuse.js` + `director-dispatch.js` 改造 | 同一需求连派两次 ⇒ 宿主会话数**不增**（跑程内读数） |
| R2 | **每个会话有自己的总监** | `store/session-dossier.js` 的 `director` 字段 + 导图节点 `data-dossier-role` | 每个分支节点可读出「归谁管」 |
| R3 | **每个会话有自己的会话总结文档** | 同上模块的 `summary` 字段，回收时写入 | 回收后每个会话档案里有独立总结（可读、可回读） |
| R4 | **清理无效的多余文件 + 所有会话** | 文件：临时脚本/无效产物；会话：先实测宿主删除契约 | 清理前后计数对照 + 删后复核 |
| R5 | **继续反复测试 + 记录全流程 + 优化建议** | 真机连跑 ≥3 次 + 本文档 §七/§八 | 连跑不累积 + 文档可读 |

### 1.3 「不会话都有自己的总监」的理解（**我的解读，如有出入请纠正**）

「不会话」判为输入误打，实为「**每个会话**都有自己的总监」。即：

* **每个分支会话 = 一个独立工作单元**，不是共享一个总监的从属物；
* 它要有**自己的总监**（该会话归哪个职能维度管 —— 即 `director.role`）；
* 它要有**自己的总结文档**（该会话做了什么、产出什么 —— 即 `summary`）。

⇒ 落到数据结构就是一个**会话档案** `sessionId → { director, summary, state, at }`，
**一份档案一份文档**，不把 8 条分支的总结挤在一条总监消息里。

### 1.4 隐性需求（用户没说但愿，从动机反推）

| 隐性需求 | 依据 | 落点 |
|:--|:--|:--|
| 要**看得见**会话堆积 | 用户说"重复创建了一百多个会话" —— 他是**看图发现的**（导图 123 个框） | 面板显示会话总数 + 复用/新建计数 |
| 要**能一键清掉** | "清理…所有会话" ⇒ 光自动复用不够，存量得能收拾 | 清理入口（真删 or 屏蔽，取决于 §三 实测） |
| 复用要**接续**不接续 | "先考虑目前存在的会话" —— 是"接着上次干"不是"随便找一条" | 同 (作品, 维度) 多条时取 **`at` 最新**的那条 |
| 闸门**不能再制造会话** | 闸门自己每跑一次也建 8 个（§二 实测）⇒ 是第二个污染源 | 复用生效后闸门重跑自动复用 ⇒ 天然封堵 |

### 2.3 为什么"删不掉"这个前提**必须重新实测**

`src/logic/branch-tree.js:485 hostCapabilities()` 写着：

```js
// 取证：SessionRuntime 成员表里**没有**合并 / 删除 ⇒ 恒 false，菜单据此禁用
merge: false,
remove: false
```

🔴 **这是第 16 批"没实测就下结论"的遗留物** —— 而**同一个文件**在 `probeSessionApi()`
的头注释里亲口批评过这件事：

> 第 16 批我有过一次**没实测就下结论**（把 sessions 说成"无删除契约"）。所以这次先把它列出来再动手

⇒ 本批 R4（清理会话）**必须先跑 `probeSessionApi()`**，拿到 `members[]` 的真实成员表，
确认是否存在 `drop` / `remove` / `delete` / `archive` 及其语义，**再**决定清理手段。
**在实测结果出来之前，任何"无删除契约"的写法都不得进代码与文档。**

#### 2.3.1 E1 实测结果（2026-09-16，逐字取自 `_probe-eval` + 宿主包只读扫描）

**（a）宿主 RPC 面**（`client.ctx.get("sessions").manager.api.sessions` 的方法表）：

```
attachment  cancel  create  fork  history  list  models  prompt  rename  search  selectModel  updateQueue
```

⇒ **确无** `drop` / `delete` / `remove` / `archive`。`hostCapabilities().remove = false` **在 RPC 层是对的** ✅
（第 16 批的结论**结论对、理由错**：它没实测，只是碰巧对了。）

**（b）🔴 但 `rename` 是有的** —— `session.rename(title)` 的实现是：

```js
await this.api.sessions.rename({ sessionId: this.sessionId, title });
```

⇒ 旧结论「宿主无 rename ⇒ 标签只能插件侧覆盖」**是错的**。见 §八 8.2。

**（c）`sessions` 服务里那个 `dropScope` 不是删除会话** ——

```js
dropScope(id, record) { record.fiber.dispose(); record.session.unbindScope(); this.rootCtx.get("slots")?.pruneStoreScope(id); this.manager.drop(id); }
manager.drop(sessionId) { this.sessions.delete(sessionId); }   // ← 只删**本地 Map 缓存**
```

**（d）会话的真身在磁盘**：`~/.dsh/sessions/<工作区>/<会话目录>/`，每会话一个 `session.jsonl.zstd`。
登记在 `~/.dsh/storages/workspace.json`（`tables.workspaces.*.sessionIds` + `global.archivedSessionIds`），
投影缓存 `~/.dsh/storages/session_projcache.json`（`tables.sessions`）。
**会话目录有两种命名纪元**：`session-<uuid>`（117）+ 裸 `<uuid>`（14）—— 只认前缀会漏一半。

⇒ **R4 的结论**：插件侧**无能力**删除宿主会话；能做的、也是正确做法是
**文件级清理 + 先移入 `.trash-<ts>`（可回滚）**，并把三处落点一起清（否则留"点开是空的幽灵会话"）。

## 四、设计

### 4.1 复用匹配（`logic/director-reuse.js` · **纯函数**）

```
输入：dims[]（本次要派的维度）· index（dsh.director.split）· aliveIds（宿主现存会话）· name（作品名）
输出：每条维度一个决定 { dim, action: "reuse"|"create", sessionId?, why }

算法：
  ① 建「存活集」alive：aliveIds 里的才算候选
  ② 建「候选表」byKey：index 里每个 entry → key = name + "|" + dim
       · sessionId 不在 alive ⇒ 记 orphan（**不可复用**，且是"无效条目"）
       · 否则入表
  ③ 每条候选按 `at` **降序**（最新在前）
  ④ 逐维度决定：
       cand = byKey[key] 里第一个**未被本批次占用**的
       有  ⇒ action="reuse", why="index-hit"
       无  ⇒ action="create"，why ∈ { no-match | orphan-only | already-used }
  ⑤ used 集合保证**同一批次内一个会话只接一个维度**（防 8 维度抢同一条）
```

**取最新的理由**：用户要的是"接着上次干"。同一 (作品,维度) 有历史多条时，
最老的那条多半是早期脏数据（模型零输出的 `partial`），接上去等于接脏。

**孤儿处置**：`orphan`（索引有、宿主没了）⇒ 顺手从 `dsh.director.split` 里**忘掉**
（`forgetSplits`）。这是"清理无效条目"的产品化落点，且**必须报数**（不许无声删）。

### 4.2 会话档案（`store/session-dossier.js`）

**持久化 key**：`dsh.director.dossier` —— 在冻结命名空间 `dsh.director` 之内。
R5 冻结的是"既有键不得改名/删除"，**新增是允许的**（见 `cdp-click-dialog.mjs` 白名单注释原文），
但**必须同步登记白名单**，否则 R5 假红（第 6 批 `agentRuns.v1` 就是这么红的）。

```js
{
  sessionId,                       // 主键
  dim,                             // 关联键（与 split-index 对齐，**不重复存 label**）
  director: { role, name, at },    // R2「自己的总监」：role 如 "A1 世界观 总监"
  summary:  { text, at, source, ok }, // R3「自己的会话总结文档」
                                   //   source ∈ { collect | host-title | none }（**不许编**）
  state, turns, at                 // 最近一次观测
}
```

**API**：`readDossiers` / `putDossier`（合并式）/ `dossierOf` / `forgetDossiers` /
`clearDossiers` / `applyDossiers(tree)` / `dossierStats()` / `installDossierApi()`

**上限** `DOSSIER_MAX = 200`（与 `SPLIT_MAX` 一致；localStorage 是全站共享预算）。

### 4.3 清理能力（取决于 §二 实测结论）

| 实测结果 | 手段 | 保障 |
|:--|:--|:--|
| 存在删除契约（`drop`/`remove` 语义 = 删会话） | 产品内「清理无效会话」入口，**小批次 + 逐条报结果** | 先 dry-run 列候选 → 用户可见 → 执行 → 删后回读数复核 |
| **无**删除契约 | 插件侧**忽略清单** `dsh.director.ignored`（新增 key）：从导图/面板隐藏 + 从 split/dossier 索引忘掉；同时提示用户在宿主 UI 手动删 | 忽略是**可逆**的（有"恢复"出口），绝不假装删掉了 |

🔴 无论走哪条：**不许把"隐藏"说成"删除"**（纪律 19 同型：降级可以，无声不行）。

### 4.4 派发链改造（`director-dispatch.js`）

```
plan() → planReuse() → for each dim:
    reuse  ⇒ sendToSession(已有 id, brief)              ← **不建会话**
             putDossier(id, {director, ...})
             info.reused = true
    create ⇒ createSession({}) → sendToSession(新 id, brief) → recordSplits
             putDossier(id, {director, ...})
             info.reused = false
返回增加 reused / created / orphanForgotten 三个读数
```

### 4.5 回收链改造（`director-collect.js`）

回收每条分支时，把该会话的产出摘要写进**它自己的档案** `summary`：
`source="collect"` + `ok` 如实（读不到 ⇒ `source="none"` + `ok:false` + 原因）。

### 4.6 数据契约（**只新增，不改冻结契约**）

| 新增 | 位置 | 用途 |
|:--|:--|:--|
| `dsh.director.dossier` | localStorage | 会话档案（R2/R3） |
| `dsh.director.ignored` | localStorage | 忽略清单（R4，仅无删除契约时启用） |
| `data-dossier-role` | 导图节点 DOM | 导图可读"归谁管" |
| `data-reused` | 派发读数 / 节点 | 区分"复用"与"新建"（**必须可分**） |
| `window.__dshDossier` | 全局诊断出口 | 闸门读数（与 `__dshDispatchLog` 同性质） |

## 八、优化建议（回答"如何更符合我的想法"）

> 每条四段：**现状 → 痛点 → 建议 → 代价**。前三条是这一轮**真机数据反推出来**的，不在原计划里。

### 8.1 「逐字节一致」不等于「是新产物」—— 缺一条 mtime 序判据

- **现状**：`plugin-install.mjs` 的复判是"仓库 `lib/client.js` ↔ 实体包 `lib/client.js` 逐字节一致"。
- **痛点**：本轮 `DirectorPage.js` 的 5 处 DOM 属性改动发生在最后一次 build **之后**，产物是**旧的**；
  两个旧产物之间当然逐字节一致 ⇒ 装机报 ✅，真机闸门 5 条假红，我一度怀疑复用逻辑写错了。
  这类缺陷**只在真机上暴露**，离线全绿。
- **建议**：新增 `scripts/check-stale-build.mjs`：比对 `lib/client.js` 的 mtime 与 `src/**` 的**最大 mtime**，
  陈旧则 exit 1，并由 `plugin-install.mjs` 在写入前调用（**未过即拒装**）。`--force` 可显式放行。
- **代价**：一条 mtime 判据；若某个 src 文件被"只读触碰"（编辑器保存无内容变化）会误报 —— 用 `--force` 兜。

### 8.2 宿主一直有 `rename`，插件却在"标签覆盖"—— 用户在最该认出会话的地方认不出

- **现状**：`store/split-index.js` 在插件侧覆盖会话标签（旧结论写"宿主无 rename，只能这样"）。
  E1 实测：`session.rename(title)` → 宿主 RPC `api.sessions.rename({sessionId,title})` **存在**。
- **痛点**：只有插件视图里标题好看；**宿主自己的会话列表与搜索**里仍是默认标题，
  用户下次在侧栏里找「A1 世界观」那条根本找不到 —— 而这正是"一百多个会话分不清"的一半原因。
- **建议**：派发时**优先调 `rename`**（成功即宿主侧生效），失败再回落插件侧覆盖，且**降级要可见**（纪律 19）。
- **代价**：rename 会写宿主数据（低不可逆）；需**先读原标题**留档，便于环境复原与回滚。

### 8.3 配额失败要**派发前**就知道，而不是回收时才发现

- **现状**：本轮已修"回收时如实报出宿主失败原因"。
- **痛点**：8 条简报已经投出去了、8 次运行已经失败了，用户才看到"配额不足"。
  在"模型侧全面拒绝"的情况下，这几个动作**纯属浪费**，还会把会话数搅大。
- **建议**：派发前做一次**极轻量预检**（读宿主 `models` 能力 / 上一次 `turn/end` 的 failure），
  命中 QUOTA 类失败就**不派发**，直接在总监页说明"配额不足，先充值或换模型"。
- **代价**：多一次 RPC；预检本身也可能消耗额度 ⇒ 应优先用"读上次结局"这种零成本判据。

### 8.4 「清理会话」应当是**一条命令**，不是每轮重新摸落点

- **现状**：本轮的会话清理摸索过程已被固化为 `scripts/clean-sessions.mjs`（dry-run 默认、移入 `.trash-<ts>`、删后三口径复核）。
- **痛点**：同一问题**至少复发两次**（16:18 一次、本轮一次），每次都重新找"会话到底存哪几处"。
  且**两处易漏**：① `workspace.json` 的 `sessionIds`/`archivedSessionIds`（漏 ⇒ 幽灵会话）；
  ② 会话目录有**两种命名纪元**（`session-<uuid>` 117 条 + 裸 `<uuid>` 14 条，漏一种就只清一半）。
- **建议**：把该脚本登记进 docs 索引与 AGENTS 命令链；纪律里补"会话落点有三处 + 两种命名"。
- **代价**：≈0（已产出）。

### 8.5 真机闸门的**起点要能自举**（零会话不再级联假红）

- **现状**：`verify-novel-split` 的 A1 原来只点"已存在的侧栏会话"。
- **痛点**：清空会话后（**清理后的常态起点**）没有会话可点 ⇒ `NS-1a` 红，后面十几条**级联假红**，
  真因（起点没建立）被淹没。
- **建议**：已加"零会话 ⇒ 真实鼠标点『新会话』自举"；进一步抽成 `scripts/lib/ensure-session.mjs`，
  所有真机闸门共用（判据与 `_probe-session-count.mjs --click-new` 一致：先证按钮在视口内，再点，再证真多出一个）。
- **代价**：一次小重构。

### 8.6 主进程不可结束 ⇒ 清盘"看起来没生效"

- **现状**：`7412`（CDP 9222）/ `5656`（app 15117）对本会话的 `Stop-Process` / `taskkill /F` **静默拒绝**
  （用户手动启动的进程树）；`restart-harness.ps1` 会起新实例，但**端口没变** ⇒ 插件未重载（纪律 61 幽灵重启）。
  `lib/client.js` 是 **client 插件、页面 boot 时读盘** ⇒ `Page.reload` 已足够让**插件产物**生效（本轮实测）。
- **痛点**：但**会话列表在宿主主进程内存里** ⇒ 磁盘已清 0，宿主仍列 **115 条幻影会话**，
  用户会以为"没清干净"。且此状态下跑真机闸门只能测到半清理态。
- **建议**：① `clean-sessions.mjs` 结束打印"必须手动重启（或重启机器）才反映为 0"（已加）；
  ② 把"清盘后必须由用户重启宿主"写进纪律；③ 若能以可被结束的方式启动 Harness，则 `restart-harness.ps1` 才能真正闭环。
- **代价**：本轮的最后一段真机验证**必须**由用户重启后补跑（首跑场景：`reused=0 ⇒ created=8`）。

### 9.4 设计（只新增，不改冻结契约）

#### D1 修法：过滤点在**唯一摄取点**

```
refreshBranchTree():
  fromCtx = readSessionsFromCtx(...)                    // 宿主快照，含归档
  arch    = await archivedSessionIds()                  // [] 可过滤；null ⇒ 不许过滤
  live    = arch ? fromCtx.filter(∉ arch) : fromCtx
  tree    = buildBranchTree(live, ...)                  // ← 归档会话在此处消失
  diag.archivedExcluded / diag.archivedKnown            // 如实报数
```

* 与派发复用**同一判据**（`archivedSessionIds()`），杜绝两套口径；
* **语义**：宿主快照非空 ⇒ 一律走 `buildBranchTree`（哪怕过滤后为 0 ⇒ 空树），**不回退 discover**
  —— 回退会让"用户确实没有活会话"被一个**伪造平铺树**盖住；
* `null`（读不到归档集）⇒ **不过滤**：宁可多显示，不可把"读不到"当"全归档"（同 dispatch 的处置）。

#### D2 修法：档案接进同一摄取点 + 导图落 DOM

```
refreshBranchTree():
  applySplitLabels(tree, …)      // 已有
  applyDispatchLabels(tree)      // 已有
  applyDossiers(tree)            // ← 新增（写 row.dossierRole / dossierSummary / hasDossier）
  diag.dossierApplied / dossierWithSummary / dossierRoles

MindMap 节点新增 DOM：
  data-has-dossier / data-dossier-role / data-dossier-summary / data-dossier-src
```

#### D3 修法：读不到就要说**为什么**

`director-collect.js` 的两条"没读到"分支补：

```js
putDossier(id, { summary: { text: "", at, source: "none", ok: false, reason: <可读原因> }, at })
```

`reason` 复用已有口径：`宿主本轮运行失败：<message>（<code> <status>）` / `事件流里还没有对话条目（简报可能还没被处理）` / `只有用户侧条目，没有助手回复`。
