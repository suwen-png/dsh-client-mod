| # | 命题 | 结论 | 证据（真机） |
|:-:|:---|:---|:---|
| P1 | 分支会话能否被**真的驱动**（agent 真执行）？ | ✅ **能** | `sendToChat("请只回复两个字：收到")` → `{ok:true, mode:"sent", verified:true}`；`sawGen=true`；耗时 **3608 ms** |

## 五、设计

### 5.1 数据流（实现后版本）

```
[总监输入框] 需求原文（含《书名》+ 项目根路径）
      ↓  dp-act-split（「派发」）→ dispatchBranches(idea)
      ↓    ① projectOf(text) 正则提项目根（不写死"墟海"）
      ↓    ② plan(text) → dims[8]（A1–A8）；briefOf(dim, text, novelName, project) 带项目落点
      ↓    ③ 逐维 createSession() → sendToSession(id, brief)（直投，降级才用 composer）
      ↓    ④ onBranch 钩子把新会话挂进层级树（导图才有节点可标）
      ↓    ⑤ recordDispatch() 记台账 → refreshStates() 读宿主快照定状态
      ↓    ⑥ recordSplits()（沿用 key `dsh.director.split`，标题覆盖）
      ↓    ⑦ hostConfirmMs 窗口**复核启动**（running || turns>0）→ data-confirmed / data-unconfirmed
[8 个分支对话]  各自 agent 读各自落点文件 → 产出（宿主事件流里累积）
      ↓  dp-act-collect（「📥 回收」）→ collectBranches()
      ↓    ⑧ refreshStates()（不该失败）
      ↓    ⑨ 逐条 history({}) 取 assistant 正文 → say；取不到则写 **sayReason**（两种不同原因）
      ↓    ⑩ 再 refreshStates()（让 partial 与 done 可分）
      ↓    ⑪ countStates() → verdictOf() → nextActionOf() → setDispatchCollect()
[总监页]  dp-flow-collect 读数：total/read/unread/done/running/say/verdict
[思维导图]  节点：维度名 + `data-branch-state` 徽标 + 第 3 行「产出：…」（或「产出未读到：<原因>」）
```

### 5.2 DOM / 数据契约（**只新增，不改冻结契约**）

| 契约 | 位置 | 说明 |
|:---|:---|:---|
| `data-dispatch="<sessionId>"` | 导图维度节点 | 该节点对应的分支会话 id（血缘） |
| **`data-branch-state="blank\|running\|done\|partial\|unknown"`** | 同上 | **派发态**（与既有 `data-state` **刻意不同名**，见 §3.0） |
| `data-said="<摘要>"` | 同上 | 产出摘要；**仅在采集到时有值**，未采集 / 未派发均为 `""`（**不许编**） |
| `data-testid="mm-node-said"` + `data-said-empty="0\|1"` | 同上第 3 行 | 有产出显示「产出：…」；无产出显示「产出未读到：<原因>」（**不静默** —— 纪律 19） |
| `data-confirmed` / `data-unconfirmed` / `data-via` / `data-attachfail` | `dp-flow-split` | 投递复核读数（进程 ⑦） |
| `data-total` / `data-read` / `data-unread` / `data-done` / `data-running` / `data-say` / `data-verdict` | `dp-flow-collect` | 回收读数（`read + unread === total` 是不变式） |
| `data-testid="dp-act-split"` / `dp-act-collect` | 总监控制台 | 派发 / 回收（`CONSOLE_ACTIONS`；`collect` = 📥） |
| `window.__dshDispatchLog` | 插件 store | `{at, text, name, kind, items:[{dim,label,sessionId,sentVia,sentOk,sentReason,attachFail,state,stateSource,turns,outputTokens,say,sayReason,title,collectedAt,confirmed,confirmedVia,assistantCount}], collect}` |
| ~~`conversationMirror.bySession`~~ | — | ❌ **不再新增**（P3′ 后无必要，也不动冻结契约） |

### 5.3 关键取舍（明写，避免"无声降级"）

1. **投递 vs 建会话**：`createSession()` 建的会话是**独立空白**会话（无父，导图上并列）—— 与 16 批一致，**不用 fork**（理由见 `branch-tree.js:513` 注释：fork 会串成链，读图者会误以为"剧情从世界观分叉来"）。
2. **投递路径**：`window.__directChatSubmit` → `conversation.send` → **如实报失败**。三级都不可用时写 `sentOk=false` + `sentReason`，**不假装已派发**（纪律 19）。
3. ~~采集只能"逐个切页签"~~ **已修正**：采集走 `history({})`，**一次全读、不切页签**（P3′）。采集仍是**显式动作**（用户点「📥 回收」），**不自动**跑 —— 8 个分支同时被读会推高宿主负载，且"回收"本身是用户要看到的动作。
4. **状态与产出分开**：状态来自宿主快照（**不切页签**，可靠）；产出摘要来自事件流（**可能缺**：分支还没回话）。⇒ 导图上"状态一定有，摘要可能空"，界面**区分**显示。
5. **`partial` 单列**：分支**跑了但没拿到助手回复**（宿主 `turns>0` 而事件流无 assistant 文本）必须与 `done` 分开，否则"空转"会被读成"完成"。
6. **自动标题不充数**：`session/title` 是模型起的名字（P7），**不进** `say`；`say` 只放 assistant 正文摘要。
