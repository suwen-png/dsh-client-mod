## 五、设计

### 5.1 数据流

```
[总监输入框] 需求原文（含小说名《墟海》+ 项目根路径）
      ↓  runDirector 五步（第 1 步：整理语言）
      ↓  第 2 步：职能识别 → plan(text) → dims[8]
      ↓  ★新增 G1/G2：逐维 createSession() → deliverToChat(brief, {sessionId, opener})
      ↓  记入 dispatch 台账（sessionId / 维度 / 状态 / 投递凭据）
[8 个分支对话]  各自的 agent 读各自落点文件 → 产出
      ↓  ★新增 G3/G4：collect() —— 逐个 openSession → syncConversationMirror(bySession) → 回原会话
      ↓  总裁定（哪几个完成 / 哪个失败 / 产出摘要）
[总监]  汇总消息 + next action
[思维导图]  节点：维度名 + 状态徽标 + 产出摘要（★新增 G5）
```

### 5.2 DOM / 数据契约（新增，不改冻结契约）

| 契约 | 位置 | 说明 |
|:---|:---|:---|
| `data-dispatch="<sessionId>"` | 导图维度节点 | 该节点对应的分支会话 id（血缘） |
| `data-state="pending|running|done|failed"` | 同上 | 分支状态（来源：快照 `running/completed` ∪ 生成态） |
| `data-said="<摘要>"` | 同上 | 产出摘要（**仅在采集到时有值**；未采集为 `""`，**不许编**） |
| `conversationMirror.bySession` | 桥 | `{ [sessionId]: {items,total,at,reason} }`（**新增字段**；现有 `items/total/at/tab/syncs/misses/reason` 不动） |
| `dispatchLog` | 插件 store | 本次派发台账（`{at, dims[], made, failed, collected}`），落盘沿用现有 key |

### 5.3 关键取舍（明写，避免"无声降级"）

1. **投递 vs 建会话**：`createSession()` 建的会话是**独立空白**会话（无父，导图上并列）—— 与 16 批一致，**不用 fork**（理由见 `branch-tree.js:513` 注释：fork 会串成链，读图者会误以为"剧情从世界观分叉来"）。
2. **投递路径**：优先 `sendToHost(sessionId, text)`（直投对话域）；不可用则 `opener` + `sendToChat`。**两级都不可用时如实报** `deliver-failed`，**不假装已派发**。
3. **采集只能"逐个切页签"**：因为 P3（总监页签读不到 DOM）。⇒ **必须**是**显式动作**（用户点「回收产出」），**不自动**跑（8 次切页签会让 UI 闪）。
4. **状态与产出分开**：状态来自快照（**不切页签**，可靠）；产出摘要来自采集（**要切页签**，可缺）。⇒ 导图上"状态一定有，摘要可能空"，界面必须**区分**显示（纪律 19：降级可以说，不能无声）。
