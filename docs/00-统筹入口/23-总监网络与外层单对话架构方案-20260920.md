## 一、用户口述需求的结构化转写

### 1.1 痛点
- 重复需求、重复确认：用户觉得讲清楚了，AI 却总停下来要确认。
- 对话平铺：无法确认哪些对话对应同一个需求。
- AI 做得比用户好但总停：需要一个「替用户把话讲完、把路选好」的中间层。

### 1.2 灵感来源
- 目标模式、立体结构：同一次调用里多个智能体各干各的。
- Harness 已经提供分支，但分支之间看不出关系。
- JARVIS 式反问：「我们会自己选择对话吗？」——不会，所以要一个替人选的人。

### 1.3 七个核心设计点
1. **总监模式**：用户把问题发给总监，总监判断该把信息发给哪个对话；总监只做「对话内容整理 / 需求理解」，保证理解不偏差。
2. **职能分流**：按整理后的需求，不同职能走不同分支。
3. **模型 / 技能 / 角色选择**：按不同大模型擅长的部分选模型；总监提供整理后的上下文，选适合的对话、模型、技能、智能体、角色。
4. **纯判断层 + 缩减上下文**：引入「只负责判断的模型」和「缩减上下文的 skill」。
5. **思维导图**：详细展示整个分支的状态、对应正在进行的工作。
6. **嵌套总监**：每个对话有自己的总监；每个文件 / 项目有总监；再往上嵌套也有总监。
7. **最终形态**：外层只剩一个对话；左侧是项目完成情况、待完成清单、已完成清单、当天正在进行的事、置顶事项；用户直接和外层对话沟通，由对话做语言整理、模型选择、上下文处理，反馈结果。

### 1.4 用户自认没讲清、需要方案补齐的四块
- 设计图
- 思维链路
- 执行逻辑
- 审核机制

本方案 §十 专门补这四块。

### 2.2 真正的缺口（本方案要解决的）

| 缺口 | 现状 |
|:---|:---|
| **外层不是「一个对话」** | 现有外层是「总监操作台」（五步区 + 流程段 + 常驻读数），不是一个可对话的收件箱；输入仍走总监页 / 弹窗 / composer 三入口。 |
| **没有左侧常驻看板** | 导图是浮层，关掉就没了；没有「完成 / 待办 / 进行中 / 置顶」这种任务态字段；当前是「分支状态」不是「任务看板」。 |
| **嵌套是结构嵌套、不是运行时嵌套** | 层级树 global / project / session 四级已存在，每个会话有角色名；但真正在跑的只有一个规则引擎 `runDirector()`，所谓「项目总监 / 对话总监」只是标签和消息桶，不会各自独立判断。 |
| **模型选择只有标签、没有真路由** | `MODEL_TIER` 存在，12 个角色存在；但 `callLocalModel` 是死代码（无本地模型、无 fs）；「选模型」只写在简报里，不真路由。 |
| **纯判断层不存在** | `judgeBranch()` 是「只判不建」的雏形，但判定与执行在同一个函数里，没有独立成一个「只输出判定、不产生副作用」的服务层。 |
| **没有专门的上下文压缩 skill** | `pickContext()` 只在 needSwitch 时取 5 条；`session-dossier` 的总结是半自动；没有常驻的、跨轮的压缩器。 |
| **id 语义在会话级 / 作用域级之间有歧义** | 现有「流转记录」用的是作用域 id（文件夹）而非会话 id；嵌套到「对话级 / 项目级 / 外层层」时这个歧义会被放大（已有登记 T-PLUG-074）。 |

### 2.3 硬约束（方案必须正面回应）

1. **宿主无 fs 服务**：总监不能自己读文件，只能结构化指派 + 要求分支回报。
2. **无法批量实时读每个对话的产出**：DOM 通道一次只能读当前打开会话；看板要做「每项目当前在干嘛」必须另建快照采集通道。
3. **模型侧 QUOTA / 余额失败**：必须自带配额预检与降级，不能把「环境阻塞」和「模型没出结果」混为一谈。
4. **宿主无 React 错误边界**：单层崩溃卸载整棵根，新 UI 必须每层包安全层。
5. **改宿主编译产物需单独授权**：主管道是独立插件包，本方案不碰宿主源码。

## 三、总体架构

### 3.1 一句话
**外层是一个常驻对话（用户唯一入口），左侧是常驻项目看板，中间是嵌套总监网络负责理解 / 分流 / 选模型 / 压缩上下文，右侧（可选）是思维导图作为「图视角」看同一份数据。**

### 3.2 与现有三页签三浮层的关系
**不是推倒，是外层重组**：

- 现有【总监】页签 → 降级为「外层对话的后台面板」（看五步链、台账、常驻读数），不再是用户主入口。
- 现有【对话】页签 → 保留，但用户日常不再手动切；外层对话需要落到具体分支时，由总监自动路由过去。
- 现有【轨迹】页签 → 保留，作为「审核 / 回溯」视图。
- 现有三浮层（设计图工作室 / 思维导图 / 总监弹窗）→ **保留为浮层**，不搬进左侧看板：
  - 思维导图 = 同一份数据的「图视角」，看板 = 同一份数据的「列表视角」；两者同源、互为补充。
  - 设计图工作室 = 分支产出的设计物编辑器，由分支对话触发打开。
  - 总监弹窗 = 作用域内的快速选择器，保留。

### 3.3 数据流向总览

```
用户（唯一入口：外层对话输入框）
   │
   ▼
┌─────────────────────────────────────────────┐
│  L0 外层总监（纯判断层）                      │
│  · 理解用户意图（去噪 + 归纳 + 项目把控）     │
│  · 判断：这条消息归哪个项目 / 哪个职能 /       │
│    哪个模型 / 哪个技能 / 哪个角色              │
│  · 输出：一个路由决策（纯数据，无副作用）     │
└─────────────────────────────────────────────┘
   │ 路由决策
   ├─► L1 项目级总监（每个项目一个实例）
   │      · 维护本项目的上下文压缩包
   │      · 判断本项目内的子任务怎么拆
   │      · 决定复用哪个已有分支 / 新建哪个分支
   │      │
   │      └─► L2 会话级总监（每个分支对话一个实例）
   │             · 维护本分支的 dossier
   │             · 执行具体的写作 / 设计 / 审核
   │             · 把产出摘要回传 L1
   │
   └─► 看板 / 导图（订阅同一份状态流）
```

## 四、需求流转链路

### 4.1 一次完整流转的时序

1. **用户输入**：在「外层对话」输入框说一句话（可能很粗糙、可能混多个意图）。
2. **L0 理解（纯判断层）**：
   - 去噪（复用现有七级噪声分辨）；
   - 归纳（复用现有 `organize()` / `organizeSummary()`）；
   - 项目把控（判断这条消息属于哪个项目、哪个职能）；
   - **输出一个路由决策对象**：`{ project, functions: [...], modelTier, skill, role, contextPlan, reason }`。
   - 这一步**不发任何消息、不建任何会话**，只做判断。
3. **L1 项目级总监接管**：
   - 按 `functions` 决定拆成几个子任务；
   - 每个子任务查复用索引（复用优先、缺才新建）；
   - 每个子任务组装「压缩后的上下文包」（见 §七）。
4. **L2 会话级总监执行**：
   - 收到 L1 转来的上下文包；
   - 在自己的分支对话里干活；
   - 把产出摘要 + 状态（done / partial / blocked）回传。
5. **结果汇总**：
   - L1 收到所有 L2 回报后做项目级归纳；
   - L0 收到 L1 归纳后做外层反馈（用用户能懂的话讲「我做了什么、结果是什么、接下来建议什么」）。
6. **可视化同步**：看板与导图订阅同一份状态流，自动刷新。

### 4.2 状态机

每个任务在三层之间的生命周期：

```
draft（用户刚说完，L0 还没判）
  → routed（L0 已出路由决策）
  → assigned（L1 已派到具体分支）
  → running（L2 在干活）
  ├─ done（产出已回传、已归纳）
  ├─ partial（跑了但没拿到完整结果）
  ├─ blocked（配额 / 环境 / 技能缺失，已如实落地）
  └─ aborted（用户取消 / L1 改判）
```

**关键纪律**：`partial` 必须与 `done` 分开（这是现有经验，不许合并）；`blocked` 必须带原因（不能只说「失败」）。

## 五、嵌套总监层级模型

### 5.1 三层职责与边界

| 层 | 挂在什么 id 上 | 职责 | 不做什么 | 上下文边界 |
|:---|:---|:---|:---|:---|
| **L0 外层总监** | 全局（不绑定项目） | 理解用户这句话；判断属于哪个项目；选模型 / 选技能 / 选角色；决定要不要拆 | 不做具体写作；不维护项目内细节；不直接发消息给分支 | 只看「用户最新这句话」+「项目清单摘要」，不看项目内部对话 |
| **L1 项目级总监** | 项目根（如《虚海》） | 维护本项目的压缩上下文；拆子任务；决定复用 / 新建分支；项目级归纳 | 不直接和用户对话；不跨项目派发 | 只看本项目下所有分支的摘要（不看全文） |
| **L2 会话级总监** | 会话 id | 在自己的分支里干活；维护自己的 dossier；产出摘要回传 | 不越级找用户；不跨分支派发 | 只看本分支的对话历史 + L1 给的上下文包 |

### 5.2 解决 T-PLUG-074 的 id 语义歧义
- 流转记录、看板条目、导图节点，**统一挂在「会话 id」上**（L2 层）；
- 项目级聚合（L1）通过「项目根 → 下挂会话 id 集合」推导；
- 外层聚合（L0）通过「项目根列表」推导；
- **禁止**再用「作用域 id / 文件夹 id」作为流转记录主键——这是现有歧义的根源。

### 5.3 与现有数据结构的关系
- 现有 `session-dossier`（每会话一个角色名 + 总结）→ 直接升级为 L2 的持久化形态。
- 现有层级树（global / project / session）→ 直接升级为 L0 / L1 / L2 的物理骨架。
- 现有消息信封（root / parent / from / to）→ 直接作为跨层通信协议。
- **新增**：L0 的「路由决策对象」需要一个持久化落点（建议放现有 IndexedDB 的 `Decisions` store，不新建 store）。

### 5.4 运行时怎么真跑起来
现状是「一个规则引擎跑所有层」。要让三层真跑起来，分两步：

- **v1（规则版，不依赖本地模型）**：L0 / L1 / L2 各是一个纯函数，输入是结构化数据、输出是结构化决策；三层用同一份代码框架，只是参数（角色 prompt、维度清单、模型 tier）不同。这一版**完全离线可测**，不依赖任何外部模型。
- **v2（模型版，接本地模型后）**：在 v1 基础上，把 L0 的「理解 / 归纳」和 L1 的「子任务拆解」换成真模型调用；L2 保持走分支对话自己的模型。v1 的纯函数作为 v2 的降级路径（模型挂了就回退到规则版）。

## 六、模型选择与纯判断层

### 6.1 为什么要分离判断与执行
现状问题：判断和执行在同一个函数里，判断的结果「判了却没人用」（历史上踩过空转的坑）。分离后：
- **判断层**只输出决策，不产生副作用（不写库、不发消息、不改 UI 状态）；
- **执行层**只读决策、产生副作用；
- 好处：判断层可以被单测、可以被替换、可以被审计、可以跑在便宜模型上。

### 6.2 模型选择决策树（纯函数）
输入 = 任务特征（项目类型、职能、复杂度、是否需要长上下文、是否需要工具调用）；输出 = `{ modelTier, reason }`。

| 任务特征 | 建议 tier | 理由 |
|:---|:---|:---|
| 去噪、意图分类、路由判断 | cheap | 模板化、可规则化 |
| 维度拆分、子任务拆解 | standard | 需要一定语义理解 |
| 正文写作、设计图、复杂推理 | strong | 质量敏感 |
| 归纳总结、上下文压缩 | standard | 要读懂但不需要创造 |
| 审核 / 验收 | strong | 要严格 |

**这棵树写成纯函数、绑离线单测；tier 到具体模型名的映射是配置项，不写死在代码里。**

### 6.3 降级路径
- 本地模型未接入时：L0 / L1 的判断走规则版（v1），界面如实显示「规则模式」；
- 模型返回 QUOTA / 余额不足：任务状态置 `blocked`，带原因，不假装成功；
- 模型超时 / 无返回：复用现有 `partial` 状态。

### 6.4 配额预检
派发前先查一下目标 tier 的当前可用额度（如果宿主有这个接口；没有就靠事后 `endFailure` 三级落地兜底），不做「发出去才发现没余额」的傻事。

## 七、缩减上下文机制

### 7.1 什么进判断层、什么不进
- **进 L0 外层判断**：用户最新这句话 + 项目清单摘要（每个项目一行：名称 / 最近活动 / 进行中任务数）。**不进**任何项目内部对话历史。
- **进 L1 项目级判断**：本项目下所有分支的 dossier 摘要（每个分支 3-5 行）。**不进**分支对话全文。
- **进 L2 会话级执行**：本分支自己的对话历史（由宿主管理）+ L1 给的上下文包（3-5 行项目背景 + 相关 dossier 摘要）。

### 7.2 预算上限与截断策略
- 每个上下文包设一个**字符预算**（建议：L0 ≤ 2 KB、L1 ≤ 4 KB、L2 外部注入 ≤ 2 KB；具体值可调）。
- 截断策略：按「最近优先 + 相关性打分」保留，不按「前 N 条」硬切（现有 `pickContext` 是硬切 5 条，要升级）。
- 现有 `session-dossier` 的总结是压缩的第一落点；L1 的项目级压缩是第二落点。

### 7.3 与现有能力的关系
- 复用现有 `organize()` / `organizeSummary()` 做「语言整理」；
- 复用现有 `noiseReasonOf()` 做「去噪」；
- **新增**一个常驻的「项目级压缩器」：每次 L1 派发前跑一次，把本项目下所有分支的最新状态压成 3-5 行摘要；这是现有 dossier 没有的粒度。

## 八、思维导图如何承载分支状态

### 8.1 现状已支持的
项目→维度两级分区、父居中、全节点可拖、血缘连线、作用域过滤、折叠、小地图、缩放、档案行（「· 总监 A1 世界观」）。

### 8.2 需要新增的任务态语义
当前节点状态是 `blank / running / done / partial`（分支执行态），需要扩展为「任务态」：

| 任务态 | 含义 | 视觉建议 |
|:---|:---|:---|
| 完成 | 已交付、已验收 | 节点打勾、淡化 |
| 待办 | 已派发但还没开始跑 | 灰色等待态 |
| 进行中 | 正在跑 | 现有 running 样式 |
| 置顶 | 用户手动标记的当前重点 | 节点加星 / 置顶角标 |
| 阻塞 | blocked（带原因） | 红色警示角标，悬停看原因 |

**这些任务态和看板是同一份数据的两种渲染**——看板是列表视图、导图是图形视图；单一真相源在 store 里。

### 8.3 与看板的关系
- 看板回答「现在有哪些事、哪些重要」；
- 导图回答「这些事之间是什么关系、在哪个分支上」；
- 点看板条目 → 导图定位到对应节点并高亮；
- 点导图节点 → 看板展开对应任务详情。

## 九、左侧项目看板

### 9.1 信息架构（从上到下）

```
┌─────────────────────────┐
│  置顶事项（用户钉住的）  │
├─────────────────────────┤
│  今天在进行的（按时间排） │
├─────────────────────────┤
│  待完成清单（按项目分组） │
├─────────────────────────┤
│  已完成清单（可折叠，默认收起）│
└─────────────────────────┘
```

### 9.2 数据来源单一真相源
看板的数据**只从一个地方来**：任务状态 store（建议扩展现有 `task-state.js`，不新建）。字段建议：
- `taskId`（来自会话 id + 子任务序号）
- `projectRoot`
- `branchSessionId`
- `title`
- `state`（draft / routed / assigned / running / done / partial / blocked / aborted）
- `pinned`（boolean）
- `updatedAt`
- `summary`（最新一句人话）

**禁止**看板自己扫 DOM 或自己拼数据——所有状态变更走同一个写入点。

### 9.3 解决「无法批量读产出」的硬约束
看板要显示「每项目当前在干嘛」，但 DOM 通道一次只能读当前会话。方案：
- L1 项目级总监每次派发 / 回收时，**主动**把摘要写进 task-state store；
- 看板只读 store，不实时读 DOM；
- 这就是「快照采集通道」——不是实时读、是事件驱动写。

### 9.4 与现有 UI 的关系
- 看板放在哪里：建议放在现有【总监】页签的左侧栏（不是浮层），常驻；
- 现有 `host-director-column.js` 的总监列可以改造成看板容器；
- 思维导图浮层保留作为「图视角」，与看板联动。

## 十、四块用户没讲清的补充设计

### 10.1 设计图
- 现有「设计图工作室」是分支产出的设计物编辑器；
- 在新架构里，它的定位是：**L2 会话级总监的产出物编辑器**——某个分支产出了设计图，就在这里打开编辑；
- 设计图本身带元数据（来自哪个分支、什么时候产出的、当前版本）；
- 看板上如果某任务的产出是设计图，点条目直接跳到设计图工作室并定位到那张图。

### 10.2 思维链路（判断层的思考过程可视化）
用户说的「思维链路」= 让用户看见 L0 外层总监是怎么想的、为什么这么派。
- 现有【轨迹】页签扩展为「思维链路视图」；
- 每一次 L0 判断留一条记录：`{ 输入, 路由决策, 理由, 时间 }`；
- 这条记录就是现有 `Decisions` store 的可视化；
- 用户可以在轨迹里翻：「上次它为什么把这条消息派给了 A4 人物分支？」——看到决策理由。

### 10.3 执行逻辑
执行逻辑 = 任务状态机 + 降级路径（§4.2 已述）。补充三点：
- **幂等**：同一个用户消息被 L0 判断多次，路由决策应一致（纯函数保证）；
- **可回放**：Decisions store 存了每次决策，回放就是「按当时的决策重走一遍流程」；
- **失败不静默**：任何一层卡住都必须把状态写到 task-state store，看板上看得见。

### 10.4 审核机制
按本项目已沉淀的审核标准，方案落地时执行 **5 层 × 2 阶段**：

| 层 | 看什么 | 前置审（设计时） | 后置审（交付时） |
|:---|:---|:---|:---|
| **L0 闸门可验证性** | 每块设计是否绑了断言、离线测试、真机套件；退出码 0/1/2 是否分层；有没有植入缺陷校准 | 设计文档里写清楚 | 离线全绿 + 反例校准通过 |
| **L1 产品层** | 用户原话逐条覆盖；三层总监 id 语义清晰；看板数据单一真相源；降级路径完整 | 逐条映射表 | 真机连跑读数稳定 |
| **L2 逻辑层** | 决策树纯函数；判断与执行分离；同一语义唯一实现；状态机无非法跳转 | 纯函数 + 单测 | 单测全绿 + 逻辑无死分支 |
| **L3 体验层** | 看板信息密度；嵌套总监可见可达；导图与看板联动；1:1 截图取证 | 交互走查 | 截图 + 真机 3 次读数一致 |
| **L4 文档生命周期** | 文档编号、变更记录只增不改、不新开基线版本号 | 本文档自审 | 落地后同步基线 |

**审的方式**：AI 自检跑离线闸门 → 用户确认设计方向与不可逆操作 → 真机连跑 → 基线重封。不通过走结构化整改表，禁止带病进下一环节。

## 十一、与 HCC（hermes-command-center）的关系

### 11.1 边界划分
| | HCC | 总监插件 |
|:---|:---|:---|
| **定位** | 只读跨项目仪表盘（6 个项目 / 33 个记忆文件 / 278 个技能） | 动态调度台（理解需求 + 分流 + 会话编排） |
| **读什么** | 文件系统存量（文档 / 脚本 / 记忆 / 待办） | 会话工作区（分支 / 任务状态 / 决策记录） |
| **写不写** | 只读、不写、不起子进程、不碰宿主启停 | 写自己的 store、派自己的会话 |
| **给人看还是给 AI 用** | 给人看全局存量 | 给 AI 做动态决策 |

**结论**：两者是并列插件，不竞争。HCC 回答「这个项目有哪些文档 / 待办」；总监回答「这个需求该派给谁、现在跑到哪了」。

### 11.2 可复用的架构模式（不是搬代码）
- **数据通道**：HCC 验证过「宿主 webServer 同源注册只读路由」是唯一可行解——总监插件未来如果要读项目文件（比如 L0 判断时要看项目文档），走这条通道，不要自己重趟。
- **力导向图谱**：HCC 有零依赖 Barnes-Hut 力导向实现；总监 MindMap 未来要升级图可视化时可参考。
- **四层校验范式**：离线 jsdom → 活宿主 bundle 比对 → CDP 真机点击 → 反证套件——与总监现有 verify-* 体系同思路，可对照补强。

### 11.3 未来集成方向（不是本轮做）
- 若总监需要展示「当前项目的文档 / 技能状态」，正确做法是**消费 HCC 的只读接口**，而不是自己再扫一遍磁盘；
- 本轮不设计任何两个插件之间的直接 RPC——保持零耦合。

## 十二、实施路线图

> 每一步都遵循：先出设计文档 → 用户确认 → 编码 → 离线闸门 → 真机验收 → 基线重封。
> 测试范围 = 受影响面 ∪ 新增面；动冻结契约 / 删目录 / 曾假红过的套件仍走全量。

### 阶段 0：数据模型对齐（不做 UI）
- 统一 id 语义（会话 id 为主键，解决 T-PLUG-074）；
- 扩展 task-state store 字段（pinned / summary / projectRoot）；
- 纯函数：路由决策对象 schema、模型选择决策树、项目级压缩器；
- 验收：离线单测全绿；界面零变化。

### 阶段 1：左侧看板（先做列表视图，不动外层对话）
- 在【总监】页签左侧栏常驻看板；
- 看板只从 task-state store 读，不实时读 DOM；
- 置顶 / 折叠 / 分组交互；
- 验收：真机看板读数与导图节点数对账；点看板条目能定位到导图节点。

### 阶段 2：外层单对话形态（把总监操作台改成可对话的收件箱）
- 外层对话输入框作为唯一入口；
- L0 外层总监先跑规则版（v1）：去噪 → 归纳 → 路由决策 → 派给 L1；
- 反馈用用户能懂的话讲「我做了什么、结果是什么」；
- 验收：用户说一句多意图的话，L0 能正确拆分并派发；看板与导图同步刷新。

### 阶段 3：嵌套总监真跑起来
- L1 项目级总监：每个项目一个实例，维护本项目压缩上下文；
- L2 会话级总监：复用现有 session-dossier，升级为独立判断实例；
- 跨层消息信封打通（现有 env 协议直接用）；
- 验收：四层链（用户 → L0 → L1 → L2）真机走通；日志看得见每一层在干嘛。

### 阶段 4：纯判断层与缩减上下文（规则版先跑通）
- 判断层与执行层代码分离；
- 项目级压缩器常驻；
- 上下文预算与截断策略落地；
- 验收：判断层离线单测覆盖；上下文包大小有界；模型未接入时走规则版降级。

### 阶段 5：模型 / 技能 / 角色真路由（依赖本地模型接入）
- 这一步依赖 T-P2-001（本地模型真接入）落地；
- 接入后，L0 / L1 的规则版换成模型版；
- 模型 tier 决策树接真模型；
- 验收：模型版与规则版在同一批测试用例上结果一致（或差异可解释）。

**说明**：阶段 0–4 不依赖外部模型，可以独立做完；阶段 5 等本地模型就绪后再接。

## 十三、与现有纪律的对齐

| 纪律主题 | 本方案怎么体现 |
|:---|:---|
| 同一语义唯一实现 | 路由决策树、id 语义、看板数据源都只有一处实现；不允许两处手写。 |
| 没跑成 ≠ 失败 | 任务状态机里 `partial` / `blocked` / `aborted` 与 `done` 严格分开；不假装成功。 |
| 插件不参与宿主启停 | 本方案所有新增逻辑都在渲染进程 / 插件 store 内；不起子进程、不碰主进程生命周期。 |
| 测试范围 = 受影响面 ∪ 新增面 | 每个阶段只跑受影响套件；新增面必须有新断言覆盖。 |
| 不新开基线版本号 | 本方案是设计文档，不另立 V17/V18；落地后就地更新 V16 锚点。 |
| 证否前先确认检索键同源 | 看板对账时，节点计数与导图计数用同一套 id。 |
| 冻结契约不改名 | localStorage key / DB store 名 / DOM 锚点保持兼容；老用户数据走迁移。 |

## 十四、自审

### 14.1 用户口述的 7 个设计点是否全覆盖

| # | 用户说的 | 本方案章节 | 覆盖情况 |
|:-:|:---|:---|:---|
| 1 | 总监模式：用户发给总监，总监判断发给哪个对话 | §三 / §四 | ✅ |
| 2 | 总监只做内容整理 / 需求理解，保证不偏差 | §五 L0 职责 | ✅ |
| 3 | 按职能分流到不同分支 | §四 / §五 L1 | ✅（复用现有 A1–A8） |
| 4 | 按模型擅长选模型 + 选技能 + 选角色 | §六 | ✅（v1 规则版先跑，v2 接模型） |
| 5 | 纯判断模型 + 缩减上下文 skill | §六 / §七 | ✅（判断与执行分离；上下文压缩器） |
| 6 | 思维导图展示分支状态 / 正在进行的工作 | §八 | ✅（扩展任务态） |
| 7 | 嵌套总监（对话 / 项目 / 外层） | §五 | ✅（三层模型 + id 语义统一） |
| 8 | 最终形态：外层一个对话 + 左侧看板（完成 / 待办 / 进行中 / 置顶） | §三 / §九 | ✅ |
| 9 | 设计图 / 思维链路 / 执行逻辑 / 审核机制四块补齐 | §十 | ✅ |

### 14.2 有没有凭空设计脱离现状
- 所有新设计都标注了复用现有什么模块；
- 阶段 0–4 不依赖外部模型，全部基于现有纯函数 + store 扩展；
- HCC 边界基于 HCC 自己的文档结论，没有编造 HCC 能力；
- **待确认项**：宿主是否有「查模型配额」的接口——方案里写的是「如果有就接、没有就靠事后 `endFailure` 兜底」，没假设有。

### 14.3 嵌套层级有没有职责重叠
- L0 不做具体写作、不看项目内部对话；
- L1 不直接和用户对话、不跨项目派发；
- L2 不越级找用户、不跨分支派发；
- 三层的 id 语义、上下文边界、职责都在 §5.1 列清楚了；
- **唯一需要警惕的重叠点**：L0 的「归纳」与 L1 的「项目级归纳」都在做归纳——方案里规定 L0 只做一句话外层反馈、L1 做项目级细节归纳，粒度不同。

### 14.4 审核机制是否闭环
- 前置审（设计时）：本文档就是被审对象；
- 后置审（交付时）：5 层 × 2 阶段（§10.4）；
- 不通过走结构化整改表；
- 文档自身按生命周期管理（编号 / 版本 / 变更记录只增不改）。

### 14.5 左侧看板与现有总监页 / 导图的关系是否清楚
- 看板 = 列表视图、导图 = 图形视图、总监页 = 操作台后台；
- 三者共享同一份 store 数据；
- 看板常驻左侧、导图保留浮层、总监页降级为后台面板；
- 联动方式：点看板定位导图、点导图展开看板。

### 14.6 HCC 边界是否清楚
- HCC = 只读跨项目仪表盘；总监 = 动态调度台；
- 本轮不做任何两个插件之间的直接通信；
- 未来若要消费 HCC 数据，走 HCC 已有的只读接口，不重扫磁盘。

### 14.7 遗留问题与假设
1. **假设**：宿主的会话创建 / 消息投递接口在阶段 3 时仍然可用——如果宿主版本变化导致接口失效，阶段 3 要重新评估。
2. **待用户决策**：阶段 1 的看板放在【总监】页签左侧栏，还是作为新的常驻面板——这是 UI 取舍，方案建议放总监页签左侧，但用户可以否决。
3. **待用户决策**：模型 tier 决策树的初始映射表（cheap / standard / strong 各对应哪个模型）——本地模型接入后由用户定。
4. **待确认**：HCC 是否愿意开放只读接口给总监插件消费——本轮不依赖，记为未来项。
5. **已知硬约束没绕过去**：宿主无 fs 服务、无法批量实时读会话产出——方案里用「事件驱动写 store」绕开了「批量实时读」，但 L0 判断时若要读项目文件，仍需 HCC 那样的宿主 webServer 路由（本轮不做）。
