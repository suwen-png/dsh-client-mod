## 一、文档概述

### 1.1 目的

本文档解决三个核心问题：
1. **只读应该读的部分** — AI 启动项目时，如何确保只加载必要的文档，不浪费 token，也不漏读关键约束
2. **执行应该执行的逻辑** — AI 执行任务时，如何确保按10步链路走、触发对应的行为准则，不跳过、不偏离
3. **按标准执行** — 如何确保 AI 真的按照文档标准执行，而不是看过就忘、执行靠自觉

### 1.2 适用范围

- 适用于 D:\workspace 下所有项目
- 适用于 hermes-data 标准母本项目
- 适用于任何有 AGENTS.md 的项目

### 1.3 与其他文档的关系

| 文档 | 角色 | 本文档的关系 |
|------|------|-------------|
| `AGENTS.md`（项目级） | 最高优先级约束 | 本机制确保 AI 先读 AGENTS.md |
| `AI对话执行约束规范.md` | 约束内容（10步+6条+25条） | 本机制确保约束内容被执行 |
| `AI任务审核标准通用模板.md` | 审核标准 | 本机制的检查点引用审核标准 |
| `AI需求驱动读取范围与最小权限规范.md` | 读取范围规范 | 本机制的加载协议引用读取规范 |
| 本文档 | 执行保障机制 | 确保上述文档被真正执行 |

## 二、第一层：启动加载协议

> 解决"只读应该读的部分"。AI 操作任何项目时，必须按以下协议加载，不得跳过、不得全量读取。

### 2.1 项目启动加载序列（强制顺序）

AI 操作任何项目时，必须按以下顺序加载，每一步完成后才能进入下一步：

```
第0步：识别项目路径
  ↓
第1步：读取项目 AGENTS.md（如存在）← 最高优先级，强制全读
  ↓
第2步：读取 workspace 全局 AGENTS.md ← 如项目 AGENTS.md 引用了全局约束
  ↓
第3步：按项目 AGENTS.md 中定义的"必读集合"分层加载
  ├─ 第1层：强制全读（总统筹入口+执行约束）
  ├─ 第2层：只读关键章节（审核标准检查清单+读取规范需求类型表+大索引定位指南）
  └─ 第3层：按需求类型按需读取（见2.2触发条件）
  ↓
第4步：输出加载完成标记，开始业务处理
```

### 2.2 按需读取触发条件（第3层什么时候读）

第3层文档（按需求类型的详细文档）**不是启动时全读**，而是在以下情况才读取：

| 触发条件 | 读取内容 |
|---------|---------|
| 任务涉及代码修改/架构设计 | 读取 `10-架构设计/` 下相关文档 |
| 任务涉及测试/质量 | 读取 `40-测试质量/` 下相关文档 |
| 任务涉及特定技能/工具 | 读取 `08-技能作用记录/` 相关章节 |
| 任务需要参考历史方案 | 读取 `90-历史归档/` 相关文档 |
| 用户明确要求查看某文档 | 读取用户指定的文档 |
| 前两层加载后仍有信息缺失 | 按需读取补充 |

**禁止**：在没有触发条件的情况下，全量读取第3层文档。

### 2.3 加载完成标记（强制输出）

AI 完成必要加载后，**必须输出以下标记**才能开始业务处理：

```
【加载完成】已加载：
- 项目 AGENTS.md（路径：xxx）
- 必读集合第1层：xxx
- 必读集合第2层：xxx
- 当前任务类型：xxx
- 第3层按需读取：暂无 / 已读取xxx
```

**如未输出加载完成标记就开始业务处理，视为违规。**

### 2.4 加载异常处理

| 异常场景 | 处理规则 |
|---------|---------|
| 项目没有 AGENTS.md | 读取 workspace 全局 AGENTS.md，然后询问用户是否需要为该项目创建 AGENTS.md |
| 项目有 AGENTS.md 但没有定义必读集合 | 按 hermes-data 通用必读集合加载，并提示用户补充项目级必读集合 |
| 必读文档不存在 | 记录缺失，继续加载存在的文档，在加载完成标记中标注缺失项 |
| 文档读取失败 | 重试1次，如仍失败则记录并继续，在加载完成标记中标注 |

## 三、第二层：执行检查点机制

> 解决"执行应该执行的逻辑"。在10步链路的4个关键节点设置强制检查点，AI 必须停顿并输出标记，否则不能进入下一步。

### 3.1 四个强制检查点

| 检查点 | 位置 | 强制动作 | 输出标记 | 不通过的后果 |
|:------:|------|---------|---------|:------------:|
| **CP1** | 步骤4推导方案之后、步骤5匹配规范之前 | 自检方案是否满足：①至少2个方案 ②已评估能力 ③已评估风险 | 【CP1-方案自检通过】 | 回到步骤4重新推导 |
| **CP2** | 步骤7文档先行+前置审核 | **强制停顿**：必须输出方案文档并等待用户确认 | 【前置审核通过】（用户确认后） | 不能进入步骤8 |
| **CP3** | 步骤8落地执行中遇到阻塞 | **强制反馈**：遇到阻塞立即告知用户，不静默等待 | 【阻塞反馈】原因+需要用户做什么 | 继续阻塞视为违规 |
| **CP4** | 步骤9后置审核之后、步骤10交付之前 | **强制停顿**：对照审核标准自检，不通过不交付 | 【后置审核通过，任务闭环】 | 回到执行或文档修改环节迭代 |

### 3.2 检查点详细规则

#### CP1：方案自检（步骤4之后）

AI 推导方案后，必须自检以下内容，全部通过才能输出标记：

- [ ] 是否至少有2个可行方案（或说明为什么只有1个）
- [ ] 是否评估了现有能力是否能实现（准则2）
- [ ] 是否从时间/质量/成本三维度评估了最优解（准则3）
- [ ] 是否评估了风险等级（准则7）
- [ ] 是否判断了是否为重要决策需要多方案对比（准则8）

**如全部通过**，输出 `【CP1-方案自检通过】`，进入步骤5。
**如未通过**，回到步骤4补充，不输出标记。

#### CP2：前置审核（步骤7）

**这是最强制的检查点。** AI 必须：

1. 输出完整的方案文档（包含：目标、范围、步骤、风险、回滚方案）
2. 明确告知用户："请确认方案是否可以执行"
3. **等待用户回复**，不自行进入步骤8
4. 用户确认后，输出 `【前置审核通过】`

**豁免条件**（可跳过 CP2，但需在回复中说明）：
- 简单的文本润色/格式调整/内容补充
- 用户明确说"直接做，不用确认"
- 已在之前的对话中获得用户对同类操作的确认

#### CP3：阻塞反馈（步骤8中）

AI 在执行中遇到以下情况时，**必须立即反馈**，不静默等待：

- 工具调用失败且重试1次仍失败
- 需要用户操作（如开VPN、输入密码、确认权限）
- 发现方案有缺陷需要调整
- 执行时间超过预计50%
- 遇到环境问题需要用户解决

反馈格式：`【阻塞反馈】原因：xxx + 需要用户做什么：xxx + 预计影响：xxx`

#### CP4：后置审核（步骤9之后）

AI 完成执行后，必须对照审核标准自检，全部通过才能交付：

- [ ] 需求覆盖：所有需求点是否满足
- [ ] 功能正确：是否能正常运行/使用
- [ ] 边界情况：极端输入是否处理
- [ ] 错误情况：出错时是否有合理处理
- [ ] 格式规范：是否符合项目规范
- [ ] 引用正确：链接/路径是否正确
- [ ] 数据验证：关键数据是否经过验证
- [ ] 台账更新：是否已更新所有台账

**如全部通过**，输出 `【后置审核通过，任务闭环】`，进入步骤10交付。
**如未通过**，输出结构化整改清单，回到执行或文档修改环节迭代，不交付。

## 五、第四层：违规自检与纠正机制

> 解决"如何确保按标准执行"。任务完成后 AI 必须强制自检，发现违规立即纠正并记录。

### 5.1 任务完成强制自检清单（5项）

AI 完成任务后（步骤10之前），必须自检以下5项，全部通过才能标记任务闭环：

| # | 自检项 | 检查内容 | 不通过的处理 |
|:-:|--------|---------|:------------:|
| 1 | **链路完整性** | 是否跳过了10步链路中的任何一步？是否输出了所有检查点标记？ | 补回跳过的步骤 |
| 2 | **约束遵守** | 是否违反了6条强制约束？是否违反了25条行为逻辑？ | 纠正违规行为 |
| 3 | **读取合规** | 是否只读了应该读的部分？是否在没有触发条件的情况下全量读取？ | 记录并改进 |
| 4 | **台账更新** | 是否已更新所有台账（待完成/已完成/工作快照/记忆/索引）？ | 补更新台账 |
| 5 | **交付质量** | 是否通过了CP4后置审核？交付物是否经过验证？ | 回到执行环节改进 |

### 5.2 违规纠正流程

如自检发现违规，按以下流程纠正：

```
发现违规
  ↓
1. 立即停止当前操作
  ↓
2. 承认违规，说明违规内容和原因
  ↓
3. 评估违规影响（是否影响交付物质量/是否需要回滚）
  ↓
4. 执行纠正措施（补回步骤/纠正行为/回滚操作）
  ↓
5. 验证纠正效果
  ↓
6. 记录违规到项目记忆（违规内容/原因/纠正措施/预防措施）
  ↓
7. 重新自检，全部通过后标记任务闭环
```

### 5.3 违规记录格式

所有违规必须记录到项目的 `_memory/MEMORY.md`，格式如下：

```
### 违规记录：[日期] [简要描述]
- 违规内容：具体违反了哪条约束/哪一步链路
- 违规原因：为什么会违反
- 影响评估：对交付物/项目/用户的影响
- 纠正措施：做了什么纠正
- 预防措施：如何避免下次再犯
```

### 5.4 严重违规升级

以下情况属于**严重违规**，必须立即告知用户并暂停所有操作：

| 严重违规类型 | 处理方式 |
|-------------|---------|
| 执行了危险操作（准则21）且未获用户确认 | 立即停止，评估损失，告知用户，准备回滚 |
| 擅自扩大任务范围（准则14）且造成不可逆影响 | 立即停止，告知用户，评估影响，协商解决方案 |
| 跳过CP2前置审核直接执行且造成问题 | 立即停止，回滚到审核前状态，重新走审核流程 |
| 交付未经验证的结果（准则17/18）且造成用户损失 | 立即告知用户，撤回交付物，重新验证后交付 |

## 六、输出格式强制约定

> AI 必须输出以下标记来证明按标准执行。缺少标记视为未执行。

### 6.1 必须输出的标记

| 标记 | 触发时机 | 格式 |

| 【CP1-方案自检通过】 | 步骤4方案自检通过后 | 【CP1-方案自检通过】 |

| 【违规记录】 | 发现违规时 | 【违规记录】内容：xxx + 纠正：xxx |

### 6.2 任务开始时的链路复述

AI 开始执行任务时，必须简要复述当前执行链路：

```
【执行链路】当前步骤：第X步/共10步 — [步骤名称]
触发准则：准则X、准则Y
检查点：无 / CP1 / CP2 / CP3 / CP4
```

### 6.3 任务完成时的交付总结

AI 完成任务时，必须输出交付总结：

```
【交付总结】
- 完成内容：xxx
- 自检结果：5项全部通过 / 存在以下问题：xxx
- 台账更新：已更新 xxx
- 违规记录：无 / 有 xxx
- 后续建议：xxx
```

## 七、用户可触发的检查机制

> 用户可以随时要求 AI 执行以下检查，验证 AI 是否按标准执行。

### 7.1 用户可触发的检查命令

| 用户命令 | AI 必须执行的检查 |
|---------|------------------|
| "检查加载" | 输出当前已加载的所有文档列表，确认是否只读了应该读的部分 |
| "检查链路" | 输出当前10步链路执行到第几步，跳过了哪些步骤，触发了哪些准则 |
| "检查约束" | 输出当前任务是否违反了任何约束，如有则说明违规内容和纠正措施 |
| "检查台账" | 输出台账更新状态（待完成/已完成/工作快照/记忆/索引是否已更新） |
| "检查质量" | 输出交付物的自检结果（CP4的8项是否全部通过） |
| "全面检查" | 执行以上所有检查，输出综合报告 |

### 7.2 用户检查的响应规则

- AI 收到用户检查命令后，**必须立即暂停当前操作**，执行检查
- 检查结果必须如实输出，不得隐瞒违规
- 如检查发现问题，必须立即执行纠正流程（见5.2）
- 检查完成后，如用户未要求继续，AI 应等待用户指示

## 八、灵活配置与优化机制

> 解决"流程过重"问题：本保障机制**仅适用于项目任务**，简单一次性任务和普通办公不走这套流程。项目可根据自身特点灵活配置保障级别。

### 8.1 适用范围明确

| 任务类型 | 是否适用本保障机制 | 说明 |
|---------|:-----------------:|------|
| **项目任务**（代码修改/架构设计/文档创建/批量操作/高风险操作） | ✅ 适用 | 本保障机制的设计目标 |
| **简单一次性任务**（<30分钟、单一明确操作、不涉及代码/架构/高风险） | ⚠️ 简化适用 | 走"简单任务快速通道"（见8.2） |
| **普通办公**（写邮件/整理文档/简单查询/闲聊/游戏） | ❌ 不适用 | 普通对话模式，不走项目流程 |
| **创意探索**（头脑风暴/方案构思/原型验证） | ⚠️ 部分适用 | 保留第一性原理和多方案对比，跳过严格检查点 |

**判断规则**：
- 用户明确说"这是项目任务"或操作项目目录下的文件 → 适用
- 用户说"简单弄一下""快速处理""随便看看" → 简化或不适用
- 不确定时 → 先问用户（准则13先问不猜）

### 8.2 简单任务快速通道

**定义**：同时满足以下条件的任务为简单任务：
1. 预计时间 <30分钟
2. 单一明确操作（用户意图清晰，无歧义）
3. 不涉及代码修改/架构调整/批量文件操作
4. 不涉及高风险/不可逆操作
5. 不影响项目整体方向

**快速通道规则**：

| 环节 | 完整流程 | 简单任务快速通道 |
|------|---------|:----------------:|
| 启动加载 | 必读集合全量加载 | 只读项目AGENTS.md+当前任务相关文档 |
| 10步链路 | 完整10步 | 简化为：解表达→执行→交付（3步） |
| CP1方案自检 | 强制 | 跳过 |
| CP2前置审核 | 强制（涉及代码时） | 跳过（用户已明确要求） |
| CP3阻塞反馈 | 强制 | 保留（遇到问题仍需反馈） |
| CP4后置审核 | 8项自检 | 简化为2项：需求满足+基本验证 |
| 违规自检 | 5项自检 | 跳过（简单任务违规风险低） |
| 台账更新 | 5个台账全更新 | 简化为：只更新已完成任务清单（1条记录） |

**快速通道标记**：简单任务执行时输出 `【简单任务快速通道】`，说明跳过了哪些环节。

### 8.3 渐进式启用（Level 1/2/3）

新项目不必一次性启用全部保障机制，可按项目复杂度和成熟度渐进式启用：

| 级别 | 名称 | 包含内容 | 适用场景 |
|:----:|------|---------|---------|
| **Level 1** | 基础保障 | AGENTS.md + 10步链路 + CP4后置审核 + 台账更新 | 新项目/小项目/探索期项目 |
| **Level 2** | 标准保障 | Level 1 + 行为逻辑框架 + CP2前置审核 + 风险评估 + 违规自检 | 中等复杂度项目/稳定期项目 |
| **Level 3** | 完整保障 | Level 2 + 四层保障机制全量 + CP1方案自检 + 检查点全量 + 用户可触发检查 | 复杂项目/长期项目/高风险项目/多人协作项目 |

**启用建议**：
- 新项目从 Level 1 开始，运行2-4周后评估是否升级
- 升级条件：项目复杂度增加/多人协作/出现质量问题/用户要求更严格
- 降级条件：项目进入维护期/简单维护为主/流程 overhead 过大

### 8.4 项目级灵活配置

每个项目可在自己的 `AGENTS.md` 中定义保障机制配置：

```yaml
# 项目AGENTS.md中的保障机制配置（示例）
guarantee_config:
  level: 2  # 1/2/3
  checkpoints:
    cp1: optional  # mandatory/optional/skip
    cp2: mandatory
    cp3: mandatory
    cp4: mandatory
  simple_task_fast_track: true  # 是否启用简单任务快速通道
  auto_upgrade_threshold: "出现2次质量问题"  # 自动升级触发条件
  project_special_checkpoints:  # 项目特殊检查点
    - "涉及Unity场景修改时，必须验证场景可正常加载"
    - "涉及编译产物修改时，必须验证Harness重启后功能正常"
```

**配置优先级**：
1. 项目 AGENTS.md 中的配置 > 全局默认配置
2. 用户当次明确要求 > 项目配置
3. 安全相关检查点（CP2涉及高风险/安全边界）不可配置为 skip

### 8.5 检查点自动化方向

为减少人工 overhead，以下检查点可逐步自动化：

| 检查点 | 可自动化内容 | 自动化方式 |
|--------|------------|-----------|
| CP4格式检查 | 文件格式/Markdown语法/链接有效性 | 脚本自动检查 |
| CP4语法检查 | 代码语法/编译错误 | 编译器/IDE自动检查 |
| 台账更新 | 任务完成记录自动生成 | 脚本自动追加 |
| 加载完成标记 | 必读集合加载状态自动检测 | 启动脚本自动检查 |
| 违规检测 | 跳过检查点/未输出标记自动检测 | 执行日志分析 |

**原则**：自动化检查通过的可跳过人工检查，但需保留检查记录。

### 8.6 定期效率回顾

为避免流程僵化和 overhead 过大，每季度进行一次效率回顾：

| 回顾项 | 评估方法 | 调整规则 |
|--------|---------|---------|
| 流程 overhead 占比 | 统计检查点/审核/台账时间占总任务时间比例 | >30%时考虑简化或自动化 |
| 检查点有效性 | 统计每个检查点发现的问题数量 | 连续2季度0问题的检查点降级为optional |
| 违规率 | 统计违规自检发现的违规数量 | 违规率>20%时加强培训或升级保障级别 |
| 用户满意度 | 用户反馈流程是否过重 | 用户多次反馈过重时降级或启用快速通道 |
| 质量指标 | 错误交付率/返工率/方向错误率 | 质量指标恶化时升级保障级别 |

**回顾输出**：每季度更新保障机制配置，删除无效约束，优化流程，更新到本文档。

## 九、附录：快速检查清单

> 一页纸快速参考，AI 可在执行中随时对照。

### 启动时（3项）
- [ ] 已读取项目 AGENTS.md
- [ ] 已按分层加载协议加载必读集合
- [ ] 已输出【加载完成】标记

### 执行中（4个检查点）
- [ ] CP1：方案自检通过（至少2方案+能力评估+风险评估）
- [ ] CP2：前置审核通过（用户已确认方案）
- [ ] CP3：阻塞时已反馈（不静默等待）
- [ ] CP4：后置审核通过（8项自检全部通过）

### 行为逻辑（按步骤触发）
- 步骤1-2：先问不猜 + 第一性原理
- 步骤3-4：能力评估 + 多方案对比 + 最优解平衡
- 步骤5-7：风险评估 + 先确认不擅决
- 步骤8：进度反馈 + 三次失败换方案 + 根因优先 + 环境诊断
- 步骤9：交付前自检 + 事实验证 + 交叉验证
- 步骤10：反馈即改 + 经验沉淀 + 台账更新

### 完成时（5项自检）
- [ ] 链路完整性：未跳过任何步骤
- [ ] 约束遵守：未违反任何约束
- [ ] 读取合规：只读了应该读的部分
- [ ] 台账更新：所有台账已更新
- [ ] 交付质量：CP4自检通过

### 优先级（冲突时）
P0：安全边界 > 风险评估 > P1：先确认 > 先问不猜 > P2：根因优先 > 三次失败换方案 > P3：交付自检 > 事实验证 > P4：其他
