## 一、项目概述

### 1.1 定位

**DeepSeek Harness 总监驾驶舱插件** —— 走 Harness 官方 client 插件通道的独立插件包。

核心定位：**总监是"沟通与治理层"，对话是"执行与产出层"。两者数据元完全独立、界面并排可见、消息双向联动；总监不执行，只负责确定上下文、派活、审核、纠偏、路由。**

### 1.2 交付物

| 项 | 内容 |
|:---|:-----|
| 插件包 | `dsh-director-plugin/` |
| 构建产物 | `lib/client.js`（964,872 B / 58 模块） |
| 绑定对账 | 474 = 474 / 185 条 import |
| 注入点 | `inject = ["slots","sessions"]` |
| 源码规模 | 60 个 js 文件 / 16,903 行 |
| 脚本规模 | 59 个脚本 / 15,307 行 |
| 闸门规模 | 离线 22 套全绿 · 真机五套各连跑 3 次全绿 |

### 1.3 界面结构

**宿主三页签**：【总监】【对话】【轨迹】

**三浮层**：
1. 设计图工作室（全屏铺满 · 可拖拽编辑 · 左侧交互逻辑 · 底部专用对话）
2. 思维导图（分支血缘树 · 缩滚展开 · 待总监路由）
3. 总监弹窗（要求 5/6/7/8/9/10/11 的落位）

**四处右上角共用同一个个性化设定面板**：总监页 / 总监弹窗 / 分支导图 / 设计图工作室

**右下角浮动按钮组**（FloatDock）：三浮层统一入口

## 二、核心架构与业务不变量（11 条要求 · 最高效力）

> 以下 11 条为业务不变量，**只增不改**。任何实现、设计稿、任务清单与之冲突时，以本节为准。

### 要求 1 — 总监与对话必须使用各自独立的数据元

| 项 | 内容 |
|:---|:-----|
| 硬约束 | ① 两者不得共用同一 object store；② 不得以"前缀/字段约定"冒充隔离；③ 总监域数据宿主不消费，对话域数据插件只读 |
| 落地 | 总监域 = `dsh-director-plugin-db` v1（插件独有，6 个 store）；对话域 = `dsh-director-db` v3（宿主拥有，R5 冻结） |
| 交叉点 | 唯一允许：`nodeId` ↔ 宿主的 `workspaceId`/`sessionId`（只读外键）。禁止联合查询、跨库事务、把宿主记录读进总监 store 后落盘 |

**总监域 6 个 store**：

| Store | keyPath | 索引 | 用途 |
|:------|:--------|:------|:-----|
| `directorNodes` | `nodeId` | `level`, `parentId` | 层级总监节点（global/project/folder/session） |
| `directorConversations` | `messageId` | `nodeId`, `createdAt` | 总监自己的对话 |
| `directorPlans` | `planId` | `nodeId` | 总监制定的方案与执行约束 |
| `directorReviews` | `reviewId` | `nodeId`, `targetId` | 六维审核记录 |
| `directorDecisions` | `decisionId` | `nodeId` | 决策与纠偏留痕 |
| `directorTodos` | `todoId` | `nodeId` | 派活/待办 |

### 要求 2 — 总监统筹当前对话；每个总监都要有自己的对话；总监不执行

- 总监有且仅有一个职责面：**治理** —— 不得代为执行具体任务
- 总监自己也是一路对话（有消息流、有输入、有历史），内容 = 需求澄清/方案/派活/审核意见/纠偏指令
- 执行产出只出现在对话域

### 要求 3 — 总监完整职责：定上下文 / 保产出达标 / 审核产出 / 防跑偏 / 按文档与用户想法纠偏

**六维审核（不得减项）**：
1. **需求满足度**（核心需求 100% 覆盖 / 可选项标注 / 约束遵守）
2. **方案符合度**（约束遵守 / 范围一致 / 变更可追溯）
3. **质量达标度**（符合智能体标准 / 功能可验证 / 性能可接受）
4. **风险控制**（无新增 Bug / 无安全风险 / 遗留问题记录）
5. **完整性**（无遗漏 / 文档完整 / 边界覆盖）
6. **一致性**（方向一致 / 规范一致 / 决策一致）

**纠偏义务**：依"文档 + 用户想法"两个基准对执行纠偏；纠偏须留痕（写入 `directorDecisions`）

### 要求 4 — 对话保持原有对话逻辑不变

- 不改宿主 `ChatView` 渲染路径
- 不改原生 InputBar 提交语义
- 对话域数据 schema 与 key 不得变更
- 宿主 `client.js` 零改动

### 要求 5 — 总监页面：左侧总监 + 右侧对话数据；右侧须与对话 tab 完全一致

**技术通道（已定案：方案 C · 布局分屏）**：
- 右栏不是副本，而是**原生对话区本体** —— 给原生根注入 `padding-left` 把它挤窄，露出的那一段就是原生 DOM
- 同一节点 / 同一渲染器 / 同一 store ⇒ "完全一致"从"需要保证的性质"退化为同义反复
- 零节点移动 ⇒ 零 React 风险、可逆性实测逐值复原

**分屏锚点判据（四步 + 两条硬约束）**：
1. 排除插件自身 DOM：`el.closest(PLUGIN_UI_SELECTOR)` 命中即 continue
2. 尺寸窗口：`height ≥ 90%vh` 且 `40%vw < width < 98%vw`
3. 跳过滚动容器：`getComputedStyle(el).overflowX ∈ {auto, scroll, hidden}`
4. 兜底只用 `textarea`，不用 `input[type=text]`
5. 取最深合法祖先，不取最浅
6. `applySplit()` 自身再挡一道：`isPluginNode(root)` ⇒ 返回 `{ok:false}`

### 要求 6 — 两者均为弹窗形式，并允许最小化

- 总监页为**覆盖式弹窗**（overlay），非嵌入 tab 内容；非模态（不锁滚动、不锁焦点、可拖拽、可并行操作）
- 左侧总监面板与右侧对话面板**各自可独立最小化**
- 整个弹窗可整体最小化为一个 chip
- 折叠/展开/宽度状态持久化（key = `dsh.director.layout`，R5 冻结，只允许新增字段）

**最小化规格**：

| 操作 | 行为 | 状态字段 |
|:-----|:-----|:---------|
| 左栏最小化 | 收成 40px 竖条（显示"总监"+ 展开钮 + 控制簇） | `directorPanelCollapsed` |
| 右栏最小化 | 收成 40px 竖条（显示"对话"+ 展开钮） | `chatPanelCollapsed` |
| 整窗最小化 | 收成右下角 chip（层级名 + 未读计数），点击还原 | `dialogCollapsed`（新增字段） |
| 复位栏宽 | 恢复 300/300；双击中缝同效 | `directorPanelWidth`/`chatPanelWidth` |
| 拖拽中缝 | `clamp(180, 55%×W)`；`<180px` 自动吸附折叠 | 同上 |

**折叠态控制可达性（硬要求）**：左栏折叠后，右栏折叠/复位/整窗最小化/关闭必须仍可达。控制簇随 rail 内置，各自 `stopPropagation()`。

### 要求 7 — 点击文件夹或项目时，展示负责该文件夹或项目的总监

- 层级 = 全局 / 项目 / 文件夹 / 对话 四层（`LEVEL` 单一真相源）
- 点击左侧文件夹或项目 → 弹出该层级的总监（内容随层级切换，外壳不变）
- 总监的职责配置**自底向上解析**（会话 → 项目 → 全局 → 默认）

### 要求 8 — 只保留一个总监页面；输入后由总监判断应进哪个对话，并可转派/直调

- 总监页面只有一个（不做"每层一个独立页面"）
- 用户向总监输入 → 总监整理 + 确认 → 判定归属对话
- 三条去向：**转给该对话的总监** / **直接调用对应对话** / **新建对话**
- 路由结果必须可确认、可回看（不得静默分发）

### 要求 9 — 上层项目文件同样拥有自己的总监

- 项目级/文件夹级总监与其下对话级总监同构（同一套数据结构与界面）
- 上层总监可访问其下所有层级数据（用于汇总与调度）
- 反之不可（下级看不到上级全局）

### 要求 10 — 总监页面需包含智能体与技能，可查看调用情况并主动选择调用

- 智能体与技能在同一行内分段切换
- 必须能看调用情况（谁在跑 / 历史调用）
- 必须能主动选择调用（用户手选）
- 调用方式须标注：总监自动决定 / 客户手选
- 5 类标准智能体：代码 / 文档 / 调研 / 测试 / 审核，各带执行标准 + 检查清单 + 推荐模型

### 要求 11 — 总监还需体现设计图的逻辑

**R1–R8 区域契约**：

| 区域 | 内容 |
|:-----|:-----|
| R1 | 顶部固定栏 |
| R2 | 项目总览卡片（定位/目标/阶段/进度/风险数/待办数） |
| R3 | 智能体/技能切换行（行尾标注调用方式） |
| R4 | 项目导航（文档树/路线图待办/关键文件） |
| R5 | 总监对话区 |
| R6 | 总监记忆面板（核心记忆/决策记录/偏差风险，hover 展开） |
| R7 | a-2 小窗（对话/文档/项目详情） |
| R8 | 全局输入框 + 焦点路由 |

### 3.2 数据流

```
用户输入
  │
  ├─→ 焦点路由（focusTarget: director/chat）
  │     │
  │     ├─ director → 总监治理链路
  │     │     ├→ director-run（五步执行）
  │     │     ├→ routing（智能路由 + 六维审核）
  │     │     ├→ orchestrate（统筹闭环）
  │     │     └→ directorConversations（总监消息流）
  │     │
  │     └─ chat → 原生对话提交（宿主原逻辑，零改动）
  │           └→ 对话域消息（总监侧只读订阅 → 触发审核/纠偏）
  │
  └─→ 四维流转（flow.js）
        ├→ 总监页同步
        ├→ 对话 tab 同步
        ├→ 思维导图同步
        └→ 设计图工作室同步
```

### 3.3 构建与安装

**构建**：`node build/build.mjs` → 产物 `lib/client.js`（React 平台外置，不打包）

**安装**（三处安装点）：
1. 实体包：`<Harness>/resources/host/node_modules/@deepseek-ai/dsh-director-plugin/`
2. profile junction：`~/.dsh/profiles/node_modules/...`
3. patch 配置：`~/.dsh/profiles/web/cordis.patch.yml`（entry `deepseek-ai.director`）

**安装器**：`scripts/plugin-install.mjs`
- `verify`（默认，零写入）
- `--apply`（幂等 + 写后逐文件回读校验）
- `--uninstall`（外科式只删本插件 entry）
- `--purge`

**生效条件**：重启 Harness（插件在 boot 时装载）。启动命令需 `env -u ELECTRON_RUN_AS_NODE`。

### 3.4 开发环境搭建

```bash
# 1. 确认 Node 版本（≥ 22）
node --version

# 2. 克隆/进入项目
cd dsh-client-mod

# 3. 跑基线校验（确认代码未漂移）
cd dsh-director-plugin
node scripts/baseline-check.mjs
# 预期输出：IS_PASS: TRUE（漂移=0）

# 4. 确认 Harness 安装路径
# 默认：C:\Users\<用户>\AppData\Local\Programs\deepseek-harness\
# 配置文件：dsh-director-plugin/scripts/_harness-paths.mjs

# 5. 构建 + 装机 + 重启（标准 7 步，见 §八 8.4）
node build/build.mjs
node scripts/plugin-install.mjs --apply
# 重启 Harness（后台方式 + env -u ELECTRON_RUN_AS_NODE）
```

**环境变量**：
- `ELECTRON_RUN_AS_NODE`：启动 Harness 时必须取消设置（`env -u`），否则 Electron 以 Node 模式运行，不加载插件
- `DSH_DEBUG`：设为 `1` 开启调试日志（`util/debug.js`）
- VPN：访问外网时需开启，连接失败即表示未开

### 3.5 新增功能代码指南

**新增一个组件**（如 `components/NewFeature.js`）：
1. 在 `src/components/` 下创建文件，顶部加 `@map` 块（职责/引用/上游/下游/设计稿板块）
2. 组件必须裹 `SafeLayer` 错误边界（宿主无 React 错误边界，单层崩溃卸载整棵 Shell 根）
3. 在 `client-entry.js` 中注册（如需要）
4. 跑 `node scripts/gen-source-map.mjs` 刷新映射
5. 跑离线闸门 + 构建 + 装机 + 真机 e2e

**新增一个 store**（如 `store/new-store.js`）：
1. 在 `src/store/` 下创建文件，遵循现有 store 模式（`createStore` 工厂 / `useStore` hook）
2. 如涉及持久化，在 `store/persist.js` 中注册加载/保存
3. 如涉及 IndexedDB，在 `store/idb.js` 或 `store/plugin-db.js` 中注册 object store
4. **R5 冻结**：不得改名已有 key/DB/store，只允许新增

**新增一个逻辑模块**（如 `logic/new-logic.js`）：
1. 优先写**纯函数**（不依赖 React/浏览器 API），便于单元测试
2. 顶部加 `@map` 块
3. 在 `client-entry.js` 中导入（如需要）
4. 配套写单元测试（`scripts/test-*.mjs`）

**新增一个闸门/验证脚本**（如 `scripts/verify-new-feature.mjs`）：
1. 顶部加正确用法注释（`node --import ./scripts/_platform-stub.mjs scripts/verify-new-feature.mjs`）
2. 退出码约定：0 通过 / 1 FAIL / 2 INVALID
3. 必须用**正负对照校准**（正对照应报红，负对照应不报）
4. 凡"点了会写盘/落库"的段，都要快照 + 还原 + 还原断言
5. 判据一律"跑程内"（不依赖持久化/累积的页面状态）

## 五、交互设计

### 5.1 页面流转

```
宿主三页签
  ├─ 总监 tab → DirectorPage（总监页）
  │    ├─ 右下角 FloatDock → 三浮层入口
  │    │    ├─ 设计图工作室（DesignStudio，全屏铺满）
  │    │    ├─ 思维导图（MindMap，覆盖层）
  │    │    └─ 总监弹窗（DirectorDialog，覆盖层）
  │    └─ 右上角 → 个性化面板（PersonalizePanel）
  ├─ 对话 tab → 原生对话（零改动）
  └─ 轨迹 tab → 原生轨迹（零改动）

浮层间关系：
  - 三浮层互不拖死（各自独立 SafeLayer 错误边界）
  - 设计图工作室全屏时，其他浮层最小化
  - 思维导图覆盖层可与总监弹窗共存
  - 总监弹窗可从总监页/思维导图/设计图工作室唤起
```

### 5.2 焦点路由

- `focusTarget ∈ { "director", "chat" }`
- 点击左区 → `director`，点击右区 → `chat`
- 全局输入框按 `focusTarget` 决定提交目标
- 输入框左侧显示当前目标徽章（可点开手选）
- 快捷键：`Alt+D` / `Alt+C` 切换提交目标

**判定粒度（四规则）**：
1. 只认容器事件（`pointerdown`，不认 `click`）
2. 排除内部输入元素（`[data-input-scope]` 命中提前返回）
3. 输入框优先（输入框自身聚焦时以输入框的 target 为准）
4. 无副作用（只写 `focusTarget`，不改消息/提交队列）

### 5.3 键盘路径

| 快捷键 | 行为 | 作用域 |
|:-------|:-----|:-------|
| `Alt+1` | 整窗最小化 ⇄ 还原 | 弹窗激活时 |
| `Alt+2` | 左栏折叠 ⇄ 展开 | 弹窗激活时 |
| `Alt+3` | 右栏折叠 ⇄ 展开 | 弹窗激活时 |
| `Alt+D` / `Alt+C` | 切换提交目标（总监/对话） | 弹窗激活时 |
| `Esc` | 关闭弹窗（先关内层弹层，再关弹窗） | 弹窗激活时 |
| `Tab` / `Shift+Tab` | 弹窗内循环遍历（焦点不逃逸） | 弹窗激活时 |
| `Enter` / `Shift+Enter` | 发送 / 换行 | 输入框聚焦时 |

### 5.4 状态机（弹窗三态）

```
                    ┌─────────────┐
                    │   正常展开   │
                    │ (双栏可见)   │
                    └──────┬──────┘
           ┌───────────────┼───────────────┐
           ▼               ▼               ▼
    ┌────────────┐  ┌────────────┐  ┌────────────┐
    │ 左栏最小化  │  │ 右栏最小化  │  │ 整窗最小化  │
    │ (40px rail)│  │ (40px rail)│  │ (chip)     │
    └──────┬─────┘  └──────┬─────┘  └──────┬─────┘
           │                 │                 │
           └─────────────────┴─────────────────┘
                              │
                              ▼
                        恢复正常展开
```

### 5.5 边界条件

- **空数据**：首次使用无总监节点时，自动创建全局级总监
- **超大数据**：思维导图节点超过 100 时，启用虚拟化渲染
- **网络中断**：IndexedDB 本地优先，网络恢复后不影响
- **窗口缩放**：断点 ≥880px 双栏展开 / <880px 右栏收窄条 / <640px 双栏自动折叠
- **权限不足**：插件注册失败时，在控制台输出可诊断的错误信息（注册失败也要能看到原因）

### 8.5 测试陷阱（两条最容易踩）

1. **坐标必须视口内且命中测试为自己** —— 画布滚动后第一个节点可能是 `x=-934`，事件打空却像"功能坏了"。改用 `focusVisibleNode()`。
2. **不要无条件按 Esc** —— 无菜单时它关闭整张导图，会让其后所有断言都在量一个已卸载的 DOM。

### 8.6 闸门纠错通则（从 13 处纠错中提炼）

1. **凡"点了会写盘/落库"的闸门段，都要快照 + 还原 + 还原断言** —— 否则闸门就是产品的破坏者
2. **判据一律"跑程内"** —— 只要被测面是持久化/累积的，"页面上有没有这几个字"就既可能假绿也可能假红
3. **尺子量对容器** —— 五步区与 `director-messages` 是兄弟节点，量错容器恒 false
4. **属性名不撞车** —— `data-dim` 被审核维度与四维流转徽标共用，一个根因连爆 3 红
5. **桩/尺寸不写死** —— 同一份平台桩抄两份必漂移，用共享桩 `_platform-modules.mjs`
6. **闸门不把整个脚本打哑** —— null 解引用在 600 行把整个脚本打哑，其后 100+ 断言静默丢失
7. **跳过比红更危险** —— 红有人看，跳过没人看；可见集取错/用常数坐标代表空白点会制造假跳过

### 8.7 文档自验证（本文档与代码一致性校验）

每次代码修改后，必须验证本文档与代码的一致性：

## 九、部署与回滚

### 9.1 构建

- 构建器：`build/build.mjs`
- 产物：`lib/client.js`（React 平台外置，不打包）
- 构建模板字符串内禁用反引号（构建期被当模板字面量求值）
- 写盘必须显式 LF（Windows 文本模式会转 CRLF，导致假重写 diff）

### 9.2 安装

- 安装器：`scripts/plugin-install.mjs`
- 三处安装点（见 §三 3.3）
- `--apply` 幂等 + 写后逐文件回读校验
- 不得删 `Network` 目录（那是 Chromium 的 cookie 存储，内含 `dsh_director_*` 持久化 cookie）

### 9.3 回滚

- `--uninstall`：外科式只删本插件 entry
- `--purge`：完全清除
- git 历史即备份（项目由 git 管理）
- 基线指纹：`BASELINE.lock.json`（64 文件 md5），`baseline-check.mjs --write` 重新封存

### 9.4 数据迁移与应急

**数据迁移流程**（总监域从宿主 `memoryCore` 迁移到插件独立库 `dsh-director-plugin-db` v1）：

| 阶段 | 动作 | 安全性 |
|:----:|:-----|:-------|
| 1 | 新建 `dsh-director-plugin-db` v1，首次打开自动建库（`onupgradeneeded` 只在本库触发） | 宿主不可见、不可感 |
| 2 | 读取期双读：优先新库；新库无该节点时回落旧 `memoryCore`（只读） | 存量不丢 |
| 3 | 迁移期把旧 `memoryCore` 中的层级节点（`level` ∈ 白名单）拷贝入新库 `directorNodes` | 幂等（按 `nodeId` upsert） |
| 4 | 迁移完成并验证后，停止回落到旧库；旧记录不删（尊重锚点契约"历史数据保留"） | 可回滚 |

**用户数据丢失应急流程**：

1. **发现数据丢失**：用户报告总监数据/设计图/记忆丢失
2. **立即停止写入**：关闭 Harness，防止新数据覆盖旧数据
3. **检查冷备**：设计图有 IndexedDB 冷备（`plugin-db.js`），检查是否可恢复
4. **检查 cookie**：`dsh_director_*` 持久化 cookie 是否存在（**不得删 `Network` 目录**）
5. **检查 localStorage**：按 origin 分区，Harness 端口变化可能导致主存丢失
6. **从 git 恢复**：代码可从 git 恢复；用户数据如未备份则不可恢复
7. **记录事故**：写入 `_memory/MEMORY.md` 违规记录/事故记录

**预防措施**：
- 关键数据双写（localStorage + IndexedDB）
- 设计图冷备库独立于主存
- 安装器 `--apply` 写后逐文件回读校验
- 基线指纹 `BASELINE.lock.json` 防止代码漂移
- **禁止删 `Network` 目录**（那是 cookie 存储）

### 9.5 重启陷阱

- 插件在 boot 时装载，不重启不生效
- 启动命令需 `env -u ELECTRON_RUN_AS_NODE`（否则 Electron 以 Node 模式运行，不加载插件）
- Harness 端口每次启动变化 ⇒ localStorage 按 origin 分区 ⇒ 主存有丢失风险，设计图有 IndexedDB 冷备

## 十、风险与约束

### 10.1 技术风险

| 风险 | 等级 | 缓解措施 |
|:-----|:-----|:---------|
| 宿主无 React 错误边界 ⇒ 单层崩溃卸载整棵 Shell 根 | 高 | 每层裹 `SafeLayer`，新增浮层必须照做 |
| 数据迁移风险 ⇒ 从宿主 memoryCore 迁移到插件独立库时数据丢失 | 高 | 双读过渡期 + 幂等 upsert + 旧记录不删 + 迁移验证后才停止回落 |
| 持久化的"打开态"是自锁死放大器 | 中 | 凡 `open && 数据为 null` 的组合必须判空 |
| Harness 端口变化 ⇒ localStorage 主存丢失 | 中 | 设计图有 IndexedDB 冷备；关键数据双写 |
| 构建模板字符串反引号陷阱 | 低 | 构建期禁用反引号，lint 检查 |
| Windows 文本模式 CRLF 转换 | 低 | 写盘显式 LF |

### 10.2 已知限制

- `review.js`（对话返回审核）保留能力，当前无调用点
- `spike-fs-probe.js`（R3 风险验证）为探针，非生产路径
- `layout-probe.js`（布局探针）为开发辅助
- 上下文压缩（V12 视图 5）为后续迭代
- T-PLUG-030「文档上下文」死链路已登记未做（`docs` 是 map 却当数组用 ⇒ 文案恒「共undefined篇文档」+ TypeError 被 `catch {}` 静默吞掉）

### 10.3 兼容性约束

- 宿主 `client.js` 零改动（要求 4）
- R5 冻结契约不可改名（见 §七 7.1）
- React 平台外置（不打包，依赖宿主提供）
- IndexedDB 版本协商：新建 `dsh-director-plugin-db` v1 不参与宿主的 `dsh-director-db` v3 版本协商
