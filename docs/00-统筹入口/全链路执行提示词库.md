# dsh-client-mod 全链路执行提示词库

> **用途**：每个行为执行前必须加载对应提示词，确保行为标准化、可追溯、可复用。
> **创建**：2026-09-13
> **原则**：没有符合的提示词就新建，新建后必须登记到本库。

---

## 〇、通用元提示词（所有行为前加载）

### META-01：行为前置自检
```
执行任何操作前，必须确认：
1. 当前阶段是什么？目标是什么？
2. 上一步的输出是否已验证？
3. 本操作是否在用户授权范围内？
4. 本操作是否有不可逆风险？如有，是否已备份？
5. 本操作完成后如何验证？
```

### META-02：最小读取原则
```
读取文件时：
1. 先读索引/目录，定位目标文件
2. 大文件优先读头部（映射头/摘要/目录）
3. 需要细节时用 offset/limit 局部读取
4. 禁止全量加载无关文件
```

### META-03：写操作回读校验
```
任何写操作（文件修改/配置写入/数据持久化）后：
1. 立即回读实际值
2. 与预期值逐字比对
3. 不一致则立即回滚并报告
4. 返回成功 ≠ 落库正确
```

## 一、阶段1：全面盘点提示词

### AUDIT-01：源码文件盘点
```
对每个源码文件，提取并记录：
1. 文件路径（相对项目根）
2. 行数/字节数
3. 顶部 @map 块中的职责描述
4. 导出的函数/组件/常量清单
5. 上游（谁 import 我）
6. 下游（我 import 谁）
7. 对应的设计稿板块
8. 对应的需求编号
```

### AUDIT-02：脚本文件盘点
```
对每个脚本文件，提取并记录：
1. 脚本路径
2. 脚本类型（闸门/验证/安装/构建/辅助/探针）
3. 入口函数/主流程
4. 预期输出格式（退出码/断言数/报告）
5. 依赖的环境/前置条件
6. 基线结果（当前通过数/总数）
7. 是否在标准工作流中被引用
```

### AUDIT-03：文档盘点
```
对每个文档，提取并记录：
1. 文档路径
2. 文档类型（规范/方案/记录/索引/设计稿/审核报告）
3. 创建日期/最后更新日期
4. 核心内容摘要（3句话以内）
5. 状态（活跃/历史/已归档/待更新）
6. 被哪些文档/脚本引用
7. 是否包含可执行的开发要求
```

### AUDIT-04：函数级盘点
```
对关键函数（导出函数/组件主函数/闸门断言函数），记录：
1. 函数名
2. 所在文件
3. 函数签名（参数/返回值）
4. 核心职责（一句话）
5. 调用链（谁调用它/它调用谁）
6. 副作用（是否写盘/改全局状态/发网络请求）
7. 对应的测试覆盖
```

## 二、阶段2：开发文档汇总提示词

### DOC-01：需求提取
```
从所有开发文档中提取开发要求，按以下维度分类：
1. 功能需求（必须实现的功能）
2. 交互需求（用户操作流程/状态变化）
3. 视觉需求（布局/配色/字体/间距）
4. 数据需求（数据模型/持久化/契约）
5. 性能需求（响应时间/并发/资源占用）
6. 兼容性需求（平台/版本/降级）
7. 安全需求（权限/数据保护/防注入）
每条需求必须标注：来源文档+章节+原文引用+优先级（P0/P1/P2）
```

### DOC-02：冲突检测
```
对比所有开发要求，检测冲突：
1. 同一功能在不同文档中有矛盾描述
2. 同一数据字段有不同定义
3. 同一交互有不同流程
4. 视觉规范不一致（颜色/尺寸/间距）
5. 已废弃的要求仍在活跃文档中
冲突必须标注：冲突双方+各自原文+建议解决方案
```

### DOC-03：汇总文档结构
```
最终开发文档必须包含以下章节：
1. 项目概述（定位/目标/范围）
2. 技术架构（模块划分/数据流/依赖关系）
3. 功能规格（按模块列出所有功能需求）
4. 交互设计（页面流转/状态机/操作流程）
5. 视觉规范（设计令牌/组件规范/布局规则）
6. 数据模型（schema/契约/持久化方案）
7. 接口定义（内部API/外部集成/事件总线）
8. 测试策略（单元/集成/e2e/验收标准）
9. 部署方案（构建/安装/配置/回滚）
10. 风险与约束（已知限制/技术债/兼容性）
11. 变更记录（版本演进/决策记录）
```

## 三、阶段3：清理整理提示词

### CLEAN-01：冗余判定标准
```
判定一个文件是否"多余"，必须同时满足：
1. 没有任何其他文件/脚本/文档引用它（grep 全仓零命中）
2. 不在标准工作流中被执行
3. 不是契约锚点（localStorage key/DB schema/DOM锚点的定义源）
4. 不是基线指纹的组成部分
5. 不是用户数据或配置
6. 删除后不影响任何闸门通过
7. 删除后不影响构建/安装/运行
满足全部7条才可标记为"可删除"。
```

### CLEAN-02：截图清理
```
截图文件的清理标准：
1. 被文档引用的截图 → 保留（移动到对应文档的 assets 目录）
2. 闸门验证的证据截图 → 保留最新3轮，旧的归档
3. 调试/临时截图 → 确认无引用后删除
4. 重复截图（内容相同/相似）→ 保留最清晰的一张
5. 命名混乱的截图 → 重命名为有意义的名称
```

### CLEAN-03：目录整理
```
整理后的目录结构必须满足：
1. 每个目录有明确的职责（在目录 README 或索引中说明）
2. 同类文件放在同一目录
3. 历史文件归档到 90-历史归档/
4. 临时文件不留在主目录
5. 构建产物不与源码混放
6. 每个文件都能在索引中找到
```

## 四、阶段4：需求统筹与设计提示词

### DESIGN-01：需求统筹
```
统筹用户需求时，必须：
1. 区分"显性需求"（用户明确说出的）和"隐性需求"（用户没说但必须有的）
2. 按 MoSCoW 分级：Must have / Should have / Could have / Won't have
3. 识别需求间的依赖关系和冲突
4. 评估每个需求的实现成本和风险
5. 与现有功能对比，识别增量和变更
6. 输出需求矩阵：需求描述/来源/优先级/依赖/估时/状态
```

### DESIGN-02：设计图规范
```
设计图必须包含：
1. 高保真界面（真实尺寸/真实配色/真实字体）
2. 标注层（尺寸/间距/颜色值/字体规格）
3. 交互说明（每个可点击元素的行为/状态变化）
4. 状态全集（默认/hover/active/focus/disabled/loading/error/empty）
5. 响应式说明（不同视口下的布局变化）
6. 组件清单（用到的所有组件及其变体）
7. 设计令牌（颜色/字体/间距/圆角/阴影的变量定义）
```

### DESIGN-03：交互流程设计
```
交互流程文档必须包含：
1. 页面流转图（页面间的导航关系）
2. 状态机（每个核心功能的状态转换）
3. 操作序列（典型用户操作的逐步说明）
4. 异常流程（错误处理/降级/回退）
5. 快捷键清单
6. 无障碍要求（键盘导航/屏幕阅读器/对比度）
7. 边界条件（空数据/超大数据/网络中断/权限不足）
```

## 五、阶段5：备份与提交提示词

### BACKUP-01：代码备份
```
代码修改前的备份流程：
1. 确认当前工作区干净（git status 无未提交变更）
2. 全量打包整个项目目录（排除 .git/node_modules/original/workspace）
3. 备份文件命名：dsh-client-mod-backup-YYYYMMDD-HHMMSS.zip
4. 备份存放位置：项目外的安全目录
5. 验证备份完整性（解压抽查关键文件）
6. 记录备份信息（时间/包含内容/大小/MD5）
```

### BACKUP-02：GitHub提交
```
GitHub提交流程：
1. 确认远程仓库配置（git remote -v）
2. 检查网络连通性（VPN是否开启）
3. git add 所有变更文件
4. git commit -m "描述本次变更的类型和内容"
5. git push 到远程
6. 验证推送成功（git log 远程一致）
7. 如网络不可用，记录为待办，本地提交保留
```

## 六、阶段6：代码修改提示词

### CODE-01：修改前置检查
```
修改代码前必须确认：
1. 基线校验通过（漂移=0）
2. 设计文档已审核通过
3. 备份已完成
4. 明确修改范围（哪些文件/哪些函数）
5. 明确修改目标（要解决什么问题/实现什么功能）
6. 明确验证方法（改完后跑哪些闸门）
7. 明确回滚方案（改坏了怎么恢复）
```

### CODE-02：修改执行规范
```
修改代码时必须遵守：
1. 只改被点名的范围，不"顺手优化"无关代码
2. 保持代码风格与现有代码一致
3. 新增函数必须有 JSDoc 注释
4. 修改点必须留三元组注释：🔴 现象 → 原因 → 正确做法
5. 不触碰冻结契约（R5）
6. 构建模板字符串内禁用反引号
7. 写盘必须显式 LF
8. 改完立即跑相关离线闸门
```

### CODE-03：修改后验证
```
代码修改后必须验证：
1. node --check 语法通过
2. 相关离线闸门全绿
3. 构建成功（产物字节数/模块数/绑定对账）
4. 安装成功（逐文件回读一致）
5. 重启 Harness 后装载自检通过
6. 真机 e2e 全绿（连跑3次）
7. 视觉改动必须截图复验
8. 更新基线文档并重新封存指纹
```

## 七、阶段7：测试与审核提示词

### TEST-01：测试计划编写
```
测试计划必须包含：
1. 测试目标（本次测试要验证什么）
2. 测试范围（哪些功能/哪些页面/哪些接口）
3. 测试环境（操作系统/浏览器版本/Harness版本/网络条件）
4. 测试数据（前置数据/测试用例数据/预期结果）
5. 测试用例清单（编号/名称/前置条件/操作步骤/预期结果/优先级）
6. 测试执行顺序（依赖关系/并行可能）
7. 通过标准（每条用例的验收条件）
8. 缺陷记录规范（严重等级/复现步骤/截图/日志）
```

### TEST-02：人类行为模拟
```
模拟人类测试时必须：
1. 用真实鼠标点击（不用内部API抄近路）
2. 用真实键盘输入（不用脚本直接设值）
3. 操作间留合理间隔（人类反应时间100-500ms）
4. 测试常见误操作（连续点击/快速切换/输入中途取消）
5. 测试边界场景（空数据/超大数据/网络慢/窗口缩放）
6. 测试视觉一致性（截图对比/计算样式回读）
7. 测试状态持久化（刷新后/重启后状态是否保留）
8. 测试错误恢复（出错后能否正常回退/重试）
```

### TEST-03：三轮审核闭环
```
每个核心产出物必须经过至少三轮审核：
第一轮：完整性审核（是否覆盖所有需求/有无遗漏）
第二轮：准确性审核（事实/数字/引用是否准确/有无矛盾）
第三轮：可执行性审核（是否可直接执行/有无模糊表述/有无TODO占位）
每轮必须：
1. 打分（0-10分，7维度：完整性2/准确性2/可执行性2/规范性1/一致性1/风险覆盖1/可验证性1）
2. 输出整改清单（问题位置/问题描述/整改建议）
3. 整改后重新审核
4. 第3轮<10分必须继续，直到10分
```

### TEST-04：缺陷分级与处理
```
缺陷按严重程度分级：
P0 阻断：功能完全不可用/数据丢失/安全漏洞 → 必须立即修复，修复后全量回归
P1 严重：核心功能异常/主要流程不通/视觉严重错乱 → 本轮必须修复
P2 一般：次要功能异常/边缘场景问题/视觉小瑕疵 → 记录待办，下轮修复
P3 建议：优化建议/体验提升/代码重构 → 记录待办，评估后决定
每个缺陷必须记录：编号/标题/严重等级/复现步骤/预期结果/实际结果/截图/日志/修复状态
```

## 八、通用审核提示词

### REVIEW-01：文档审核清单
```
审核文档时逐项检查：
1. 结构是否清晰（章节划分/层级/编号）
2. 内容是否完整（有无遗漏/有无TODO占位）
3. 事实是否准确（数字/引用/日期/版本号）
4. 逻辑是否一致（前后矛盾/因果关系/推理链）
5. 表述是否明确（有无模糊用词/有无歧义）
6. 格式是否规范（命名/排版/表格/代码块）
7. 引用是否有效（链接是否可达/引用文档是否存在）
8. 是否可执行（读完能否直接动手/有无缺失步骤）
```

### REVIEW-02：代码审核清单
```
审核代码时逐项检查：
1. 语法是否正确（node --check）
2. 逻辑是否正确（边界条件/异常处理/并发安全）
3. 是否符合项目规范（命名/注释/结构/模式）
4. 是否触碰冻结契约（R5 key/schema/锚点）
5. 是否有安全隐患（注入/XSS/数据泄露/权限绕过）
6. 是否有性能问题（内存泄漏/循环复杂度/不必要的重渲染）
7. 是否有可测试性（纯函数比例/依赖注入/可mock）
8. 是否有可维护性（复杂度/重复代码/魔法数字/注释质量）
```
