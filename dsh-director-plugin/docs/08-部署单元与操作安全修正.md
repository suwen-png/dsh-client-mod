## 一、起因

`T-PLUG-008` 的任务定义是「apply/restore/deploy 支持插件部署单元 + 安装 README」，验收标准写作：

> **双机模拟：复制 → init → apply → 重启即用**

实际状况是：

| 问题 | 现状 |
|:-----|:-----|
| 安装 | **只能手工**：复制 3 类文件 → 建 junction → 编辑 YAML → 清缓存 → 重启 |
| 卸载 | **无工具**：只能人工回忆三处路径，易残留 |
| `scripts/deploy.ps1` | ⚠️ **已失效**：`$SourceDir = "D:\hermes-data\dsh-director"`（废弃路径）、`$PluginDir` 指向旧包名 `dsh-director`、**清理列表含 `Network`** |
| 验收标准 | 「双机模拟」在单机上**无法执行**（会污染真实环境） |

于是本轮要解决三件事：**① 一条命令装/卸**；**② 权威安装文档**；**③ 让「双机模拟」在单机可跑**。

## 二、T-PLUG-008：插件部署单元

### 2.1 三处安装点（缺一不可）

| # | 路径 | 缺了会怎样 |
|:-:|:-----|:-----------|
| ① | `<Harness>/resources/host/node_modules/@deepseek-ai/dsh-director-plugin/` | 插件根本不存在 |
| ② | `~/.dsh/profiles/node_modules/@deepseek-ai/dsh-director-plugin`（junction → ①） | host 启动时报依赖解析失败 |
| ③ | `~/.dsh/profiles/web/cordis.patch.yml` 的 `insert` entry `deepseek-ai.director` | host face 从未被 create ⇒ client bundle 也不会被请求 |

三者共同构成「**包存在** → **可解析** → **被装载**」的必要链条；任何一处缺失都表现为**不报错但功能不生效**。

### 2.2 命令面与三条硬纪律

```bash
node scripts/plugin-install.mjs                       # verify（默认）：只读检查，零写入
node scripts/plugin-install.mjs --apply               # 安装（幂等）
node scripts/plugin-install.mjs --uninstall           # 卸载 ②③，保留 ①
node scripts/plugin-install.mjs --uninstall --purge   # 连 ① 一起删
node scripts/plugin-install.mjs --harness <p> --profile-root <p>   # 重定向（供干净目录模拟）
```

| 纪律 | 落实方式 |
|:-----|:---------|
| **A. 默认零写入** | 无 `--apply` / `--uninstall` 时任何路径都不改 |
| **B. 幂等** | 已就绪报 `unchanged`；entry 不重复插入；② 已存在则校验可解析性而非重建 |
| **C. 绝不删第三方内容** | ③ 是**共享**文件 ⇒ 卸载只做**外科式**移除本插件那一个 entry；`rmSync` 只作用于自己的路径 |

**两个实现细节值得留痕**：

1. **为何是 Node 不是 PowerShell** —— 本机 PowerShell 通道无输出（工作区既有记录），脚本无法自证；且仓库既有工具链全是 `node scripts/*.mjs`。目录 junction 用 `fs.symlinkSync(t, p, "junction")`，Windows 下**免管理员**。
2. **卸载终态必须留 `[]`** —— YAML 里「只有注释」解析成 `null`，而 ③ 的顶层契约是**数组**。`[]` 才是「零个 patch」。且 `--apply` 追加前会**先剔除独立的 `[]` 行**，否则得到 `[]` 紧跟 `- insert:` 的**非法 YAML**。**该缺陷由 uninstall → apply 往返测试实测发现**。

### 2.3 干净目录验收（「双机模拟」的单机实现）

`scripts/verify-install-clean.mjs`（**52 项**）在两个**临时沙箱**（伪 Harness 根 + 伪 profile 根）里跑完整生命周期：

| 节 | 内容 |
|:--|:-----|
| `[A]` | 干净目录首次 `--apply`（★ 含「可被 Loader 发现」判据） |
| `[B]` | 幂等：再跑一次不得重复写入 |
| `[C]` | verify 模式判定「已完整就绪」且零写入 |
| `[D]` | `--uninstall` 外科式移除（②③ 走、① 留） |
| `[E]` | **从已卸载态再 apply**（回归 `[]` 残留导致的非法 YAML） |
| `[F]` | `--uninstall --purge` + 全清后重建 |
| `[G]` | **真实用户环境零触碰反证**（对真实 `cordis.patch.yml` 取前后逐字节快照比对） |
| `[H]` | **三份清单一致性**（安装器 / 本测试 / `package.json#files`） |

**关键设计**：`[G]` 不是「相信脚本不会越界」，而是**对真实环境取前后快照做逐字节反证** —— 让「零触碰」成为**被测量的结论**而非**声明**。

### 2.4 🔴 该测试捕获的真实缺陷（缺陷 A）

| 项 | 内容 |
|:--|:-----|
| **现象** | 本机一切正常，`verify` 报「已完整就绪」 |
| **缺陷** | `plugin-install.mjs` 的 `PAYLOAD_FILES` **漏了 `package.json`** |
| **为何本机正常** | 它早先被**手工**拷入过 ⇒ **环境残留掩盖缺件** |
| **为何后果严重** | host Loader **靠 `package.json` 发现本包**（`dsh-client-modules` 扫描 host Loader entries 中声明 `dsh.client` 的包）。缺件 ⇒ ② 目录存在但**插件永不被装载，且不报错** |
| **双重后果** | ① 干净机器上功能静默失效；② 安装器**自身状态判据就是该文件** ⇒ `hostState` **永远停在 missing**，verify **永不通过** |

**反证实测**（临时移除 `package.json` 后跑本测试）：

| 指标 | 结果 |
|:-----|:-----|
| 失败项 | **8 项转红**（含 `[A10]` `ENOENT ... package.json`） |
| 安装器**自身** `IS_PASS` | **仍为 TRUE** ⚠️ |

> 🔴 **最后一行才是本轮最重要的发现**：安装器对自己造成的缺件**是盲的**。
> 因为它的三个判据（① `package.json` 存在 / ② 是链接 / ③ 含 entry）在缺件时分别退化为
> 「尚未安装（正常）」「已创建」「已追加」—— **每一步都"成功"，合起来却是坏结果**。
> ⇒ **单机幂等测试必然漏检这类缺陷**，只有「干净目录 + 独立声明的期望清单」能暴露它。

**已固化的防复发措施**：`[H]` 节**静态解析安装器源码**提取 `PAYLOAD_FILES`，与测试自身 `EXPECT_FILES`（**刻意独立声明、不共享常量**）及 `package.json#files` 做三方交叉核对。
> 附带修正一处认知：`package.json` 由 **npm 隐式**包含（不写在 `files` 里也进 tarball，实测 `npm pack --dry-run` 7 项含它），但**手工安装器必须显式列出** —— 它不经过 npm。

## 三、T-PLUG-011：缓存误删缺陷族

### 3.1 缺陷清单（4 处）

由 `plugin-install.mjs` 的注释中「历史教训」一句**逆向排查**同类脚本，全仓 grep 定位：

| # | 位置 | 形态 |
|:-:|:-----|:-----|
| 1 | `scripts/deploy.ps1` | 清理列表含 `Network` |
| 2 | `scripts/clear-cache.ps1` | 同上 |
| 3 | `scripts/restart-harness.ps1` | 同上 |
| 4 | `docs/50-信息中心/01` §坑5（标为「**修改前必读**」） | 文字 + **可执行片段**均含 `Network` |

### 3.2 为何 `Network` 不是缓存

| 目录 | 实际语义 | 可否清 |
|:-----|:---------|:------:|
| `Cache` / `Code Cache` / `GPUCache` / `DawnGraphiteCache` / `DawnWebGPUCache` | 渲染与着色器缓存，可再生 | ✅ |
| `blob_storage` | 临时二进制块 | ✅ |
| **`Network`** | **Chromium 的 cookie 存储 + 网络状态**（`Network/Cookies` 等） | ⛔ **禁清** |
| `IndexedDB` / `Local Storage` | 总监与宿主持久化数据 | ⛔ 禁清 |

**与 R5 冻结契约交叉印证**：`src/store/persist.js` 使用 cookie 前缀 **`dsh_director_`** 做总监持久化
⇒ 执行一次旧 `deploy.ps1` / `clear-cache.ps1` 即**总监状态丢失**。这不是「缓存没清干净」这类可自愈问题，而是**真实用户数据丢失路径**。

### 3.3 处置

| 对象 | 动作 |
|:-----|:-----|
| `scripts/deploy.ps1` | **整体退役**为硬失败垫片（`exit 1` + 指引改用 `plugin-install.mjs`）。**全 ASCII 正文** —— 规避 PowerShell 5.1 对无 BOM UTF-8 的编码陷阱（工作区既有铁律） |
| `scripts/clear-cache.ps1` | 从 `$dirsToDelete` 移除 `Network`；把它列入 `$dirsToKeep` 并注明原因；补红线注释（UTF-8 **BOM + CRLF** 原样保留） |
| `scripts/restart-harness.ps1` | 同上（该文件为 **BOM + LF**，按文件自身行尾改写，避免 615 行噪声 diff） |
| `docs/50-信息中心/01` §坑5 | 三处更正（可执行片段 + 正文 + 检查清单），并留「2026-09-12 更正」留痕 |
| `docs/30-开发链路/dsh-director插件开发环境文档.md` | 加「本章已过时」横幅 + §3.2 整段换为部署单元 + §3.3 缓存列表更正 + 故障排查表/关键路径表/开发规范 3 处 |
| `docs/00-统筹入口/07-项目认知初始化报告-20260911.md` | §7.4 与 §2 表两处更正 |

### 3.4 取证方式

- **定位**：全仓 `grep '"Network"'`（脚本）+ `grep Network`（文档），逐处人工判读语义。
- **语义查证**：`Network` 目录内容与 Chromium 数据布局（cookie 库位于 `Network/Cookies`）。
- **契约印证**：与 `persist.js` 的 `dsh_director_` 前缀（R5 冻结）交叉比对 ⇒ 确认影响面。
- **写后回读**：所有改写均先 `assert 锚点命中` 再写，写完 grep 复核；`clear-cache.ps1` / `restart-harness.ps1` 额外复核 **BOM 与行尾未变**。

## 四、可复用教训

| # | 教训 | 依据 |
|:-:|:-----|:-----|
| 1 | **环境残留会掩盖缺件**。「本机正常」不能证明「干净机器正常」——必须用**干净目录 + 独立声明的期望清单**验证部署类改动 | 缺陷 A：漏 `package.json` 在本机完全不可见 |
| 2 | **「每步都成功」不等于「整体正确」**。缺少交叉核对时，一组各自退化为 no-op 的检查会合起来放行坏结果 | 缺陷 A：安装器自身 `IS_PASS` 在缺件时仍 TRUE |
| 3 | **破坏性列表必须逐项查证语义，不能按目录名归类**。`Network` 名字像缓存，实为 cookie 库 | 缺陷 B |
| 4 | **断言「不存在」前先证明判据能命中「存在」** | `07` §五（沿用） |
| 5 | **同一事实只留一份真相源**。安装说明正文落 `INSTALL.md`，README 收敛为指针 | 防止两处漂移 |
| 6 | **改文件前先勘察该文件自身的行尾与 BOM**，不要套用「本轮用 CRLF」 | 上一轮 615 行噪声 diff 的根因（沿用） |
