## 一、为什么要专门做这一项

宿主把**会话记忆**放在 IDB `dsh-director-db` **v3** 的三个 store：

| store | keyPath | 归属 |
|:--|:--|:--|
| `memoryCore` | `projectId` | 宿主会话记忆核心 |
| `memoryDecisions` | `decisionId` | 宿主决策记录 |
| `memoryRisks` | `riskId` | 宿主风险记录 |

既定边界是「**插件不消费宿主记忆 store，历史数据不得删除**」。但存在一条**硬架构约束**与之拉扯：

> 🔴 宿主与插件**共享同一个 DB**。插件**不能升到 v4** ——
> 一旦升版，宿主再以 v3 打开会**直接失败** ⇒ 宿主记忆全部读不出来。
> ⇒ **无法为插件新增独立 store。**

于是批次 7 的层级节点**复用了 `memoryCore`**，靠「**id 前缀 + `level` 字段**」与宿主记录互不干扰。
这属于「**约定隔离**」而**不是**「物理隔离」，是本项目**最大的潜在数据风险面**。
本项任务的实质就是：**把这条约定固化成机器可校验的断言**，并在每次改动后重跑。

---

## 二、隔离机制（现状）

| 维度 | 插件记录 | 宿主记忆记录 |
|:--|:--|:--|
| `projectId`（= IDB key） | `__global__` / `ws_<workspaceId>` / `se_<sessionId>` | 宿主传入的 projectId |
| `level` 字段 | 三值之一：`global` / `project` / `session` | 无 |
| 读取口径 | `getAll()` + schema 白名单过滤 | `get(projectId)` **精确读** |
| 写入口径 | `put()`（`projectId = node.id`） | `put()` |

实测归属：`memoryCore` 共 **11** 条 —— **插件 11 / 宿主 0**，层级分布 `{global:1, project:2, session:8}`。

## 三、🔴 本项发现的主体缺陷：隔离靠「真值判断」而非「白名单」

**原实现**：

```js
return tx("readonly", (s) => s.getAll())
    .then((r) => (r || []).filter((n) => n && n.level))   // ← 只要 level 为真就收
```

**问题**：宿主记忆记录**只要哪天带上一个任意 `level` 字段**，就会被当成层级节点混入总监树 ——
不报错、不崩溃，只是树里凭空多出莫名其妙的节点。属「**约定失效即静默**」类缺陷
（与本项目 2026-09-12 那批「构建通过但运行时报错」同源：**构建通过 ≠ 功能正确**）。

**硬化后**（`src/store/hierarchy.js`）：

```js
const LEVEL_WHITELIST = Object.freeze(Object.keys(LEVEL).map((k) => LEVEL[k]));  // 由 LEVEL 单一真相源派生

export function isHierarchyNode(n) {
    return Boolean(n)
        && typeof n.id === "string" && n.id.length > 0
        && LEVEL_WHITELIST.indexOf(n.level) >= 0;   // level 必须**恰为**三值之一
}
```

**反证（改前 / 改后实测，同一台真机）**

| 注入的宿主形态记录 | 改前（真值判断） | 改后（白名单） |
|:--|:--|:--|
| 无 `level` | 挡住 ✅ | 挡住 ✅ |
| `level: "note"`（伪值） | **泄露 1 条 ❌** | 挡住 ✅ |
| `level: "global"` 但**缺 `id`** | **泄露 1 条 ❌** | 挡住 ✅ |
| 树节点数 | **13**（虚增 2，静默） | **11**（= 真实节点数）✅ |

> 该反证已固化为脚本第 **[4b]** 节的常驻断言，改回真值判断会立刻报红。

**残余风险（显式登记，刻意不再收紧）**：宿主记录若**同时**具备合法 `level` + 字符串 `id`，仍会混入。
不进一步改成「id 前缀白名单」的原因：一旦将来新增 id 方案，**合法节点会静默消失** ——
比混入更难排查。故保留现状并在此登记，由脚本每次运行复核。

| 3 | 记录归属分类 | 4 | 插件/宿主记录**可按 `level` 判别**；插件 `projectId === id`（无静默写失败）；**未越界写** `memoryDecisions` / `memoryRisks`（均为 0） |
| 4 | 隔离性动态反证 | 6 | 注入宿主形态记录 → 插件 `listAllNodes()` **不泄露**；且该记录**确实存在于 IDB**（证明是「被过滤」而非「没写进去」）→ 删除后条数回基线 |
| 4b | 硬化反证 | 6 | 伪 `level` / 缺 `id` 两种形态**均被挡住**；树节点数不虚增 |

插件与宿主**双向读取互不可见**，且该性质已被**动态反证**而非仅静态声明。

## 五、验证口径的两条修正（踩坑留痕）

1. **身份判据必须用 IDB 主键**
   探针记录刻意**不带 `id`**，首版却用 `String(n.id) === PROBE_KEY` 判定「是否泄露」——
   该比对**恒为 0**，断言**空洞通过**。改用 `projectId`（真实主键）后才有判别力。
   > 教训：断言「某物不存在」时，必须先证明**判据能命中存在的情形**，否则是自我安慰。

2. **R5 key 契约应查「定义处」，不查「环境残留」**
   首版断言「localStorage 里存在 `dsh.director.store.*`」。但该 key **只在总监 store 有消息且落过盘后**才存在
   ⇒ 冷启动 / 刚重启必然没有 ⇒ **换个环境就误报**（清缓存重启后实测踩中）。
   改为对 `src/store/messages.js` / `persist.js` 做**源码静态断言**，与运行环境无关。

## 六、🟢 观测口径缺陷 F-DATA-01（**已结案** · 判为假阳性，非数据丢失）

### 6.1 起因
本轮一次冷启动后，探针读到 `dsh.director.store.director-e0w2f3`（原 6600 B）与 IDB `directorStores`
（原 1 条）**双双缺席** → 初判为「重启丢数据」，登记为开放项。

### 6.2 决定性实验（3 次冷启动 · 只读探测）
| 次 | 探测内容 | 结果 |
|:-:|:--|:--|
| 1 | 冷启动后立刻探测 | `dsh.director.*` = 无 **且** `dsh.workspace.view.*` = **无** ← 关键异常信号 |
| 1 | 同一进程内**数秒后**再探测 | `dsh.workspace.view.v5` = **1118 B**（与重启前**逐字节同尺寸**） |
| 2/3 | 冷启动（无总监活动） | `dsh.director.*` = 无（**本就该无**）、`dsh.workspace.view.v5` = **1118 B** 恒定 |

### 6.3 根因（两条叠加，**均为探测侧问题**）
1. **宿主核心数据是「开机后异步写入」的**
   `dsh.workspace.view.*` **不是** `dsh-client-ui-conversation` 写的
   —— 在该宿主 bundle 中 grep `dsh.workspace.view` → **0 处命中**，它由**另一个 bundle** 持有。
   冷启动后立刻探测必然读空 ⇒ **任何「重启前后对比」若不等待，都会把「还没写」误读成「数据没了」**。
2. **`dsh.director.store.*` 只在总监活动时写入**
   `create-store.js#notify → saveDirectorStore`（设计即「任何状态变更都落盘」，
   见该文件 JSDoc「永不丢消息」）。⇒ **冷启动且无总监活动时，该 key 本来就应为「无」**。

### 6.4 判据与结论
- **宿主核心数据未损**：`dsh.workspace.view.v5` 在 3 次冷启动间**恒为 1118 B**；
  IDB `memoryCore` **11 条层级节点**完好；`dsh.sessions.current` 存在。
- **无删除来源**：宿主与插件源码**不存在** `localStorage.removeItem`(针对该 key) /
  `localStorage.clear()` / `deleteDatabase` 任何分支（全仓 grep 取证）。
- ⇒ **原观测不构成数据丢失证据**，降级为**观测口径缺陷**。

### 6.5 已落地的修复（把陷阱写进脚本，防复发）
`scripts/verify-data-safe.mjs` 新增 **[0] 宿主核心数据就绪等待**：取基线**之前**轮询等待
`dsh.workspace.view.*` 出现（超时 60 s），并在第 6 节输出**锚点**：

```
观察: dsh.director.* 残留 0 个 [无] · IDB directorStores=0 · dsh.workspace.view.v5=1118B
      ↑ 冷启动无总监活动时该值本就应为 0/「无」；宿主核心数据以 dsh.workspace.view.* 字节数为锚
```

> **可复用教训**：做「重启前后对比」类数据验证时，**必须先确认被观测对象是「同步写入」还是「异步/按需写入」**。
> 前者可直接比；后者必须**等待就绪**，且要能区分「未写入」与「被删除」——
> 否则会周期性产出**假阳性**，而假阳性会消耗掉真阳性该有的注意力。
