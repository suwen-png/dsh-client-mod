## 一、需求锚定（严格按文档，不自行改动）

### 1.1 用户的显性需求

1. **每一个对话都有一个总监**（对话级）
2. **每一个文件夹都有一个总监**（文件夹级）
3. **最上层有总监负责**（全局级）
4. **总监的逻辑是否完善** —— 要求总监不只是"有个节点"，而是**真的在干活**

### 1.2 文档对"总监"的权威定义

| 维度 | 出处 | 原文要点 |
|:-----|:-----|:---------|
| 本质 | `03号文` §1.2（:27-40） | 总监层 = **会话预处理中枢**。❌不执行业务 ❌不调用工具 ❌不跑业务推理；✅索引检索 → 按需加载 → 上下文筛选精简 → 模型路由 → 组装报文 → 写入提交列 |

## 三、方案列举与评分

评分维度（1–10，**实现成本 = 分越高成本越低**）：信息密度 / 导航效率 / 可扩展性 / 实现成本 / 与现有 UI 一致性。

### 方案 A：只补配置层（职责 5 项 + 继承链）

- 做法：新增 `logic/duties.js` + `store/duty-config.js`，在层级面板加一栏"执行逻辑开关"。
- 优点：改动最小、风险最低。
- 缺点：**总监仍然不能对话**，用户看不到"总监在干活"，M3/M4/M5/M6 全部未解。

| 信息密度 | 7 | 只加配置，无过程可见性 |
| 导航效率 | 7 | 层级面板内多一栏 |
| 可扩展性 | 7 | 继承链可复用于后续能力 |

| UI 一致性 | 8 | 沿用现有卡片样式 |
| **合计** | **38** | |

### 方案 B：只补总监对话流（五区域布局）

- 做法：新建独立总监工作台，含输入栏 + 5 步思考路径 + 对话记录，不动配置。

- 缺点：职责不可配 → 与 §3.1 冲突；无继承 → 与 §3.2 冲突；三级总监只是"三个相同的框"。

### 方案 E（✅ 选定）：层级面板内嵌「总监工作台」—— 配置继承 + 对话流 + 逐层可验

- 做法：在现有三级层级面板右栏**增加一个「总监」页签**，把方案 A 与 B 合并：
  - **执行逻辑面板**：文档 §3.1 五项职责 + 开关 + prompt 模板可编辑，支持**继承**与**向上提交**（§3.2）

  - **自动转发开关 + 转发目标**（§2.3 ④）
  - 每一级节点（全局/文件夹/会话）**各自持有一份职责配置**，继承解析自底向上回溯
- 为何优于 C：智能体/技能面板无数据源，本轮不做空壳；其余全部覆盖。
- 为何优于 D：零宿主改动、零不可逆风险。

| 维度 | 分 | 理由 |
|:--|:--:|:--|
| 信息密度 | 9 | 配置 + 对话流 + 层级树同屏，一屏看全三级 |
| 导航效率 | 9 | 左树选级 → 右栏即切该级总监，无需跳转 |
| 可扩展性 | 9 | 职责项/梯度/面板均可后补（C 的智能体技能面板可后续挂在此骨架） |
| 实现成本 | **7** | 复用现有 store/总结/同步，新增 3 文件 + 改 1 组件 |
| UI 一致性 | 8 | 沿用现有卡片 + 徽标样式，新增页签不破坏既有布局 |
| **合计** | **42** ✅ | |

> **混合点**：吸收 C 的"执行逻辑面板 + 对话流"结构，吸收 A 的"继承链"，吸收 B 的"过程可见"，弃 C 的无源空壳面板、弃 D 的宿主改动。

### 7.4 本轮真机实测发现并修复的 5 个缺陷

| # | 现象 | 根因 | 修复 |
|:--|:--|:--|:--|
| **1** | 面板点击后**完全空白**（`DirectorWorkbench is not defined`） | `DirectorHierarchy.js` 用了 `DirectorWorkbench` 却**漏写 import**。打包器只跟 import 走 → 产物语法合法、构建通过，直到**运行时渲染**才抛错，React 卸载整棵子树 | 补 import + **给打包器加构建期静态检查** `lintUndefinedComponents`：未绑定的 JSX 组件 → **构建直接失败**并报出组件名与行号 |
| **2** | 点发送后 1.8s 消息区**零变化** | `store.addMessage(user)` 写在 5 步**之后**；步骤 1/2/3 会调本地模型（单次超时 60s，串行 3 次）→ 模型不可用时用户盯着空面板等待 | 用户消息改为在 5 步**之前立即上屏**（§2.3 消息流）；`history` 取上屏前快照避免本条重复入上下文；并补 `catch` 分支写【总监异常】，失败不再静默 |
| **3** | 点树节点**选中态不变** | 测试用「textContent 前缀」匹配 `div`，先命中**祖先包裹层**；`click` 只向上冒泡、不向下传给行 → `onSelect` 永不触发 | 树行加 `data-node-id` / `data-selected`（定位唯一、与文案解耦、可回读选中态） |
| **4** | 「向上提交」**取错按钮** | 概览区与工作台各有一个同名「向上提交」，`__byText` 只能靠文档顺序取第一个 | 全部交互元素补 `data-testid`（概览 `h-*`、工作台 `w-*`） |
| **5** | 后续点击**静默失效**（新建无反应） | `guard()` 会把按钮置 `disabled`，而 `click()` 对禁用按钮是原生 no-op；固定 `sleep` 短于实际操作耗时时必然踩中（`summarizeTree` 遍历全树需数秒） | 测试引入 `waitIdle()` **轮询等待空闲**；`I14` 判据由「长度增长」（不幂等）改为 `summaryAt` 时间戳推进 |

> 缺陷 1 与 5 的共性：**构建/测试通过 ≠ 功能可用**。前者是「静态合法、运行时才炸」，后者是「操作静默丢弃」。二者都已固化为防回退断言。

### 7.5 关键约束（不可违反，已写成断言）

1. **不得新增 IDB store / 不得升 DB 版本** —— 宿主与插件共享 `dsh-director-db` v3，插件升 v4 会让宿主以 v3 打开**直接失败**。三层节点复用 `memoryCore`。
2. **`memoryCore` 的 keyPath 是 `projectId`** —— 写入必须注入 `projectId: node.id`，否则 `put()` 缺 key → **静默失败**。
3. **React 必须外置**（ADR-001）—— 打进产物会因双实例崩溃。
4. **宿主零改动** —— 本批次全部改动都在插件包内。

### 7.6 回滚

本批次改动**全在插件包**（`dsh-director-plugin/`，git 纳管），`git revert <commit>` + 重新下发 `lib/client.js` 即可；**宿主 `client.js` 未改动**。
