## 一、为什么 G 区是「宿主注入点」而不是普通可迁移块

G 区是 **`window.__directorCurrentView` / `window.__directorFocusTarget` 两个全局状态变量的写入侧**，它们**寄生在宿主原生组件的生命周期钩子里**（ChatView 的 `useEffect`、ConversationSession 的 `useEffect`）。

这类代码**无法整体搬到插件**，原因是：

1. **载体是宿主 React 组件** —— `ChatView`（7111 起）与 `ConversationSession`（9141 起）都是宿主 `dsh-client-ui-conversation` 内部的组件，插件**不能跨包 value import**（约束 E8）。
2. **写入时机绑定宿主渲染周期** —— `useEffect` / `useLayoutEffect` 的触发点由宿主的 view 切换驱动，插件无法在其外部等价复现。
3. **读取侧在宿主输入分流里** —— 3568 / 3794 两处读 `__directorCurrentView` 决定消息投递给谁（总监 or 对话），**属 F1/F2 范围**，与 G 区构成一条完整链路的「写 → 读」。

**结论**：G 区的正确处置方式是 **`window` 桥接** —— 宿主侧**保留最小写入锚点**（这几行不动），插件侧**提供实现与消费者**。即：

```
宿主（不动，保留锚点）              插件（提供实现 / 消费）
─────────────────────────         ────────────────────────────
G1: ChatView.useEffect    ──写──▶  window.__directorCurrentView
G4: ConversationSession   ──写──▶  window.__directorFocusTarget
                                   │
F1/F2: 输入分流 (3568/3794) ──读──▶ 决定消息投递目标
A11:  layout store.setFocusTarget ──写──▶ store/layout.js（已迁入插件）
```

> ⚠️ **A11 布局 store 的写入已迁至插件**（`store/layout.js:setFocusTarget`，源自 6469 行）。但 **7114 / 9151 两个调用点仍在宿主体内** —— 它们调用的是**全局 `directorLayoutStore`**，插件提供该对象后调用即生效，**无需改动宿主这两行**。这是「宿主留 shim、插件供实现」的典型形态。

## 七、结论

- **G 区不可迁移**（载体是宿主 React 组件 + 跨包 value import 禁止）→ 处置方式为 **宿主保留最小写入锚点 + 插件提供实现**。
- **G 区共 6 个写入/调用锚点**（G1-a/b/c/d + G4-a/b），**全部原样保留**，批次 6 不做改动，仅做**回归校验**。
- **A11 的实现侧（6469）已迁入插件**，宿主 5 个调用点自动指向插件对象 —— 这是本轮批次 2 的连带收益。
- **风险 R7 已澄清**：原判「宿主注入点寄生」的处置结论是 **"不迁，只保"**，而非"想办法迁走"。T6 闭环。
