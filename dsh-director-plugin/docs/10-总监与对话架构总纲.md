## 一、核心架构（一句话）

> **总监是"沟通与治理层"，对话是"执行与产出层"。两者数据元完全独立、界面并排可见、
> 消息双向联动；总监不执行，只负责确定上下文、派活、审核、纠偏、路由。**

```
                    ┌────────────────────────────────────┐
                    │  总监域（独立数据元 · 插件拥有）      │
                    │  总监自己的对话 · 方案 · 审核 · 决策  │
                    └───────────────┬────────────────────┘
                    确定上下文 │ 派活 │ 审核 │ 纠偏（只读引用）
                               ▼
                    ┌────────────────────────────────────┐
                    │  对话域（原生数据元 · 宿主拥有）      │
                    │  原对话逻辑一字不改 · 纯执行         │
                    └────────────────────────────────────┘
```

## 三、数据元规格（要求 1 的落地定义）

### 3.1 两个数据域

| | **对话域** | **总监域** |
|:--|:--|:--|
| **归属** | 宿主（`dsh-client-ui-conversation`） | **插件**（`dsh-director-plugin`） |
| **数据库** | `dsh-director-db` **v3**（🔴 不得变更名/版本） | 🟢 **`dsh-director-plugin-db` v1**（**新建，插件独有**） |
| **内容** | 会话消息、记忆核心、决策、风险 | 总监节点、总监对话、方案、审核、派活、纠偏 |
| **插件权限** | **只读**（不得写、不得删） | **读写** |
| **宿主权限** | 读写 | **不消费** |

### 3.2 总监域 schema（对齐 17 号文 §2.2 原始设计）

> 17 号文原设计 6 个 store，本文档**逐项落名**（store 名加 `director` 前缀以显式声明归属）。

| Store | keyPath | 索引 | 用途 |
|:--|:--|:--|:--|
| `directorNodes` | `nodeId` | `level`, `parentId` | 层级总监节点（global / project / folder / session） |
| `directorConversations` | `messageId` | **`nodeId`**, `createdAt` | **总监自己的对话**（要求 2） |
| `directorPlans` | `planId` | `nodeId` | 总监制定的方案与执行约束（要求 3） |
| `directorReviews` | `reviewId` | `nodeId`, `targetId` | **六维审核**记录（要求 3） |
| `directorDecisions` | `decisionId` | `nodeId` | 决策与**纠偏留痕**（要求 3） |
| `directorTodos` | `todoId` | `nodeId` | 派活 / 待办（17 号文 §2.2 原设） |

### 3.3 唯一允许的交叉点

- **外键形态**：`nodeId` ↔ 宿主的 `workspaceId` / `sessionId`（**只读引用**，仅用于把总监挂到对应层级）。
- **禁止**：联合查询、跨库事务、把宿主记录读进总监 store 后落盘。
- **理由**：交叉点收窄到"一个只读外键"，即**结构性地保证**要求 1 的不变量；一旦放开，隔离就退化为"约定"。

### 3.4 为何「独立库」既满足要求 1、又不破 R5 约束（🔴 关键论证）

> **这是本次架构重构的核心技术判断，用于订正 T-PLUG-009 的结论。**

- T-PLUG-009 的约束原文是：**不得给宿主的 `dsh-director-db` 升 v4**
  —— 因为宿主以 v3 打开，版本不匹配会**直接失败**（IndexedDB 版本协商是全局的）。
- 但「版本协商」只发生在**同一个数据库名**内。**新建一个属于插件自己的数据库（不同 DB 名）**
  **完全不参与宿主的版本协商** ⇒ 对宿主**零影响**。
- **结论**：`dsh-director-plugin-db` v1 既满足要求 1（物理隔离），又不触碰 R5 约束。
  T-PLUG-009 的「复用 `memoryCore` + 约定隔离」是**在错误前提下求得的次优解**，现予**订正**。
- **保留不变**（R5 冻结）：`dsh.director.store.*` / `dsh.director.layout` / `director-main` /
  `dsh.director.config` / DB `dsh-director-db` v3 及其 3 store / cookie 前缀 `dsh_director_`。

### 3.5 迁移与兼容

| 阶段 | 动作 | 安全性 |
|:--:|:--|:--|
| 1 | 新建 `dsh-director-plugin-db` v1，**首次打开自动建库**（`onupgradeneeded` 只在本库触发） | 宿主不可见、不可感 |
| 2 | 读取期**双读**：优先新库；新库无该节点时回落旧 `memoryCore`（**只读**） | 存量不丢 |
| 3 | 迁移期把旧 `memoryCore` 中的**层级节点**（`level` ∈ 白名单）**拷贝**入新库 `directorNodes` | 幂等（按 `nodeId` upsert） |
| 4 | 迁移完成并验证后，**停止回落到旧库**；旧记录**不删**（尊重《锚点契约》"历史数据保留"） | 可回滚 |

### 4.2 焦点路由（要求 5「双向联动」）

- `focusTarget ∈ { "director", "chat" }`，点击左区 → `director`，点击右区 → `chat`。

### 4.4 双向联动链路（06 号文 §4 原文语义，要求 5 的实现）

```
① 左（总监）→ 右（对话）
   用户在总监输入框输入 → 总监整理/确认 → 派活或直接转发
     → 对话域收到消息（走原生 send 路径）
       → ChatFlow（右栏）与 ChatView（对话 tab）**同时**经 useSession 看到新消息

② 右（对话）→ 左（总监）
   用户在对话输入框输入（或右栏点击后提交，focusTarget=chat）
     → 走原生对话逻辑，产出入对话域
       → 总监侧订阅到该 session 的产出变化 → 触发**审核 / 纠偏**（六维）
```

> **「完全一致」的保证机制**：右栏**不持有副本**，而是与主区域**订阅同一 store**
> ⇒ 结构上不可能不一致（而非"同步努力"）。这是 06 号文 §0 选型「不提取 ChatView」的正面理由。

### 7.2 `.gitignore` 的排除面（`workspace/` 是重灾区）

`.gitignore` 头部注释原文：**「本项目核心产物小、状态信息大，git 入仓只保留"可重建物"」**

| 被忽略项 | 纳管数 | 后果 |

**⇒ 结论**：目录设计上把「**可重建物**」入仓是对的；但 **`workspace/` 与 `snapshots/` 里放的是
"不可重建物"**（手写的宿主改造 + 唯一回滚点），二者被同一规则排除 ⇒
**任何一次工作区覆盖或重置，宿主侧新建内容即不可恢复、不可追溯。**

### 7.3 历史上被删除的文件

- `fe6e651`（2026-09-06 · `chore: clean V1.2 batch cleanup`）**批量删除 78 个文件**
  （`scripts/_archived-20260831/fix_*.py`、`scripts/check-*.py`、`scripts/deploy.py` 等一次性探针）。

  ⇒ 后来者无法判断"哪些脚本是资产、哪些是垃圾"。

### 7.4 另一层：**宿主侧改动与 git 完全脱钩**

- `git ls-files workspace/` = **0** ⇒ 宿主 `client.js`（12 001 行）的每一次改造**都无提交记录**；
- 项目文档中多处写着「**快照 + git + `restore.ps1` 三重**」作为回滚保障 ——

**⇒ 综合答案**：新建内容"未被保留"**不是被谁删掉了**，而是
**① 宿主侧改动从未进入版本控制 ② 其唯一回滚点（快照）也未被版本控制 ③ 插件迁移只继承了
"数据与组件"，没有继承"渲染位置与业务不变量"** —— 三者叠加，表现为"东西不见了"。
