## 三、为何 F3/F4「不能迁移」而只能「改为调用插件」

### 3.1 技术障碍（E8 约束的必然结果）

| 依赖 | 位置 | 插件可否获取 |
|:--|:--|:--|
| `concreteConversation(ctx)`（F3） | 宿主组件闭包内（`ctx` 为 registrant context） | ❌ **不可** |
| `scopedConversation(sessions, sessionId)`（F4） | 宿主组件闭包内（`sessions` 为 session store） | ❌ **不可** |

⇒ 二者均为**宿主私有 API**，插件包**无法 import**（跨包 value import 是构建错误，见清单 E8）。

### 3.2 因此的正确形态：宿主 → 插件**单向调用**

```
宿主 F3（持有 ctx 闭包）
   └─ 调用 window.__dshDirectorProcess(...)   ← 插件已挂（批次 4 交付）
         └─ 内部使用插件的 saveDirectorStore / classifyTask / callLocalModel ...
```

**契约已就绪**：批次 4 已挂 `window.__dshDirectorProcess`（真机实测 `typeof === "function"`）。

const dStore = directorStoreFactory(sessionId);

**风险**：极低。带**存在性检查 + 回落**，即使插件加载失败也走原路径。

## 五、⚠️ 遗留架构问题：双份实例（不属本批次，但需登记）

### 5.1 现象

宿主内联实现与插件实现**当前并行存在**，各自持有独立的内存态：

| 层 | 宿主内联 | 插件 | 是否共享 |
|:--|:--|:--|:--:|
| `directorStores` Map | ✅ 独立一份 | ✅ 独立一份 | ❌ **不共享** |
| `directorStoreFactory` | ✅ 独立一份 | ✅ 独立一份 | ❌ **不共享** |
| 持久化 key `dsh.director.store.*` | 写同一 key | 写同一 key | ✅ **共享** |
| `window.__dshMemory` 等契约 | 宿主直接调用 | 插件提供 | ✅ 共享 |
| `window.__dshDirectorProcess` | ❌ 无 | ✅ 已挂 | — |

### 5.2 实际影响评估

- **内存态**：同一页面内，宿主路径与插件路径可能操作**不同 store 对象** ⇒ 可能出现「同页临时不同步」。
- **持久化层**：二者写**同一 localStorage / OPFS key** ⇒ 刷新后最终一致，**不丢数据**。
- **结论**：当前为**可接受的过渡态**（功能可用、数据不丢），但**长期应消除**。

### 5.3 消除方式（硬退坡）与风险

删除宿主内联副本（A1/A2/A4/A5/A6/A7/A8/A9/A10/A14/C1/C2/D1/D2/E1 ≈ 1,400+ 行），使插件成为**唯一真相源**。

| 风险 | 说明 |
|:--|:--|
| 🔴 不可逆 | `workspace/` 被 `.gitignore` 排除，git 无法回滚；仅 `snapshots/snapshot-20260908-131412-before-apply/` 兜底（**且该快照为 A14 剥离前状态**） |
| 🔴 影响面大 | 宿主 `client.js` 是 Harness 实际加载的唯一客户端产物，改坏将导致整个客户端不可用 |
| 🟡 收益递减 | 双份实例在持久化层已统一，硬退坡主要收益是「消除冗余」+「消除同页内存态不一致」 |
