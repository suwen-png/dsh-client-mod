## 〇、结论先行（审计结论，不是设计）

| # | 用户诉求 | **真实现状（代码取证）** | 判定 |
|:-:|:---------|:------------------------|:----:|
| 1 | 「我在总监发的消息，是否经过处理然后发给对话执行」 | `DirectorPage.deliver()`（`DirectorPage.js:375`）只做三件事：`appendDirectorMessage` → `route()` → `flowStore.push()`。**既不调 `runDirector()`（五步），也不调 `sendToChat()`（投递）** | 🔴 **未实现** |
| 2 | 总监对话**持续性** | 消息落 `plugin-db`（IDB，按 nodeId 分桶）⇒ 重启可回读；但**总监的处理过程**（`steps`/`reasoning`）只在 `runDirector` 返回值里，**没有落库**；且 `deliver` 根本没调 `runDirector` ⇒ 无「处理链」可续 | 🔴 半残 |
| 3 | 右下角「发送到该对话」不好用 | `NodeDetailPanel.send()`（`:196`）用 `sendToChat(text, { autoSend: false })` ⇒ **只填充、不发送**。用户点完以为没反应（还得再去按回车） | 🔴 不好用 |
| 4 | 「交给总监」不好用 | `dp-send` → `deliver()` ⇒ 见 #1，不真投递 | 🔴 不好用 |
| 5 | 去掉解释性文案 | R8 常驻提示「输入在**原生对话框**（页面底部）；这里只负责标目标与登记流转…」；`focusNative` 的 toast「光标已送进原生对话框…**打字的还是它，不是插件自建的框**」；多处 `say()` 长句 | 🟡 待清理 |
| 6 | 按钮/边框命名标准化 | 现文案混杂动词短语：「◆ 总监」「⌨ 聚焦原生对话框」「📥 登记为流转」「交给总监整理」 | 🟡 待规范 |
| 7 | 点对话 → 只显示该分支链路，可选含上一层，可往下走 | 导图有**完整血缘树**（`branch-tree.js`）与折叠，但**没有"聚焦单条链路"的视图** | 🔴 未实现 |
| 8 | 导图顶部总览弹窗（左完成 / 右待完成，按文件夹+对话分类，可点，点击显示执行情况，可发消息修正） | 无 | 🔴 未实现 |
| 9 | 总监统筹全流程（想法 → 文档 → 审核 → 蓝图 → 测试）+ 打分（≥3 轮多方位） | 有 `review6`（六维）与 `duties`（五项职责），但**没有"阶段编排"**、没有**打分标准**、没有**三轮机制** | 🔴 未实现 |
| 10 | 总监页实时更新（工作顺序 / 待完成 / 问题记录） | R6 记忆面板 + R2.5 待办有数据，但刷新依赖事件总线；**没有"问题记录"这一栏** | 🟡 部分 |

**一句话**：总监目前是「**记录员**」（记消息、记流转、出路由建议），不是「**执行中枢**」。本轮把它变成执行中枢。

## 二、我的补充（用户授权「你需要补充完善」）

| ID | 补充项 | 为什么必须补 |
|:--:|:-------|:-------------|
| S1 | **投递通道分级 + 归因**：`sendToChat` 可能取不到 composer（总监页与对话页可能是不同 view）。必须三级降级：① 直投 ② `sessions.open(目标会话)` 后重试 ③ 如实报因 | 不补 ⇒ R1 在真机上"看起来通、实际不通"，且 R6 的"有错误"无法定位 |
| S2 | **投递与处理解耦**：`runDirector`（五步）与 `deliverToChat`（投递）分开，各自可单测、可独立降级 | 耦合 ⇒ 一处失败全链静默 |
| S3 | **处理链持久化**：`steps`/`reasoning`/`model`/`branch` 写进消息记录（`parsed` 字段已在 `plugin-db.appendDirectorMessage` 支持） | 没有它，R2「持续性」只剩聊天记录，总监的"判断"每次都从零开始 |
| S4 | **省流不省证据**：删掉界面上的解释长句，但把关键归因**写进 `data-*` 属性**（如 `data-deliver-mode="sent"`）⇒ 界面干净、测试仍可断言 | 直接删掉会连"可验证性"一起删掉 |
| S5 | **问题记录栏**：用户提到但现有 UI 没有。落在 R6 记忆面板加一段（源：`listReviews` 未通过项 + `flowStore` 卡住项） | R5 的"问题记录"是用户点名要的 |
| S6 | **导图总览分类口径**：左"已完成"= `state==='done'` 或 `todo.done`；右"待完成"= 其余。分组键优先 `folder`（workspace），无则归"未分组" | 不定义口径 ⇒ 分不准，用户会说"这明明是完成的" |
| S7 | **打分标准自身要可审**：标准写成**可枚举的评分项**（每项 0–5 分 + 判据），且对标准本身跑一次"标准审核"（可达性 / 不重叠 / 可证伪） | 用户明确说「打分标准也需要进行审核」 |
| S8 | **三轮的"多方位"要落成机制**：R1 规格符合性（对照本文件）/ R2 独立证据源（真机截图 + DOM 回读，不看同一批断言）/ R3 反证（主动构造"应该失败"的输入） | 否则"三轮"会退化为"同一套断言跑三次" |
| S9 | **`FLOAT_DOCK_RESERVE` 同源**：导图弹窗与新增栏位也要避让浮动药丸（复用既有常量，不另写 108） | 本项目已栽过一次（R6/R8 被压住） |
| S10 | **一键回归**：新增闸门纳入既有 `verify-*` 体系，并纳入基线指纹 | 不然新功能下次就被"没人跑的测试"遗忘 |

## 三、设计

### 3.1 A 组 · 总监消息**真流转**（核心，对应 R1/R2/R6/R11）

```
总监页输入框(R8) ──▶ deliver(text)
                       │
                       ├─① 立即上屏：appendDirectorMessage(nodeId, {role:'user'})      ← 不许让用户等模型
                       ├─② 五步处理：runDirector({ store: pageStore, duties, config })
                       │      store = 适配器：getState→当前 msgs / addMessage→plugin-db / setStatus
                       │      产出：{ steps[5], instruction, model, branch, taskType, reasoning }
                       ├─③ 处理结论落库：appendDirectorMessage(nodeId, {role:'assistant', parsed: payload})
                       ├─④ 真投递：deliverToChat(instruction, { sessionId: flowSession })
                       │      三级：direct → openSession+retry → report(reason)
                       │      写后回读：composer 清空 = 已发出（弱证据，记进 data-deliver-mode）
                       └─⑤ 流转登记：flowStore.push → move(DIRECTOR) → move(CHAT, {target: sessionId})
```

**`deliverToChat` 契约**（新增 `bridge/chat-bridge.js` 导出）：

| 步 | 动作 | 成功判据 | 失败判据 |
|:-:|:-----|:---------|:---------|
| 1 | `findComposer()` | 可见 | → 进第 2 步 |
| 2 | `openSession(sessionId)` + 等 450ms | 拿到 composer | → 进第 3 步 |
| 3 | 再 `findComposer()` | 可见 | `{ok:false, mode:'failed', reason:'composer-unavailable'}` |
| 4 | `sendToChat(text,{autoSend:true})` | `mode==='sent'` 且回读为空 | `mode==='filled'`（发送按钮 disabled）或抛错 |

**降级铁律**（§4.3）：任何一步失败都必须 **返回原因 + 在 UI 上可见**，禁止静默。

### 3.2 B1 组 · 分支链路聚焦（对应 R9）

新增 `logic/branch-focus.js`（纯函数，可离线单测）：

| 函数 | 语义 |
|:-----|:-----|
| `focusChain(rows, sessionId, { includeParents })` | 返回该会话的**下游链路**（自身 + 所有后代，按行序）；`includeParents=true` 时并上「祖先链」 |
| `upstreamOf(rows, sessionId)` | 祖先链（排除自身） |
| `downstreamOf(rows, sessionId)` | 后代集合（含自身） |
| `focusSummary(rows, sessionId, opts)` | 统计：本链 N 个 / 上游 M 个 / 下游 K 个 |

UI：导图节点点击 → 进入"聚焦态"（`data-focus="1"`），只渲染链路行；顶栏出现两个开关：
`含上一层 (mm-focus-up)` / `下钻 (mm-focus-down)`（有子节点才可用）。

### 3.3 B2 组 · 导图总览弹窗（对应 R10）

新增 `components/OverviewDialog.js`，挂在 `MindMap` 的**最上面**（`mm-top` 之上，独立 fixed 层）。

```
┌─ 总览（mm-ov）────────────────── ✕ ─┐
│ ┌ 已完成 (N) ─┐  ┌ 待完成 (M) ─┐   │   左列 / 右列，各自按「文件夹 → 对话」两级分组
│ │ ▸ 文件夹 A  │  │ ▸ 文件夹 A  │   │   每条：状态点 + 标题 + 来源标签
│ │   · 对话 1  │  │   · 对话 3  │   │
│ └────────────┘  └────────────┘   │
│ ┌ 详情（选中条目）──────────────┐  │   点条目 → 左下方显示"执行情况"
│ │ 状态 / 依据 / 最近动作 / …    │  │   + 输入框 → 「发送修正」(mm-ov-send)
│ └──────────────────────────────┘  │
└──────────────────────────────────┘
```

分类口径（S6）：完成判定 `state==='done' || todo.done===true`；分组键 `row.folder || '未分组'`。
点击条目 → 左列下方 `mm-ov-detail` 显示：当前状态 / 依据（哪条信号）/ 最近一次流转 / 消息数；
下方输入框 + `mm-ov-send` → 走 §3.1 的 `deliverToChat`（可发消息修正）。

### 3.4 C 组 · 总监统筹闭环 + 打分审核（对应 R3/R4）

新增 `logic/orchestrate.js`（纯函数为主）：

| 阶段 | key | 产出物 | 进入下一阶段的条件 |
|:----:|:----|:-------|:------------------|
| 1 | `plan` | 需求理解 + 任务拆分清单 | 拆分非空 |
| 2 | `doc` | 设计/开发文档 | 文档非空且含"验收判据" |
| 3 | `review` | 打分（≥3 轮） | 总分 ≥ 阈值（默认 70%） |
| 4 | `blueprint` | 蓝图 / 施工图 | 蓝图非空 |
| 5 | `test` | 测试计划 + 结果 | 计划含"期望结果" |
| 6 | `done` | 收口 | — |

**打分标准（本文件定义，代码常量与之同源）**：

| # | 维度 | 0–5 分判据（摘） |
|:-:|:-----|:-----------------|
| 1 | **核心目的达成** | 5=用户原话逐条可对上；0=与目标无关 |
| 2 | **前端审美** | 5=与宿主令牌同源、无割裂色；0=硬编码色/对比度 <3:1 |
| 3 | **按钮与交互** | 5=每颗按钮有真实回调 + 回读证据；0=点了无反应 |
| 4 | **边界与降级** | 5=失败可归因 + 有降级路径；0=静默失败 |
| 5 | **一致性** | 5=复用既有常量/令牌，无重复真相源；0=另起一套 |
| 6 | **可验证性** | 5=有自动化断言且断言承重；0=无证据 |

**三轮机制（S8）**：
- 第 1 轮 **规格符合性**：逐条对照本文件 §一 的 R1–R12。
- 第 2 轮 **独立证据源**：不引用第 1 轮的断言，改用真机截图 / DOM 回读 / 网络无关的独立探针。
- 第 3 轮 **反证**：构造"应该失败"的输入（空消息、composer 不可见、目标会话不存在），断言**它确实失败且原因正确**。

**打分标准的审核（S7，独立一条）**：
`auditRubric()` 检查三条 —— ① 可达性（每档分都举得出例子）② 不重叠（维度两两不涵盖同一判据）
③ 可证伪（存在能打出 0 分的输入）。三条全过才允许用该标准打分。

### 3.5 D 组 · 文案与命名规范（对应 R7/R8）

**规则**：① 按钮 = 标准动词/名词（2–4 字），不含解释、不含破折号从句；② 一切说明进 `title`（≤ 20 字）；
③ 界面上的常驻说明句删除（信息改走 `data-*` + `title`）。

| 位置 | 现文案 | 新文案 | title |
|:-----|:-------|:-------|:------|
| `dp-route-director` | `◆ 总监` | `总监` | 输入目标：总监 |
| `dp-route-chat` | `💬 对话` | `对话` | 输入目标：对话 |
| `dp-focus-native` | `⌨ 聚焦原生对话框` | `定位输入框` | 定位到原生输入框 |
| `dp-register-flow` | `📥 登记为流转` | `登记流转` | 把当前输入登记为流转 |
| `dp-send` | `交给总监整理` | `执行` | 经总监处理并发送到对话 |
| R8 常驻提示 | 「输入在**原生对话框**（页面底部）……」 | 删除 | — |
| `focusNative` toast | 「光标已送进原生对话框…不是插件自建的框」 | `已定位输入框` | — |
| `nd-*` 发送 | `发送到该对话` | `发送` | 直接发送到该对话 |
| `mm-route` | `交给总监判断` | `交由总监` | — |

## 四、测试计划（**先写"测什么 + 期望结果"**，对应 R12）

### 4.1 测试需求（测什么）

| TB | 被测行为 | 期望结果（Expectation） |
|:--:|:---------|:------------------------|
| TB-1 | 总监页输入一句话并点「执行」 | ① 总监消息区出现 1 条 user + 1 条 assistant（带五步结论）② 原生 composer 被清空 ③ `data-deliver-mode="sent"` |
| TB-2 | 刷新/重进后读总监消息 | 上一条 user/assistant **都在**，且 assistant 的 `parsed.steps` 长度 = 5 |
| TB-3 | 连续两次输入 | 第 2 次的 `history`（处理入参）**不为空**（含第 1 次） |
| TB-4 | 点「发送」（NodeDetailPanel） | composer 被清空 + 对话区消息 + `mode==='sent'`（不是 `filled`） |
| TB-5 | 会话无 composer 可用时点「发送」 | 返回 `ok:false` 且 `reason` 非空，UI 显示原因 |
| TB-6 | 导图点某会话 → 聚焦 | 只渲染该链路行；`含上一层` 打开后行数增加；关掉回到原状 |
| TB-7 | 导图总览弹窗 | 左/右列条数 = 按口径算出的数；分组标题 = 文件夹名 |
| TB-8 | 点总览条目 | 详情区出现该条目状态；`mm-ov-send` 可投递 |
| TB-9 | 打分 | 返回 6 维分数 + 总分 + 轮次；`auditRubric()` 三条全过 |
| TB-10 | 反证 | 空消息 → `ok:false`；不存在会话 → `ok:false,reason` 明确 |

### 4.2 测试流程（**≥3 轮，每轮含"审核 → 改 → 再审核"**）

| 轮次 | 内容 | 通过标准 |

### 6.1 各轮共性结论（值得单独记的十二条）

1. **假绿灯比红灯更贵**：第 1 轮里 `dp-send` 点击本身成功、`mode` 也曾经显示过 `sent`，
   但**消息其实没到智能体**（宿主的 `__directorSubmit` 抛 `session.prompt is not a function`）。
   ⇒ 本轮为此新增**宿主侧第三方凭据**（`G6`：`__directChatProbe.called` 增量），
   不再用"我们自己账本上记了一笔"当送达证据。
2. **同名函数重复声明是"静默的"**：语法自检、绑定对账、打包器**全都看不到**。
   ⇒ 已在 `build/build.mjs` 加 `lintDuplicateFnDecl`（构建期按作用域栈判定），
   并在 `verify-bundle.mjs` 加产物级反证（`deliver` 声明数 = 1）。
3. **起点不复原 ⇒ 时红时绿**：同一份代码在 r2 红、在 r1/r3 绿，差别只在"D8 点到了哪个会话"。
   ⇒ 测试脚本必须**自己建立前置**（`G0` 前置自检 + D 段环境复原）。
4. **"还原"要还原到**跨轮次**也成立**：`r5tab`（R5 页签）与"起点会话"都是**跨轮存活**的界面状态。
   不还原的后果是**"重启后第一轮绿、之后全红"** —— 这类假红最难查（r7 绿 / r8 起红）。
   ⇒ 两条固定动作：① 动过的界面状态当场还原（G3b 后切回流转页签）；② **阶段 0 无条件归位**
   （不靠上一轮自觉）；③ 起点会话按 **sessionId** 复原（"composer 可见"不等于"回到起点会话"）。
5. **断言要"等下界"，不要"等固定拍"**：位置/异步挂载类断言改为**等收敛**
   （`settleDock()` ≤1.5s / 等目标条目出现 ≤2s），并把收敛耗时打进日志 ——
   于是"慢"（正常滞后）与"不动"（真缺陷）在日志上可分辨。
6. **组件推导值 ≠ 渲染结果**：`segFlow` 写着「流转 1」而 `dp-flow-item` 是 0 ——
   只读"组件算出来的数"会漏掉"渲染没跟上"。穿透探针必须同时给三层：
   **数据**（store 里的 flows）、**组件推导值**（分段键文案）、**DOM 事实**（testid 计数）。
7. **"以为关了"与"选择器写错"是同一类事故**：`closeOverlays` 用裸名当选择器 ⇒
   `exists()` 恒 0 ⇒ 清场**静默无效**（r15 的 A6/B2–B8 全由它而来）。
   ⇒ 清场类动作一律**自带自检**并把残留打进日志。
8. **"点不中"往往是布局在动，不是按钮坏了**（r19/r20 最大收获）：用户说"两个按钮点击
   不好用"，第一反应会去翻按钮的 `onClick`／`disabled`／`z-index` —— 全错。真因是
   **一句提示把整条焦点条顶走了 23px**：手指移过去的那一刻，按钮已经不在原来的位置。
   判据必须升级为「**出提示的前后，按钮坐标逐像素不许变**」（D5p），
   否则"点击时它在不在"这种自检**永远抓不到它**（读数时它确实在）。
9. **事件驱动的复量不能只挂在 rAF 上**（r19 F11 定案）：`requestAnimationFrame` 在
   窗口被遮挡时会被 Chromium **暂停**，而"跑 e2e 时窗口在后台"恰恰是常态 ⇒
   只靠 rAF 的实现会偶发"永远不跟"。凡是"DOM 变了就要复量"的逻辑，
   都要有一条**不依赖帧**的通道（MutationObserver 回调里直接量）。
10. **同一类缺陷已经出现四次**：`r5tab`（页签）/ 导图 `focusId` / `nd-panel`（开关）/
    `collapsed`（折叠集合）——**都是"跨轮存活的组件 state 与当前数据对不上"**。
   ⇒ 统一纪律：**派生值只从当前数据推，不读可能过期的容器**；
   表单/树/列表这类"作用于集合"的开关，读取前必须先与当前集合对账。
11. **"跳过"比"红"更危险**（r22 定案，用户要求"测试起码过三次"的必然推论）：
    红有人看，**跳过没人看**。r19/r20 的导图一直有 **5 条跳过**，报告写的是一句
    「本机数据如此」——而探针 `m1` 实测本机血缘**有 3 层 / 19 个节点**，那句话是**假的**。
    跳过掩盖的正是 C-M14a–f（右键菜单）、C-M15a–c（悬浮工具条）、C-M16a（Esc 逐层退）、
    C-M8a–d（折叠/展开）**共 19 条真断言**；把它们变真之后**立刻逮到 1 条实缺陷**级失败（C-M15a0 的
    前置缺失）。⇒ 三条纪律：① 跳过**必须带可分辨原因**（本脚本给 `focusVisibleNode()` 加自诊断
    `window.__mmFocusWhy`，打出 `body / nodes / inView / hitSelf`）；
    ② **不许用不可证伪的话收尾**（"本机数据如此""环境限制"）；③ 能建前提就建前提，不能建就显式报缺什么。
12. **闸门自己会过期**（r21 定案）：同一天抓到 5 处，全部是**旧断言把"现状变了"读成"功能坏了"**。
    最典型的是 `batch1` —— 它拿「宿主里还有 1 处越界引用」当**我方产物健康**的凭据，
    可那是**取证期的现场**；宿主补丁一落地，命中数从 1 变 0，断言立刻假红。
    ⇒ 判据口诀：**写死的版本号 / 写死的计数 / 单字符字符类，都是定时炸弹**；
    "已修好"的证据要写成**双向一致性**（两侧都归零 + 都能找到同一处修正），
    而不是"某处还剩一个坏点"。**先审闸门，再信闸门。**
